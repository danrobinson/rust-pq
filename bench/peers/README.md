# SLH-DSA provider benchmark

The benchmark exercises the five functions in each parameter set's public FIPS 205 API. It compares seeded key generation, public-key extraction, deterministic signing, signing with caller-supplied randomness, and successful verification. It covers all six SHA-2 and all six SHAKE parameter sets at 32 bytes and 1 MiB. A second matrix measures six key conversion operations for all twelve sets on the same platforms. It covers raw private/public key import, PKCS#8 encode/decode and SubjectPublicKeyInfo encode/decode. The three providers must produce identical DER and recover the original raw keys. These operations take keys as input and have no message-size axis. RustCrypto and EVP construct owned key objects on import. The library returns fixed-size byte arrays. Its specialized DER functions accept the canonical encoding, while the peer decoders provide general DER processing.

The timings exclude internal tree/hash primitives and adapters, signature-length checks, and constant-time private-key byte equality. The latter two are byte predicates. For example, OpenSSL's key comparison can compare public components, which would give it different private-key equality semantics.

The library uses `platform-sha2`. The comparator is RustCrypto `slh-dsa` 0.2.0-rc.5 with the dependency versions and default features in the library's lockfile. Both use Rust's optimized bench profile and the same binary. OpenSSL 4.1.0 uses the default provider through its EVP interface. The Linux builds used the official release commit and its default assembler optimizations, with `./Configure no-shared no-tests` and `make -j2 build_libs`. Apple used Homebrew's shared OpenSSL 4.1.0. [OpenSSL release source](https://github.com/openssl/openssl/tree/2f4e3a5fec05394068cfa7379890ab552483a8a6) · [OpenSSL signing parameters](https://docs.openssl.org/4.0/man7/EVP_SIGNATURE-SLH-DSA/)

The EC2 fleet used on-demand `.large` instances in `us-east-1` and Amazon Linux 2023. The 8124M used `c5n.large`. AWS assigned the first `c5.large` an 8275CL, which appears as an additional result. The newer Xeon used `c8i.large`, EPYC used `c8a.large`, and Graviton2 and Graviton4 used `c6g.large` and `c8g.large`. The instance images were `ami-0aacbf72109c53c0c` (x86-64) and `ami-04af8b6fff5606f81` (AArch64). The OpenSSL source tarball from GitHub's codeload endpoint at the pinned commit had SHA-256 `3eb00d3dbf2b3393dcf1cb82127a3d19ed911cec4e8315fe2ca20f3038b5ddde`.

Each workload starts with one warm-up round. The six measured rounds use all six permutations of provider order. Within a round, all three providers use identical key seeds, empty contexts, messages and additional signing randomness. Each invocation measures keygen and each sign once, verification 32 times, and public-key extraction 256 times. Times are elapsed nanoseconds per call. Private and public key bytes and both complete signatures must agree across providers at every message size and round. Each provider also verifies its deterministic signature and rejects it under a different context. These checks occur outside the signing measurements.

The caller supplies entropy to every provider, including OpenSSL's test-entropy option for hedged signing. This measures the algorithm with identical inputs across providers and excludes operating-system entropy acquisition. OpenSSL fetches algorithms and prepares the key-generation context outside the timers, then measures EVP key generation, including private-key object construction. It retains the keys and fetched signature algorithm. Signing allocates a signature buffer and creates, initializes, and releases an EVP context. Each verification also creates, initializes, and releases a context. The Rust library accepts raw key bytes while RustCrypto retains its typed key. Public-key extraction measures each API producing raw public-key bytes, including provider dispatch in EVP. Its subnanosecond and low-nanosecond results are sensitive to compiler optimization and timer overhead.

To benchmark the current checkout, copy the committed source and drivers into a disposable directory. From the repository root, run

```sh
run_dir=$(mktemp -d)
git archive HEAD rust bench/peers | tar -x -C "$run_dir"
cd "$run_dir"
bash bench/peers/run.sh
bash bench/peers/run-encodings.sh
```

The scripts replace the benchmark entry point in the disposable tree and write per-call samples, vector checks and host metadata under `out/`. The published runs used Rust 1.100.0. Linux requires OpenSSL 4.1.0 built under `$HOME/openssl` and affinity to CPU 0. Apple uses Homebrew OpenSSL 4.1.0 and normal scheduling. The seven-platform report lists the exact source revisions. [Measured sources and validation](../results/peers-optimized/README.md#source-and-validation)

From the repository root, `python3 bench/peers/summarize.py bench/results/peers-optimized` reads the combined samples and generates one row per CPU, input size, set and operation. It reports each provider's median latency and each peer's latency divided by this library's latency, paired within rounds before taking the median. A value above 1 means this library ran faster. The aggregate tables give equal weight to each parameter set and, for signing API workloads, each message size, using a geometric mean of the per-workload paired medians. Key generation and public-key extraction ignore message size, so their two length rows are repeat measurements. The paired minima and maxima describe observed variability.

For higher-resolution RustCrypto comparisons on raw key extraction and import, copy `raw-keys.rs` to `rust/benches/platforms.rs` in the disposable tree. Build the same release bench with the features and flags in `run.sh`. Run that executable without arguments, pinned to CPU 0 on Linux. It reports 21 paired samples per operation, with alternating provider order and 100,000 calls per provider per sample. Discard round zero before summarizing.
