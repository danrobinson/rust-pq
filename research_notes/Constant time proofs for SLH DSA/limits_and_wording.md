# Limits of a source/IR-level constant-time proof, and how verified-crypto projects word the claim (as of 2026-11-21)

Scope reminder: the theorem under discussion is a Lean 4 proof over the Aeneas/Charon translation of Rust MIR for SLH-DSA-SHA2-128s (no secret-dependent control flow, memory-access indices or variable-time operands at IR level). Target hardware is AArch64 (Apple Silicon, generic ARMv8), with portable SHA-256 or the ARMv8 SHA-256 instructions.

How to read the evidence tags on each bullet (all sources fetched 2026-11-21):

- **[V]** = quoted verbatim from raw text I downloaded and read (README, source file, abstract, standard, commit message).
- **[F]** = short quotes/facts as extracted from the page by the fetch tool's summariser; very likely exact, but not independently re-read by me.
- **[S]** = taken from a search-result summary only; treat as a lead, verify before quoting.

## 1. Compilers breaking constant-time: documented cases, and which constructs are at risk

### Takeaway
Every documented compiler-introduced leak found starts from source that already computes something *conditional on a secret* in branch-free form (mask/select, comparison-to-mask, addition or xor of a secret carry/flag, table scan), or that divides a secret; the compiler recognises the idiom and re-materialises a branch, a secret-dependent address, or a variable-time instruction. No source found documents a compiler adding a secret-dependent branch to code that only copies and hashes secrets with public loop bounds, but no source proves that cannot happen either, and the largest study explicitly says safety "just by looking at the source code" could not be established.

### Cited Findings
- **Breaking Bad (Schneider, Lain, Puddu, Dutly, Čapkun; arXiv Oct 2024, v2 Sep 2025; ACM ASIA CCS '25).** Tested 8 libraries (HACL\*, Libsodium, Botan, BearSSL, BoringSSL, OpenSSL, WolfSSL, MbedTLS), GCC 5–13 and LLVM 5–18, 7 optimisation levels, 6 architectures (x86-64, x86-i386, armv7, **aarch64**, RISC-V, MIPS-32); 6,608 binaries / 44,604 experiments attempted, of which 5,716 binaries / 37,818 experiments completed. The paper says defensive techniques are "still inadequate, incomplete, and bound to fail" when combined with compiler optimisations. [F] — [arXiv 2410.13489v2](https://arxiv.org/html/2410.13489v2)
- Breaking Bad, constructs broken: (a) bitmask conditional move (HACL\* `cmovznz4`): "LLVM understands the bitmask generation and arithmetic logic and replaces it with a select IR instruction" (InstCombine), then the backend lowers it to branches (RISC-V, x86-i386) or address computations (MIPS, armv7); (b) BearSSL modular exponentiation: mask select turned into `cmov` (x86-64) / `csel` (AArch64) computing a **secret-dependent memory address** ("On Aarch64, LLVM inserts csel instead of cmov"); (c) BearSSL `check_scalar` comparison turned into a secret-dependent branch by recent LLVM on RISC-V; (d) "arithmetic shortcuts": Botan 128-bit software addition, where "binaries by some compilers first check the carry and skip the second addition if the carry is not set" — GCC on MIPS and x86-i386 "under all optimization levels (including no optimization -O0)"; Botan GHASH key schedule (LLVM 15, RISC-V): "If carry is 0, then jump over the XOR"; (e) BoringSSL P-256 compound branch condition split by LLVM (rare). [F] — [arXiv 2410.13489v2](https://arxiv.org/html/2410.13489v2)
- Breaking Bad on formally verified code: issues appear "even when the high-level source code was formally verified to be free of side channels"; "Notable findings include issues in libraries that were formally verified to be free of such side channels" (the HACL\* secp256 cmov pattern under some LLVM versions). [F] — [arXiv 2410.13489v2](https://arxiv.org/html/2410.13489v2)
- Breaking Bad on predicting safety from source: "We did not find a way to ascertain if a specific arithmetic source code pattern is safe just by looking at the source code." The poly1305-donna bitmask pattern produced no secret-dependent operations in any tested compiler, but the paper notes that small source changes can introduce them. Mainstream architectures (incl. aarch64) "seem to be less affected but not entirely free of compiler-induced issues". [F] — [arXiv 2410.13489v2](https://arxiv.org/html/2410.13489v2)
- Breaking Bad threat model: targets "secret-dependent memory access and control flow operations" and explicitly excludes "instructions that exhibit variable timing based on their arguments" (so it does not measure compiler-introduced variable-latency instructions). The authors' method "can find issues but cannot prove their absence". [F] — [arXiv 2410.13489v2](https://arxiv.org/html/2410.13489v2)
- Breaking Bad recommendations: continuous testing across many architectures and compilers "should be the standard for cryptographic libraries"; libraries should publish the list of tested architectures, compilers and flags; principled options are formal analysis of the binary or a compiler with guarantees such as CompCert. [F] — [arXiv 2410.13489v2](https://arxiv.org/html/2410.13489v2)
- **"clangover" (Antoon Purnal, PQShield, June 2024; CVE-2024-37880).** "compiling the Kyber reference implementation with Clang may result in the emission of a secret-dependent branch" in `poly_frommsg` (a masked loop over message bits). Affected: Clang 15–18 on x86 with `-Os`, `-O1`, `-O2 -fno-vectorize`, `-O3 -fno-vectorize`; "it takes between 5-10 minutes to leak the entire ML-KEM 512 secret key" (i7-13700H, Clang 16.0.6). The PoC is x86-only; AArch64 is not mentioned. [F] — [clangover repo](https://github.com/antoonpurnal/clangover); [NVD CVE-2024-37880](https://nvd.nist.gov/vuln/detail/CVE-2024-37880); [pqc-forum thread](https://groups.google.com/a/list.nist.gov/g/pqc-forum/c/hqbtIGFKIpU)
- Mozilla's NSS bug for the same rewrite notes the pattern is common in "constant time" C code, and Mozilla engineers doubted the upstream source patch would survive unified builds, suggesting a value barrier instead; D. J. Bernstein questioned whether the patch survives LTO. [S] — [Mozilla bug 1900430](https://bugzilla.mozilla.org/show_bug.cgi?id=1900430); [pqc-forum thread](https://groups.google.com/a/list.nist.gov/g/pqc-forum/c/hqbtIGFKIpU)
- **Rust case: RUSTSEC-2024-0344 (curve25519-dalek, 18 June 2024).** `Scalar29::sub`/`Scalar52::sub` "contained usage of a mask value inside a loop" and "LLVM saw an opportunity to insert a branch instruction" (`jns` on x86). Fix: "introduce a volatile read as an optimization barrier" (patched >= 4.1.3). Found by Alexander Wagner and Lea Themint with the DATA binary-analysis tool (Fraunhofer AISEC). [F] — [RUSTSEC-2024-0344](https://rustsec.org/advisories/RUSTSEC-2024-0344.html)
- **KyberSlash (TCHES 2025; ePrint 2024/1049).** "two timing vulnerabilities in several implementations (including the official reference code)" from secret-dependent division; demonstrated on Arm Cortex-A7 and Cortex-M4. The authors "patch the dynamic analysis tool Valgrind to allow detection of variable-time instructions operating on secret data, and apply it to more than 1000 implementations of cryptographic primitives in SUPERCOP" and propose "a more rigid approach to guarantee the absence of variable-time instructions in cryptographic software using formal methods". [V] — [ePrint 2024/1049](https://eprint.iacr.org/2024/1049)
- KyberSlash FAQ on why source inspection does not settle the instruction used: "Does a division in C, C++, Go, Rust, etc. always turn into a division instruction in machine language? Not necessarily. There are some important combinations of CPUs, compilers, and compiler options that will convert divisions with public denominators into multiplications. For example, on Intel/AMD CPUs, gcc -Os (size optimization) will produce division instructions, but gcc -O3 (time optimization) will produce multiplication instructions." [V] — [KyberSlash FAQ](https://kyberslash.cr.yp.to/faq.html)
- **Binsec/Rel (Daniel, Bardin, Rezk; IEEE S&P 2020).** Binary-level relational symbolic execution over 338 cryptographic binaries; found that gcc `-O0` and clang backend passes introduce violations in code that an LLVM-IR-level verifier (ct-verif) had accepted; e.g. a mask-based `ct_select` compiled by clang `-O3 -m32 -march=i386` to a conditional jump. [S] — [arXiv 1912.08788](https://arxiv.org/pdf/1912.08788); [Binsec S&P'20 page](https://binsec.github.io/nutshells/sp-20.html)
- **Fun with flags (Geimer, Maurice; arXiv July 2025; PriSC @ POPL 2026).** Studied LLVM 12/18 and GCC 9/13 at O3/Os on x86 (AArch64 not covered). Responsible passes — LLVM: loop unswitching ("SimpleLoopUnswitchPass considers select IR instructions as well"), loop vectorisation, cmov conversion (x86 backend and CodeGenPrepare), with InstCombine creating the `select`; GCC: loop unswitching, jump threading, path splitting. Affected source patterns: bit-mask arithmetic, constant-time table lookups, equality-to-mask helpers, ternaries in loops. Proposed flags (`-mllvm --x86-cmov-converter=false -mllvm --disable-cgp-select2branch=true`, `-mllvm --unswitch-threshold=1`, `-fno-vectorize`; GCC `-fno-unswitch-loops -fno-thread-jumps -fno-split-paths`) removed all violations in their benchmark, but the approach "does not guarantee completeness: there may exist other passes or interactions that introduce vulnerabilities." [F] — [arXiv 2507.06112](https://arxiv.org/html/2507.06112v1)
- BoringSSL's own source comment on the select idiom: "Clang recognizes this pattern as a select. While it usually transforms it to a cmov, it sometimes further transforms it into a branch, which we do not want. Hiding the value of the mask from the compiler evades this transformation." [V] — [BoringSSL crypto/internal.h](https://github.com/google/boringssl/blob/main/crypto/internal.h)
- The LLVM constant-time RFC names the mechanism: early InstCombine iterations "replace the constant-time selection recipe's mask creation and bitwise operations with IR `select`", and `x86-cmov-conversion` can then "replace `cmovcc` with a conditional jump or branch". [F] — [LLVM RFC, Aug 2025](https://discourse.llvm.org/t/rfc-constant-time-coding-support/87781)

### Inferences
- Constructs with documented compiler-introduced leaks: boolean/mask selects (including pointer selects that become secret-dependent addresses), comparison-to-mask helpers, conditional add/xor keyed by a secret carry or mask, masked operations inside loops (unswitched or given an early exit), constant-time table scans, and division/modulo. All of them require the *source* to compute something conditional on a secret.
- Constructs with no documented case found: bounds checks on public indices, loops whose trip count is public and whose body contains no secret-conditional operation, plain copies of secret bytes, and straight-line add/rotate/xor/and hashing. For these the honest statement is "no known instance, no proof of absence" rather than "safe".
- The closest counter-example to "pure arithmetic is safe" is Botan's 128-bit add: there the *source* computes a secret carry bit and adds it, and GCC (MIPS, i386 only) emitted "skip if carry is zero". A 32-bit modular add inside SHA-256 has no separately materialised carry at source level on a 64-bit target, so this specific rewrite has no obvious analogue on AArch64; that is an argument from mechanism, not a guarantee.
- SHA-256's Ch and Maj are bitwise multiplexers over full 32-bit words (the "mask" is arbitrary secret data, not an all-ones/all-zeros flag). The select-recognition rewrites documented above act on 0/−1 masks derived from a boolean; I found no report of Ch/Maj being turned into a branch. Worth a one-off disassembly check since it is cheap.
- An IR-level "no variable-time operand" statement does not fix which machine instruction is emitted: the compiler may turn a division into a multiplication or vice versa depending on flags and target (KyberSlash FAQ), so the claim should name what is assumed about instruction selection.
- Because every existing study is x86-centric for exploitation and none tested rustc output, results cannot be read as "AArch64/Rust is unaffected", only "less evidence".

### Gaps
- No study found that measures compiler-introduced leaks in Rust crates at scale (Breaking Bad and Fun with flags do not mention Rust; the dalek advisory is a single case).
- Breaking Bad reports no per-architecture counts in text for aarch64; only one aarch64 case (BearSSL modpow/`csel`) is described.
- Breaking Bad's Table 2 lists flags for Botan HMAC primitives (hmac-sha1/sha2/blake2) but the text does not explain them individually; I could not determine whether they come from the hash core or from surrounding code.
- Conflict: the Trail of Bits blog describes the ETH study as "19 libraries across five compilers"; the paper text read here says 8 libraries with GCC and LLVM version ranges. I could not reconcile these — [Trail of Bits, Dec 2025](https://blog.trailofbits.com/2025/12/02/introducing-constant-time-support-for-llvm-to-protect-cryptographic-code/) vs [arXiv 2410.13489v2](https://arxiv.org/html/2410.13489v2).
- No source found stating positively that code with no secret-dependent select/compare/index is immune to compiler-introduced leaks.

## 2. rustc/LLVM-specific facts: bounds checks, `black_box`, LLVM constant-time intrinsics, Rust RFCs, auto-vectorisation

### Takeaway
As of November 2026 neither Rust nor LLVM offers any mechanism that guarantees constant-time code generation; the Rust standard library documentation says so in as many words. LLVM's `__builtin_ct_select` / `llvm.ct.select` work (RFC August 2025) was still in open pull requests when checked, covers only selection, and explicitly excludes hardware effects; Rust exposure is only "being explored".

### Cited Findings
- `core::hint::black_box` documentation: it is "only (and can only be) provided on a "best-effort" basis"; "it **must not be relied upon to control critical program behavior.** This also means that this function does not offer any guarantees for cryptographic or security purposes."; and "This limitation is not specific to `black_box`; there is no mechanism in the entire Rust language that can provide the guarantees required for constant-time cryptography. (There is also no such mechanism in LLVM, so the same is true for every other LLVM-based compiler.)" [F] — [Rust std docs: black_box](https://doc.rust-lang.org/std/hint/fn.black_box.html)
- `subtle` crate (used across the Rust crypto ecosystem): "This crate represents a "best-effort" attempt", "Because side-channel resistance is not a property of software alone", any such effort "is fundamentally limited"; constant-time execution requires that "the bitwise operations are not recognized as a conditional assignment and optimized back into a branch"; it "tries to hide the value of a `Choice`'s inner `u8` by passing it through a volatile read"; "**USE AT YOUR OWN RISK**". Debug builds: "These invariant checks involve secret-dependent branches, and are not present when compiled in release mode." [F] — [subtle docs](https://docs.rs/subtle/latest/subtle/)
- RustCrypto `cmov` crate: "guaranteed constant-time operation using inline `asm!`" on x86/x86_64 (CMOV) and aarch64 (CSEL), the asm being "a black box that will not be rewritten by e.g. LLVM's architecture-specific lowerings"; elsewhere a "“best effort” portable fallback implementation based on bitwise arithmetic" for which it "cannot guarantee that this implementation generates branch-free code". [F] — [cmov docs](https://docs.rs/cmov/latest/cmov/)
- RustCrypto's position in the LLVM RFC thread (Tony Arcieri): "We are still in a position where we would prefer to replace code using new intrinsics to get constant-time guarantees"; RustCrypto currently uses inline assembly as a workaround; he recalled the earlier proposal to "add 'secret integer types' to Rust". [F] — [LLVM RFC thread](https://discourse.llvm.org/t/rfc-constant-time-coding-support/87781)
- A real rustc/LLVM instance: RUSTSEC-2024-0344 (see section 1) — a masked loop in Rust compiled to a secret-dependent `jns`. [F] — [RUSTSEC-2024-0344](https://rustsec.org/advisories/RUSTSEC-2024-0344.html)
- **LLVM "[RFC] Constant-Time Coding Support"** (Trail of Bits, posted 8 Aug 2025): proposes `__builtin_ct_select(cond, a, b)` backed by `llvm.ct.select`. Stated scope: "This work is scoped to address only branching-related timing attacks."; "This work is not intended to, and in fact cannot, prevent hardware-level security issues like SPECTRE or Rowhammer."; "Our initial implementation does not use ARM DIT or Intel DOIT." Maintainer pushback: "there's no underlying model for what it means to 'use' a value that needs constant-time guarantees" (efriedma-quic), with suggestions that a new IR type (secret types) is the principled design. [F] — [LLVM RFC thread](https://discourse.llvm.org/t/rfc-constant-time-coding-support/87781)
- Status of the implementation: PR #166702 (`llvm.ct.select`) was opened 6 Nov 2025 and shows as **open, not merged** when fetched on 2026-11-21, as do the stacked PRs #166703 (Clang builtin), #166704 (x86) and #166706 (AArch64); mailing-list activity on the stack runs to May 2026 (that last point from search results only). [F]/[S] — [llvm-project PR #166702](https://github.com/llvm/llvm-project/pull/166702); [llvm-branch-commits, May 2026](https://lists.llvm.org/pipermail/llvm-branch-commits/2026-May/093379.html)
- Trail of Bits (2 Dec 2025): the changes are "under review and will be included in a future LLVM release"; claimed property "This intrinsic guarantees that the selection operation above will compile to constant-time machine code, regardless of optimization level."; arithmetic/string operations are future work; "The Rust compiler team is exploring how to expose these intrinsics through its `core::intrinsics` module". [F] — [Trail of Bits blog](https://blog.trailofbits.com/2025/12/02/introducing-constant-time-support-for-llvm-to-protect-cryptographic-code/)
- Rust RFC for secret integer types ("added secret types rfc", rust-lang/rfcs #2859, opened 23 Jan 2020) is **closed**; it proposed `secret_i8`-style types forbidding division and secret indexing, and acknowledged LLVM support would be "required for the secret type guarantees to be fully guaranteed throughout the compilation process." [F] — [rust-lang/rfcs #2859](https://github.com/rust-lang/rfcs/pull/2859)
- Auto-vectorisation: the loop vectoriser is one of the LLVM passes implicated in introducing violations (in combination with select handling), and `-fno-vectorize` is among the proposed mitigation flags. [F] — [Fun with flags](https://arxiv.org/html/2507.06112v1). In the clangover case the branchy code appears at `-O2 -fno-vectorize`/`-O3 -fno-vectorize`, while plain `-O2`/`-O3` binaries contain both a branchy and a vectorised version. [S] — [clangover repo](https://github.com/antoonpurnal/clangover)
- KyberSlash was first noticed by Tamvada, Bhargavan and Kiefer while writing a formally verified Rust implementation of Kyber; the Rust `pqc_kyber` crate has an open advisory (RUSTSEC-2023-0079). [S] — [RUSTSEC-2023-0079](https://rustsec.org/advisories/RUSTSEC-2023-0079); [ePrint 2024/1049](https://eprint.iacr.org/2024/1049)
- Charon consumes rustc MIR and converts it to ULLBC then LLBC (control-flow reconstruction) for Aeneas; LLVM runs after MIR. [S] — [Charon paper, arXiv 2410.18042](https://arxiv.org/html/2410.18042v3)

### Inferences
- A MIR-level theorem sits *before* every transformation that has been shown to break constant-time (InstCombine, SimplifyCFG/loop unswitching, vectorisation, CodeGenPrepare select-to-branch, backend cmov/csel conversion), and before monomorphisation choices, inlining, LTO and intrinsic lowering. Everything from "MIR as Charon saw it" to "bytes in the binary" is in the unverified gap.
- Rust bounds checks and panics are branches on index and length. If the theorem shows all indices and lengths are public, those branches leak nothing; the compiled binary may also delete or hoist them, which is harmless. The claim should say panics/bounds checks are treated as control flow on public data (and that panic *paths* are not otherwise analysed), rather than that the code is "branch-free".
- Build profile matters to the branch set: with overflow checks or debug assertions enabled, arithmetic on secret-derived integers gains secret-dependent panic branches (compare `subtle`'s warning about debug builds). The claim should name the profile(s) it is meant to cover and say whether the extracted MIR included overflow checks.
- The ARMv8 SHA-256 path goes through `core::arch` intrinsics or inline asm that the Lean model can only axiomatise; the claim for that build is "the Rust code around the intrinsics is secret-independent, and the intrinsics are assumed to be data-independent-time instructions" (see section 4).
- Calls that leave the verified crate (`memcpy`/`memset` from the platform libc or compiler-builtins, the allocator, the RNG) are not covered by a MIR-level proof of the crate; their timing depends on lengths and alignment, which should be argued public.
- `black_box`/volatile-read/empty-asm barriers reduce the chance that LLVM re-derives a select, but every project that uses them describes them as mitigations pending language support, not guarantees. A project with no secret-dependent selects has nothing for a barrier to protect, which is a stronger position than relying on barriers.

### Gaps
- I found no Rust RFC, tracking issue or project goal from 2025–2026 for constant-time intrinsics or secret types; searches returned only generic `core::intrinsics` documentation. Absence of evidence only — the rust-lang/rust tracker was not searched directly.
- The closing date and reason for rust-lang/rfcs #2859 were not visible in the fetched page.
- LLVM PR status is from a truncated page fetch; I could not confirm whether any part of the stack merged after May 2026 or which LLVM release (if any) carries it. The Trail of Bits statement of a "guarantee" should therefore be read as the design goal of unmerged work.
- An earlier thread "[RFC] Constant Time Execution Guarantees in LLVM" exists but was not read — [LLVM discourse 86700](https://discourse.llvm.org/t/rfc-constant-time-execution-guarantees-in-llvm/86700).
- Which MIR phase Charon extracts for this project (and so which rustc MIR optimisations are inside or outside the model) was not confirmed from a primary source; check against the project's Charon invocation.

## 3. Compiler-preservation results (CompCert-CT, Jasmin), and whether anything comparable exists for rustc/LLVM

### Takeaway
Machine-checked constant-time *preservation* exists only for (a mildly modified) CompCert and for Jasmin; even Jasmin's own library documents the property as "not machine-checked for the current compiler version", and preservation of *speculative* constant-time was shown to fail in practice before being repaired. I found nothing comparable for rustc or LLVM; the alternative used by projects that need machine-code assurance is to verify or test the binary itself.

### Cited Findings
- **CompCert-CT (Barthe, Blazy, Grégoire, Hutin, Laporte, Pichardie, Trieu; POPL 2020, ePrint 2019/926).** The authors modify CompCert to remove sources of leakage, instrument the semantics of its intermediate languages with leakage, and prove the modified compiler preserves cryptographic constant-time. [F] — [ePrint 2019/926](https://eprint.iacr.org/2019/926); [POPL 2020 listing](https://popl20.sigplan.org/details/POPL-2020-Research-Papers/9/Formal-Verification-of-a-Constant-Time-Preserving-C-Compiler)
- **Jasmin, constant-time preservation (Barthe, Grégoire, Laporte, Priya; ePrint 2021/650).** "One important goal is then to relate leakage of source programs and leakage of their compilation---this can be used, e.g., to prove preservation of CCT... We illustrate our methods on the Jasmin compiler and prove preservation results for two policies of interest: CCT and cost." [V] — [ePrint 2021/650](https://eprint.iacr.org/2021/650)
- **Preservation of Speculative Constant-Time by Compilation (Arranz Olmos, Barthe, Blatter, Grégoire, Laporte; POPL 2025, ePrint 2024/1203).** "Compilers often weaken or even discard software-based countermeasures commonly used to protect programs against side-channel attacks; worse, they may also introduce vulnerabilities that attackers can exploit." "Prior work establishes that (a mildly modified version of) the CompCert and Jasmin formally verified compilers preserve constant-time". "We first show that preservation of speculative constant-time fails in practice by providing examples of secure programs whose compilation is not speculative constant-time using GCC (GCC -O0 and GCC -O1) and Jasmin." They then prove preservation for "a proof-of-concept compiler that distills some of the critical passes of the Jasmin compiler". [V] — [ePrint 2024/1203](https://eprint.iacr.org/2024/1203)
- **Protecting Cryptographic Code Against Spectre-RSB (ASPLOS 2025, ePrint 2024/1070).** "Using the Coq proof assistant, we prove that the type system is sound with respect to the idealized semantics and that the compiler transformation preserves speculative constant-time." [V] — [ePrint 2024/1070](https://eprint.iacr.org/2024/1070)
- Libjade's assurance document states the compilation claims with their status: "The Jasmin compiler preserves the semantics of the source program; the proof is checked in Rocq." and "The compiler preserves constant time: control flow and memory accesses that do not depend on secrets in the source do not depend on secrets in the assembly (not machine-checked for the current compiler version)." [V] — [formosa-libjade docs/assurance.md](https://github.com/formosa-crypto/formosa-libjade/blob/main/docs/assurance.md)
- **Low\*/KreMLin (ICFP 2017).** "At extraction time, specifications and proofs are erased, and the remaining code enjoys a predictable translation to C. We prove that this translation preserves semantics and side-channel resistance." [V] — [arXiv 1703.00053](https://arxiv.org/abs/1703.00053)
- HACL\* paper on where that chain stops: "Note that our toolchain stops with verified C code. We do not consider the problem of compiling C to verified assembly, which is an important but independent challenge. Verified compilers like CompCert can preserve functional correctness and memory safety guarantees from Clight to x86, and enhanced versions of CompCert [9] can ensure that the compiler does not introduce new side-channels. However, for maximal performance, users of HACL\* are likely to rely on mainstream compilers like GCC and CLANG." [V] — [HACL\* (CCS 2017), ePrint 2017/536](https://eprint.iacr.org/2017/536) (text read from the [MIT course mirror](https://css.csail.mit.edu/6.5660/2024/readings/hacl-star.pdf))
- For rustc/LLVM: the Rust documentation states "there is no mechanism in the entire Rust language that can provide the guarantees required for constant-time cryptography. (There is also no such mechanism in LLVM...)". [F] — [Rust std docs: black_box](https://doc.rust-lang.org/std/hint/fn.black_box.html). LLVM maintainers responding to the 2025 RFC note "there's no underlying model for what it means to 'use' a value that needs constant-time guarantees". [F] — [LLVM RFC thread](https://discourse.llvm.org/t/rfc-constant-time-coding-support/87781)
- Verification at the binary instead of preservation: s2n-bignum proves constant-time over machine code ("the sequence of instructions executed and all memory addresses accessed are independent of secret inputs") [V] — [s2n-bignum SOUNDNESS.md](https://github.com/awslabs/s2n-bignum/blob/main/SOUNDNESS.md); mlkem-native's AArch64/x86_64 assembly is "proved functionally correct, memory-safe, and to have secret-independent timing (constant-time)" at the object-code level [F] — [mlkem-native README](https://github.com/pq-code-package/mlkem-native); Binsec/Rel checks compiled binaries [S] — [arXiv 1912.08788](https://arxiv.org/pdf/1912.08788).

### Inferences
- "Has anyone proved that rustc/LLVM preserves constant-time?" — on the evidence gathered, no. The only verified-preservation results are for CompCert (C) and Jasmin; the POPL 2025 abstract's summary of prior work names only those two, the Rust docs deny any such mechanism, and LLVM's own constant-time support is an unmerged, selection-only intrinsic with no formal model. The report should say "we are not aware of any" rather than "none exists".
- The precise analogue of this project in the literature is HACL\*: a proof at source level, a (paper-proved) preservation step to an intermediate form, then an untrusted mainstream compiler. HACL\*'s sentence "our toolchain stops with verified C code" is the model for "our theorem stops at Rust MIR".
- A MIR-level proof plus a binary-level check (disassembly review, Valgrind-style taint test, or statistical timing test on the shipped target) is the combination other projects use to close the compiler gap without a verified compiler.

### Gaps
- I did not read the CompCert-CT paper body; details of which CompCert passes had to be modified, and its leakage model (control flow and memory addresses; whether division operands are included), are not confirmed here.
- No search was made for LLVM-IR-level or binary-level verifiers that support AArch64 Rust output specifically (e.g. whether Binsec/Rel or similar handle AArch64 SHA-extension instructions).

## 4. Hardware: ARM DIT and Intel DOIT — the guarantee, enabling, OS support, and what is excluded (cache/address timing, control flow, Hertzbleed, GoFetch/DMP)

### Takeaway
Data-independent instruction latency is an *opt-in* architectural guarantee: on AArch64 the architecture "makes no statement about the timing properties of any instructions" unless PSTATE.DIT is set, which user space must do itself on both macOS and Linux. DIT/DOIT cover only the latency of a listed set of instructions (the ARMv8 SHA-256 instructions are on Arm's list); they exclude addresses and control flow by design, do not address frequency/power channels, and their effect on the Apple data memory-dependent prefetcher is confirmed only for M3 (not M1/M2).

### Cited Findings
- **Arm PSTATE.DIT definition** (Arm system-register reference, 2024-03 release, read from a mirror): DIT = 0: "The architecture makes no statement about the timing properties of any instructions." DIT = 1: "The architecture requires that: The timing of every load and store instruction is insensitive to the value of the data being loaded or stored. For certain data processing instructions, the instruction takes a time which is independent of: The values of the data supplied in any of its registers. The values of the NZCV flags." "The Operational Information section of a data processing instruction description indicates if that instruction is affected by this bit." Reset: "On a Warm reset, this field resets to 0." [V] — [Arm DIT register description (mirror of Arm XML)](https://df.lth.se/~getz/ARM/SysReg/AArch64-dit.html)
- Same page's note: "The architecture makes no statement about the timing properties when the PSTATE.DIT bit is not set. However, it is likely that many of these instructions have timing that is invariant of the data in many situations." The access pseudocode shows `MSR DIT` is permitted at EL0 (user mode). [V] — [Arm DIT register description (mirror)](https://df.lth.se/~getz/ARM/SysReg/AArch64-dit.html)
- The load/store guarantee is about the *data value*, not the address: "insensitive to the value of the data being loaded or stored". [V] — [Arm DIT register description (mirror)](https://df.lth.se/~getz/ARM/SysReg/AArch64-dit.html)

[S] — [SHA256SU0 (mirror)](https://www.scs.stanford.edu/~zyedidia/arm64/sha256su0_advsimd.html)

- Apple, enabling: `timingsafe_enable_if_supported()` / `timingsafe_restore_if_supported(token)` from `<timingsafe.h>`, available in macOS 15.2, iOS/iPadOS 18.2, tvOS 18.2, watchOS 11.2, visionOS 2.2 and later ("If the timing-safe features aren't supported they are ignored and the function has no effect."); on older systems `msr dit, #1` followed by a speculation barrier ("To ensure that subsequent instruction timing reflects the updated DIT processor state, add a speculation barrier after turning on DIT. - Linux and DOITM: a January 2023 patch to enable DOITM was not merged in that form [S] — [LKML, Jan 2023](https://lkml.iu.edu/hypermail/linux/kernel/2301.3/01400.html). [V, as quoted in a reply] — [LKML, 18 Mar 2026](https://lkml.iu.edu/hypermail/linux/kernel/2603.2/07054.html)
- **GoFetch (USENIX Security 2024; disclosed to Apple 5 Dec 2023).** "GoFetch is a microarchitectural side-channel attack that can extract secret keys" from constant-time implementations via the data memory-dependent prefetcher (DMP), which "activates (and attempts to dereference) data loaded from memory that "looks like" a pointer" and so "explicitly violates a requirement of the constant-time programming paradigm". End-to-end attacks on M1; "m2 and m3 CPUs also exhibit similar exploitable DMP behavior". Targets shown: OpenSSL Diffie-Hellman, Go RSA, CRYSTALS-Kyber and Dilithium. The attacker is co-located on the same machine. [F] — [gofetch.fail](https://gofetch.fail/)
- GoFetch and DIT: "We observe that the DIT bit set on m3 CPUs effectively disables the DMP. This is not the case for the m1 and m2." An April 2024 update notes a chicken bit found by Hector Martin can disable the DMP on M1/M2 but "requires kernel support that is not available in macOS at this time." Intel's DOIT bit "can be used to disable DMP on the Raptor Lake processors." Recommended developer measures: set DIT/DOIT where supported, input blinding, avoid hardware sharing. [F] — [gofetch.fail](https://gofetch.fail/)
- **Hertzbleed (2022; site updated 29 May 2026).** "Hertzbleed is a new family of side-channel attacks: frequency side channels."; "even when implemented correctly as constant time, cryptographic code can still leak via remote timing analysis". "Intel's security advisory states that *all* Intel processors are affected."; AMD lists several families; Arm's documentation says "Arm CPUs may be affected" (not confirmed by the authors); "To our knowledge, Intel and AMD do not plan to deploy any microcode patches to mitigate Hertzbleed."; disabling frequency boost works but is "not a recommended mitigation strategy as it will significantly impact performance." The page does not mention DIT/DOIT as a mitigation. [F] — [hertzbleed.com](https://www.hertzbleed.com/)
- s2n-bignum's summary of the hardware residual after a machine-code constant-time proof: "It does not and cannot guarantee that the hardware executes those instructions in constant time. Microarchitectural effects (variable-latency instructions, Hertzbleed-style frequency scaling) could still leak information. Some hardware provides opt-in guarantees for a listed set of instructions: ARM platforms with the DIT (Data Independent Timing) bit set (Armv8.4-A onwards), and Intel platforms with DOITM ... enabled (Ice Lake onwards; earlier Intel processors are documented as behaving as if DOITM is always enabled). AMD does not currently offer an equivalent mechanism. Even with DIT or DOITM enabled, coverage is limited to a specific set of instructions, and power/frequency-based side channels remain outside scope." [V] — [s2n-bignum SOUNDNESS.md](https://github.com/awslabs/s2n-bignum/blob/main/SOUNDNESS.md)

### Inferences
- The layers compose as follows. The Lean theorem (at IR level) addresses which instructions run and which addresses are touched. DIT addresses how long each listed instruction takes for given operand values. Neither addresses: cache/TLB state caused by *public* addresses (not a leak), prefetchers that react to data *values* (DMP), frequency/power effects, or speculation.
- For the hardware-SHA build the "variable-time operand" part of the theorem bottoms out in an assumption: `SHA256H`, `SHA256H2`, `SHA256SU0`, `SHA256SU1` are data-independent-time *when PSTATE.DIT = 1*; with DIT = 0 the architecture promises nothing (though Arm says it knows of no pre-DIT core with data-dependent timing for these instructions). An honest claim either says the library sets DIT (and where), or says DIT is the caller's responsibility and timing of individual instructions is otherwise assumed.
- On Apple Silicon, "set DIT" has three distinct consequences worth separating in the text: an architectural latency guarantee (all FEAT_DIT cores); the DMP being disabled (reported for M3 only; M1/M2 unaffected by DIT); and whatever Apple additionally hangs off the bit, which is not publicly specified.
- On generic ARMv8.0–8.3 cores there is no DIT bit at all; the claim there can only cite Arm's "not aware of any implementation" statement, which is weaker than an architectural guarantee.
- DOIT is largely irrelevant to an AArch64-only claim, but it shows the pattern: on Linux/x86 user space cannot turn it on, so even an x86 build could not rely on it.
- Whether the DMP can be exploited against a hash-based signer was not addressed by any source found; GoFetch's demonstrated targets are schemes with attacker-influenced algebraic intermediates. The safe wording is "outside the model", not "not applicable".

### Gaps
- The official Arm page for the DIT register did not render through the fetch tool; quotes are from mirrors of Arm's published XML (2024-03 system registers, 2026-03 ISA). The full list of DIT-covered instructions (including which Advanced SIMD instructions an auto-vectorised portable SHA-256 would use) was not extracted — check "About PSTATE.DIT" in the current Arm ARM.
- Whether DIT disables the DMP on M4 or later Apple cores: not confirmed by any source read. The GoFetch page covers M1–M3 only.
- A search summary says the FLOP paper reports DIT disabling the M3 load value predictor per process; the predictors.fail front page does not say this and I did not read the paper — unverified. [FLOP paper](https://predictors.fail/files/FLOP.pdf)
- Apple's page defers to Arm for the instruction list ("including but not limited to those described in" Arm's documentation) and does not state publicly which instructions vary in latency on Apple cores when DIT is off.
- Signal-handler behaviour for PSTATE.DIT on Linux and macOS, and whether macOS preserves DIT across system calls in all cases, were not checked.
- Arm's own response to Hertzbleed was not read directly (only the Hertzbleed site's characterisation).

## 5. Speculative execution: leaks despite constant-time code, "speculative constant-time", and how unprotected projects phrase the gap

### Takeaway
Classical constant-time is defined over sequential execution; Spectre-class attacks leak along mis-speculated paths that such a model never sees, and "speculative constant-time" (SCT) is the strengthened property. Only Jasmin-based code has machine-supported SCT (selective speculative load hardening, plus Spectre-RSB protection); every other project examined states that its model is non-speculative and that Spectre-class leakage is out of scope.

### Cited Findings
- **Cauligi et al., PLDI 2020.** "the advent of micro-architectural attacks makes constant-time as it exists today far less useful. This paper lays foundations for constant-time programming in the presence of speculative and out-of-order execution. We present an operational semantics and a formal definition of constant-time programs in this extended setting. Our semantics eschews formalization of microarchitectural features (that are instead assumed under adversary control)". Tool: Pitchfork. [V] — [arXiv 1910.01755](https://arxiv.org/abs/1910.01755)
- **Barthe et al., IEEE S&P 2021.** "Traditionally, these guarantees are established under a sequential execution semantics. However, this semantics is not aligned with the behavior of modern processors that make use of speculative execution to improve performance. This mismatch, combined with the high-profile Spectre-style attacks that exploit speculative execution, naturally casts doubts on the robustness of high-assurance cryptography guarantees." They build on Jasmin "an end-to-end approach for proving properties of cryptographic software under speculative execution" (ChaCha20, Poly1305). [V] — [ePrint 2020/1104](https://eprint.iacr.org/2020/1104)
- **Spectre-RSB (ASPLOS 2025).** "For software-visible side-channels, it was long believed that "constant-time" programming would be sufficient as a systematic countermeasure. However, this belief was shattered in 2018 by attacks exploiting speculative execution". Overhead of full Spectre protections in Jasmin: "below 2% for most cryptographic primitives and reaches only about 5–7% for the more complex post-quantum key-encapsulation mechanism Kyber." [V] — [ePrint 2024/1070](https://eprint.iacr.org/2024/1070)
- SCT is not automatically preserved by compilers: "preservation of speculative constant-time fails in practice" (examples with GCC -O0/-O1 and Jasmin). [V] — [ePrint 2024/1203](https://eprint.iacr.org/2024/1203)
- Libjade's definitions: "Constant time (CT): no secret input of a function influences the control flow of an execution or the addresses of its memory accesses. Values that the code explicitly declassifies, for example the outcome of a rejection-sampling test, count as public." "Speculative constant time (SCT): CT also holds for executions in which the processor mispredicts conditional branches (Spectre v1). The code establishes SCT with selective speculative load hardening: a misspeculation flag, initialised at the entry of each exported function, masks the values that could leak during misspeculation." Both checks run on Jasmin source with `--doit`: "secret values (for SCT, transient ones too) only reach instructions of Intel's data operand independent timing (DOIT) list." Libjade's single target is x86-64/AVX2; no AArch64. [V] — [formosa-libjade docs/assurance.md](https://github.com/formosa-crypto/formosa-libjade/blob/main/docs/assurance.md); [formosa-libjade README](https://github.com/formosa-crypto/formosa-libjade)
- s2n-bignum: "**Speculative execution** -- the model is non-speculative. Side-channel risks from speculative execution (Spectre-class) are not addressed by the current proofs." (listed under "What the model omits", alongside caches/TLBs, interrupts, virtual memory). [V] — [s2n-bignum SOUNDNESS.md](https://github.com/awslabs/s2n-bignum/blob/main/SOUNDNESS.md)
- mlkem-native: it "targets resistance against timing side-channels only"; "Other attack classes, such as power and electromagnetic side-channels," together with microarchitectural (e.g. speculative execution) and fault-injection attacks, "are currently out of scope." [F] — [mlkem-native README](https://github.com/pq-code-package/mlkem-native)
- LLVM constant-time RFC: "This work is not intended to, and in fact cannot, prevent hardware-level security issues like SPECTRE or Rowhammer." [F] — [LLVM RFC thread](https://discourse.llvm.org/t/rfc-constant-time-coding-support/87781)
- `zeroize`: "there is still potential for microarchitectural attacks" (such as Spectre/Meltdown) to leak zeroized secrets; the crate "makes no guarantees that zeroized values cannot be leaked through such channels." [F] — [zeroize docs](https://docs.rs/zeroize/latest/zeroize/)
- Intel's DOIT guidance likewise says developers handling secrets "may need to consider speculative execution vulnerabilities". [F] — [Intel DOIT guidance](https://www.intel.com/content/www/us/en/developer/articles/technical/software-security-guidance/best-practices/data-operand-independent-timing-isa-guidance.html)
- Apple-specific data-speculation attacks (disclosed May/Sept 2024, published 2025): SLAP exploits the Load Address Predictor ("Apple CPUs starting with the M2/A15 are equipped with a Load Address Predictor (LAP)"); FLOP exploits the Load Value Predictor ("Apple's M3/A17 generation and newer CPUs are equipped with a Load Value Predictor (LVP)"). The demonstrated targets are browser sandboxes, not cryptographic libraries. [F] — [predictors.fail](https://predictors.fail/)

### Inferences
- A MIR-level sequential leakage model says nothing about transient execution. In particular, Rust bounds checks are exactly the Spectre-v1 gadget shape (a conditional branch guarding an indexed load); the theorem's "indices are public" property does not constrain what a mis-predicted bounds check loads transiently.
- The mitigating structural fact for this code — worth stating only as an observation, not a guarantee — is that speculative-leak gadgets need a secret (or attacker-controlled index) to flow into an address or branch on the transient path; code that never uses secrets as indices offers fewer such paths. No tool has checked this for the compiled binary.
- No Rust/LLVM equivalent of Jasmin's selective SLH with proofs was found; LLVM's generic speculative load hardening exists but is not something any examined crypto project relies on for a claim.
- Suggested phrasing pattern, following s2n-bignum: "The model is sequential and non-speculative; Spectre-class leakage is not addressed."

### Gaps
- I did not find a published SCT analysis of any SLH-DSA/SPHINCS+ implementation.
- Whether rustc's or LLVM's speculative-load-hardening options have been evaluated for Rust cryptographic code was not researched.
- Formal SCT definitions were read only at abstract level; the exact adversary directives in Cauligi et al. are not reproduced here.

## 6. Other channels outside any timing model: power/EM, faults, Rowhammer, memory disclosure and zeroisation, allocator behaviour

### Takeaway
Projects scope these out explicitly and briefly, usually in a single sentence or a "what the model omits" list. For SLH-DSA specifically, FIPS 205 itself calls out side-channel and fault attacks and requires destruction of sensitive intermediate data, and fault/Rowhammer attacks on SPHINCS+/SLH-DSA signing are a published, practical concern — so a constant-time theorem should say plainly that it is not a fault-resistance or zeroisation claim.

### Cited Findings
- **FIPS 205 §3.2, "Side-channel and fault attacks":** "For signature schemes, the secrecy of the private key is critical. Care must be taken to protect implementations against attacks, such as side-channel attacks or fault attacks [17, 18, 19, 20, 21]. A cryptographic device may leak critical information with side-channel analysis or attacks that allow internal data or keying material to be extracted without breaking the cryptographic primitives." (References include Castelnovi–Martinelli–Prest "Grafting Trees: A Fault Attack Against the SPHINCS Framework" (2018), Genêt et al. "Practical Fault Injection Attacks on SPHINCS" (2018), Genêt "On Protecting SPHINCS+ Against Fault Attacks" (2023).) [V] — [FIPS 205 (Aug 2024)](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)
- **FIPS 205 §3.1, "Destruction of sensitive data":** "Data used internally by key generation and signing algorithms in intermediate computation steps could be used by an adversary to gain information about the private key and thereby compromise security. ... Therefore, implementations of SLH-DSA shall ensure that any local copies of the inputs and any potentially sensitive intermediate data are destroyed as soon as they are no longer needed." The same paragraph notes verification intermediates can be sensitive in some applications (bearer-token signatures, confidential messages). [V] — [FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)
- **FIPS 205 §9.2:** "The hedged variant is the default and should be used on platforms where side-channel attacks are a concern. ... The deterministic variant is available for platforms where a random bit generator is not available." [V] — [FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)
- Rowhammer against SLH-DSA: "SLasH-DSA: Breaking SLH-DSA Using an Extensible End-To-End Rowhammer Framework" (arXiv, Sept 2025) reports a software-only Rowhammer forgery attack on SLH-DSA in OpenSSL 3.5.1; deterministic signing is the most exposed mode, and the randomised mode also fell in their experiments. [S] — [arXiv 2509.13048](https://arxiv.org/pdf/2509.13048)
- s2n-bignum on faults: "**Hardware faults and errata.** The proofs reason about an idealized machine and do not protect against physical faults (transient bit flips from cosmic rays or voltage fluctuations, deliberate fault injection) or undocumented CPU errata. ... Transient physical faults and deliberate fault injection are entirely out of scope; high-assurance deployments in physically hostile environments would need additional countermeasures at the hardware or protocol level." [V] — [s2n-bignum SOUNDNESS.md](https://github.com/awslabs/s2n-bignum/blob/main/SOUNDNESS.md)
- HACL\* paper on power: "Secret independence is a necessary but not complete mitigation for side-channel attacks. It provably prevents certain classes of timing side-channel leaks that rely on branching and memory accesses, but does not account for other side-channels like power analysis." [V] — [HACL\* paper](https://eprint.iacr.org/2017/536) (text via [mirror](https://css.csail.mit.edu/6.5660/2024/readings/hacl-star.pdf))
- mlkem-native: power and electromagnetic side-channels, microarchitectural and fault-injection attacks "are currently out of scope." [F] — [mlkem-native README](https://github.com/pq-code-package/mlkem-native)
- Libjade on what its game-based model omits: it "ignores several aspects such as the encoding into binary code, potential adversarial access to memory, etc., which means that many practical attacks may circumvent the guarantees provided by the above end-to-end result." [V] — [formosa-libjade docs/assurance.md](https://github.com/formosa-crypto/formosa-libjade/blob/main/docs/assurance.md)
- Zeroisation as a separate claim. libcrux: "At this moment, we do also not give guarantees on the zeroization of secret values on the stack or heap. We are working on best-effort implementations of zeroization." [V] — [libcrux Readme](https://github.com/cryspen/libcrux). Libjade (compiler-inserted): "Every entry point erases the stack it used before it returns, so that no intermediate value of the computation stays in memory after the call. The compiler inserts the erasure (attribute `stackzero` ...: a loop of 256-bit stores, followed by a speculation barrier)." [V] — [formosa-libjade docs/assurance.md](https://github.com/formosa-crypto/formosa-libjade/blob/main/docs/assurance.md)
- `zeroize` crate limits: it "prevent[s] the compiler from eliminating writes using volatile operations" but warns that "stack spilling and other optimizations may leave temporary copies of data from the heap on the stack"; `Vec`/`String` impls "cannot guarantee copies of the data were not previously made by buffer reallocation"; "Clearing registers is a difficult problem that can't easily be solved by something like a crate."; memory protections such as `mlock`/`mprotect` are "explicitly out-of-scope for this crate." [F] — [zeroize docs](https://docs.rs/zeroize/latest/zeroize/)
- Allocation behaviour as part of the constant-time story: s2n-bignum functions "never strip away leading zeros to make numbers shorter, nor do they allocate extra space to make them longer; indeed, they perform no memory allocation or other OS calls at all." [V] — [s2n-bignum README](https://github.com/awslabs/s2n-bignum). The `fips205` crate states it is `#![no_std]` with "no heap allocations". [F] — [fips205 README](https://github.com/integritychain/fips205)
- Power/thermal/frequency are excluded even by the hardware vendors' data-independent-timing modes (Intel: inclusion on the DOIT list "does not mean that its usage is resistant to power, thermal, or frequency-based side channels"). [F] — [Intel DOIT guidance](https://www.intel.com/content/www/us/en/developer/articles/technical/software-security-guidance/best-practices/data-operand-independent-timing-isa-guidance.html)
- AWS-LC's WebAssembly caveat shows the platform-dependence of any side-channel claim: "**No side-channel protections**: Timing and cache-based side-channel mitigations that exist for native builds may not apply in the WASM environment". [V] — [AWS-LC README](https://github.com/aws/aws-lc)

### Inferences
- The usual scoping pattern is a short enumerated list: (i) power/EM, (ii) fault injection including Rowhammer, (iii) speculative/microarchitectural effects, (iv) memory disclosure and zeroisation, (v) the caller/OS/RNG. Each is named so the reader does not infer coverage from silence.
- For SLH-DSA the fault item deserves more than boilerplate: a single faulted signature can enable forgery in the SPHINCS framework (FIPS 205's own references), and a constant-time proof is orthogonal to that. Saying whether the implementation defaults to hedged signing (FIPS 205 §9.2) is relevant context but is not a fault countermeasure claim.
- Zeroisation is not implied by constant-time: a secret-independent trace can still leave key material in stack frames, registers and reallocated buffers. Rust moves and compiler spills make source-level zeroisation claims weak (per `zeroize`), so the theorem text should say explicitly "no claim about erasure of secrets" unless a separate argument exists; FIPS 205 §3.1 makes erasure a *requirement* of conformance, so silence could be misread.
- Heap allocation with public sizes: no source found discusses this directly. The reasoning that it is acceptable is that allocator timing and placement depend on request sizes and allocator state, not on buffer contents; the residual concerns are (a) the allocator is outside the verified model, and (b) freed or reallocated buffers may retain secret copies (the `zeroize` reallocation caveat). State both as assumptions.

### Gaps
- No primary source found that analyses allocator timing as a side channel for crypto code with public-size allocations; the statement above is reasoning, not citation.
- The SLasH-DSA paper was not read beyond the search summary; details (which parameter sets, number of faults, hedged-mode success rate) are unverified.
- Core dumps, swap and hibernation images as disclosure channels were not researched; projects examined do not mention them (only `zeroize` mentions `mlock`-style protections as out of scope).

## 7. Wording: how verified-cryptography projects phrase constant-time claims and caveats, and who checks the binary

### Takeaway
The honest claims share one shape: name the *property* (secret-independent control flow and memory addresses, sometimes plus operand classes), name the *artifact* it was established on (source, IR, or machine code), then list what is assumed (compiler, CPU) and what is out of scope. Projects that stop at source level say so in a sentence (HACL\*: "our toolchain stops with verified C code"; libcrux: "Executables ... are *not* verified to be side-channel resistant"; `fips205`: "The claim is at the source level"); projects that want more either prove the machine code (s2n-bignum, mlkem-native assembly, Vale) or test the binary (Valgrind-based taint checking, dudect), and call the tests "evidence, not proof".

### Cited Findings

**HACL\* / EverCrypt / Vale**
- README: verified "for memory safety, functional correctness, and secret independence (resistance to some types of timing side-channels)." ValeCrypt: "proves that its implementations are memory safe, functionally correct, and that timing and memory accesses are secret independent." [V] — [hacl-star README](https://github.com/hacl-star/hacl-star)
- Overview page definition: secret independence means the observations — "the time it takes to execute or the memory addresses that it accesses" — "are independent of the secrets manipulated by the library". The page does not state at which level (F\*, C, binary) this holds. [F] — [HACL\* overview](https://hacl-star.github.io/Overview.html)
- Paper, discipline and its limits: "The best current practice in cryptographic libraries is to require a coding discipline that treats secret values as opaque; code cannot compare or branch on secrets or access memory at secret indices. This discipline is called secret independence (or constant-time coding), and while it does not prevent all side-channel attacks, it has been shown to prevent certain classes of timing leaks". [V] — [HACL\* paper](https://eprint.iacr.org/2017/536) (via [mirror](https://css.csail.mit.edu/6.5660/2024/readings/hacl-star.pdf))
- Paper, the theorem informally: "if a well-typed cryptographic implementation has an input containing a secure integer, then even an attacker who can observe low-level event traces that contain the results of all branches (left or right) and the addresses of all memory accesses cannot distinguish between two runs of the program that use different values for the secure integer input." [V] — same source.
- Paper, model limits: "Furthermore, our current model only protects secrets at the level of machine integers; we treat the lengths and indexes of buffers as public values, which means that we cannot verify implementations that rely on constant-time table access (e.g. sbox-based AES) or length-hiding constructions". [V] — same source.
- Paper, compiler gap: "the translation also preserves event traces, which means our secret independence properties carry all the way down to C. Note that our toolchain stops with verified C code. We do not consider the problem of compiling C to verified assembly ... users of HACL\* are likely to rely on mainstream compilers like GCC and CLANG." [V] — same source.
- Outcome: Breaking Bad later found an HACL\* mask-select compiled to secret-dependent code by some LLVM versions/targets. [F] — [arXiv 2410.13489v2](https://arxiv.org/html/2410.13489v2)

**libcrux (Cryspen)**
- "## Side-Channel Resistance and Zeroization — Executables compiled from the code in this repository are *not* verified to be side-channel resistant, although we try to enforce that the source code is secret-independent (also sometimes called “constant-time”)." and "At this moment, we do also not give guarantees on the zeroization of secret values on the stack or heap. We are working on best-effort implementations of zeroization." [V] — [libcrux Readme](https://github.com/cryspen/libcrux)
- Verification badges distinguish HACL\*-derived code ("verified for memory safety, functional correctness against a high-level spec, and secret independence") from hax-verified Rust ("verified to be panic free and functionally correct against a mathematical spec") — i.e. secret independence is not among the properties claimed as *verified* for the hax-verified Rust. [V] — [libcrux Readme](https://github.com/cryspen/libcrux)
- The `libcrux-secrets` crate provides classify/declassify wrappers and a `check-secret-independence` feature for checking code against the discipline at the type level. [S] — [libcrux-secrets docs](https://docs.rs/libcrux-secrets/=0.0.5)

**Jasmin / Libjade (formosa-crypto; old `libjade` repo archived 10 Nov 2026, continued in `formosa-libjade`)**
- CT/SCT definitions, `jasmin-ct` on Jasmin source with `--doit`, and the compilation statement "(not machine-checked for the current compiler version)" — see sections 3 and 5. [V] — [docs/assurance.md](https://github.com/formosa-crypto/formosa-libjade/blob/main/docs/assurance.md)
- README wording: the `sct` profile is "optimised for speed and protected against timing side channels, with CT and SCT countermeasures"; "`kat`, `memcheck`, `ct` and `sct` are checks ... `safety` and `correctness` are proofs". [V] — [formosa-libjade README](https://github.com/formosa-crypto/formosa-libjade)
- Trusted-base entry for the leakage model: "the CT and SCT checks performed by `jasmin-ct` are trusted to guarantee that the abstract leakage generated by a Jasmin program is independent from secrets; the leakage model itself is not assumed to be a faithful model of reality, but good enough to guarantee that the best practices in protection against timing attacks are correctly deployed." Also in the TCB: parts of the compiler outside the Rocq proof, the assembler and linker, the C headers, and "the x86-64 semantics of the Jasmin model, with respect to the processor". [V] — [docs/assurance.md](https://github.com/formosa-crypto/formosa-libjade/blob/main/docs/assurance.md)
- Overall hedge: "many practical attacks may circumvent the guarantees provided by the above end-to-end result." [V] — same source.

**Fiat Cryptography**
- The README makes no explicit constant-time or side-channel claim; its only compiler caveat concerns integer-size casts, and "We do not provide any quality guarantees for code generated by the backends." [F] — [fiat-crypto README](https://github.com/mit-plv/fiat-crypto)
- The generated C nevertheless carries a compiler workaround for the select idiom: `fiat_p256_value_barrier_u64` (an empty inline-asm barrier, compiled out under `FIAT_P256_NO_ASM` or non-GNU compilers) applied to the mask inside `fiat_p256_cmovznz_u64`. [V] — [fiat-c/src/p256_64.c](https://github.com/mit-plv/fiat-crypto/blob/master/fiat-c/src/p256_64.c)

**BoringSSL**
- Barrier comment: "value_barrier_w returns `a`, but prevents GCC and Clang from reasoning about the returned value. This is used to mitigate compilers undoing constant-time code, until we can express our requirements directly in the language." [V] — [crypto/internal.h](https://github.com/google/boringssl/blob/main/crypto/internal.h)
- Binary-level validation: with `BORINGSSL_CONSTANT_TIME_VALIDATION`, `CONSTTIME_SECRET` marks memory undefined for Valgrind so that "If secret data is used as a condition for a branch, or as a memory index, it will trigger warnings in valgrind."; `CONSTTIME_DECLASSIFY` marks data public. Stated purpose and limit: "Valgrind-based constant-time validation is partly to check the compiler has not undone any constant-time work. Any place `BORINGSSL_CONSTANT_TIME_VALIDATION` influences optimizations, this validation is inaccurate." [V] — [crypto/internal.h](https://github.com/google/boringssl/blob/main/crypto/internal.h)

**AWS-LC and its verification repo**
- aws-lc-verification states what is proved as functional correctness ("have the correct behavior as defined by a formal specification") for "a subset of algorithms ... only for certain platforms", on "code that is produced by Clang" with named versions; it makes **no** constant-time or side-channel claim. Its caveat list (NoInline, OptNone, InputLength, ToolGap: "It is assumed that a proof of correctness in one tool implies correct behavior as determined by another tool", etc.) is a model for enumerating assumptions. The only timing-related remark is that `value_barrier_w` "primarily exists to prevent Clang from applying certain optimizations" that "would adversely affect constant-time code." [F] — [aws-lc-verification README](https://github.com/awslabs/aws-lc-verification)
- AWS-LC's README lists Valgrind among its CI checks and points to s2n-bignum for formally verified assembly. [V] — [AWS-LC README](https://github.com/aws/aws-lc)

**s2n-bignum (AWS)**
- Definition (README): "By "constant-time" we mean roughly that a given bignum operation takes a time that is independent of the actual numbers involved, depending only on their *nominal* sizes." and "the actual sequence of machine instructions executed, including the specific addresses and sequencing of memory loads and stores, is *independent of the numbers themselves*". [V] — [s2n-bignum README](https://github.com/awslabs/s2n-bignum)
- README's two failure modes: either the discipline "is not followed at all points as intended. We consider this very unlikely, but in contrast to functional correctness it is not actually rigorously machine-checked at present", or "Some individual machine instructions that are used take a time that depends on their data. We have specifically avoided certain machine instructions known to be problematic in this respect (e.g. division instructions), but we have no absolute guarantees from the hardware makers that there are no such variations in the instructions we use, except on ARM platforms where the "DIT" = "data-independent timing" bit is set." [V] — [s2n-bignum README](https://github.com/awslabs/s2n-bignum)
- SOUNDNESS.md (newer, and in tension with the README sentence above): "Since late 2025, s2n-bignum has included formal HOL Light proofs of the constant-time property alongside functional correctness. The formal model introduces *microarchitectural events* that flag uses of instructions with potentially data-dependent timing (e.g., integer division). The safety proof then establishes that (a) the sequence of instructions executed and all memory addresses accessed are independent of secret inputs, and (b) no variable-timing microarchitectural events occur." Coverage: "All s2n-bignum functions currently used by AWS-LC ... on both ARM and x86". [V] — [SOUNDNESS.md](https://github.com/awslabs/s2n-bignum/blob/main/SOUNDNESS.md)
- Residual-risk wording: "The formal proof establishes that the *instruction sequence and memory access pattern* are secret-independent. It does not and cannot guarantee that the hardware executes those instructions in constant time." Risk table row: "B3 | Model omissions (caches, speculative execution, etc.) | Standard for sequential user-mode verification; omissions documented". One function is exempt and "telegraphed in its name `mlkem_rej_uniform_VARIABLE_TIME`". [V] — [SOUNDNESS.md](https://github.com/awslabs/s2n-bignum/blob/main/SOUNDNESS.md)
- Empirical complement: benchmark "var"/"corr" statistics that "attempt to give some empirical results on the variation in runtime with respect to the data being manipulated." [V] — [s2n-bignum README](https://github.com/awslabs/s2n-bignum)

**mlkem-native (pq-code-package; consumed by AWS-LC)**
- Assembly is "proved functionally correct, memory-safe, and to have secret-independent timing (constant-time)" in HOL Light at object-code level ("free of secret-dependent control flow, memory access patterns, and variable-latency instructions"); the C code is CBMC-proved "memory-safe (no memory overflow) and type-safe (no integer overflow)" with no constant-time proof; "C code is hardened against compiler-introduced timing side channels" via barriers and patterns (citing KyberSlash and clangover); absence of secret-dependent branches, memory access and variable-latency instructions "is also tested using `valgrind` with various combinations of compilers and compilation options."; assumption stated: "The C code assumes constant-time 32x32->32 and 32x32->64 multiplication, which some targets do not provide"; "Formal Verification is never absolute." [F] — [mlkem-native README](https://github.com/pq-code-package/mlkem-native)

**RustCrypto and the Rust ecosystem**
- `slh-dsa` crate README's only security text: "The implementation contained in this crate has never been independently audited! USE AT YOUR OWN RISK!" — no constant-time claim either way. [F] — [RustCrypto slh-dsa](https://github.com/RustCrypto/signatures/tree/master/slh-dsa)
- `subtle` ("best-effort", "side-channel resistance is not a property of software alone"), `cmov` (guarantee only where inline asm is used; "cannot guarantee" for the portable fallback), and the std `black_box` disclaimer — see section 2. [F] — [subtle](https://docs.rs/subtle/latest/subtle/); [cmov](https://docs.rs/cmov/latest/cmov/); [black_box](https://doc.rust-lang.org/std/hint/fn.black_box.html)

**`fips205` crate (integritychain), README as of 2026-11-21 (crate 0.5.x, MSRV 1.85)**
- Intro: "Key generation and signing are constant-time: every branch, loop bound and memory index depends only on public data, and each signature makes the same number of hash calls for its parameter set, whatever the key, message or randomness." [V] — [fips205 README](https://github.com/integritychain/fips205)
- Notes bullet, in full: "Constant-time: key generation and signing never branch, loop or index memory on secret data (`SK.seed`, `SK.prf`, `opt_rand`, and the FORS and WOTS+ secret values derived from them). Control flow and memory access follow only public data: the parameter set, the message and context lengths, the `hedged` flag, and the message digest, tree indices and WOTS+ digits that the signature reveals. For each parameter set, key generation and signing always make the same number of calls to each hash function; only hashing the message and context takes longer as they grow. Checked by source review, by counting hash calls in all twelve parameter sets, and by the [`dudect`] measurements. The claim is at the source level: the compiler and CPU are trusted not to add secret-dependent timing, and the caller's RNG is outside it. Verify uses only public data and makes no constant-time claim." [V] — [fips205 README](https://github.com/integritychain/fips205)
- Its dudect README: two classes with different fixed seeds/randomness; "Results depend on the machine and configuration; they are evidence, not proof."; quotes dudect's own caveat that "t-values less than 5 does not necessarily imply that the function is constant-time, since there may be other input distributions under which the function behaves significantly differently."; recorded run dated 14 Oct 2026 on an Intel i7-13700K (x86-64), Rust 1.98.1, fips205 v0.5.0, max t = +2.29. No AArch64 run is recorded there. [V] — [fips205 dudect README](https://github.com/integritychain/fips205/blob/main/dudect/README.md)

**Who checks the binary, and what is recommended**
- Proof on machine code or assembly (no compiler in between): s2n-bignum (HOL Light over machine code, ARM and x86) [V] — [SOUNDNESS.md](https://github.com/awslabs/s2n-bignum/blob/main/SOUNDNESS.md); mlkem-native assembly (object-code level) [F] — [README](https://github.com/pq-code-package/mlkem-native); Vale assembly-language code in HACL\*/EverCrypt [V] — [hacl-star README](https://github.com/hacl-star/hacl-star).
- Valgrind/ctgrind-style taint testing of compiled code: BoringSSL [V] — [internal.h](https://github.com/google/boringssl/blob/main/crypto/internal.h); mlkem-native, across compilers and options, including variable-latency instructions [F] — [README](https://github.com/pq-code-package/mlkem-native); KyberSlash authors' patched Valgrind for variable-time instructions [V] — [ePrint 2024/1049](https://eprint.iacr.org/2024/1049).
- Statistical timing tests on the binary: `fips205` (dudect) [V] — [dudect README](https://github.com/integritychain/fips205/blob/main/dudect/README.md); s2n-bignum's var/corr benchmark [V] — [README](https://github.com/awslabs/s2n-bignum).
- Symbolic binary analysis: Binsec/Rel [S] — [arXiv 1912.08788](https://arxiv.org/pdf/1912.08788); DATA (found the dalek issue) [F] — [RUSTSEC-2024-0344](https://rustsec.org/advisories/RUSTSEC-2024-0344.html).
- Source/IR-level only, with the gap disclosed: HACL\* (Low\*→C), libcrux, Libjade (Jasmin source check + compiler preservation claim), `fips205` (source review) — sources as above.
- Recommendations: continuous testing across architectures/compilers and publishing the tested configurations; formal analysis of the binary or a verified compiler [F] — [Breaking Bad](https://arxiv.org/html/2410.13489v2). Pass-disabling flags as a partial measure that "does not guarantee completeness" [F] — [Fun with flags](https://arxiv.org/html/2507.06112v1).

### Inferences
- Common anatomy of a careful claim, in the order projects use: (1) property in observable terms ("control flow and addresses of memory accesses do not depend on secrets"); (2) what counts as secret and what is public/declassified (Libjade: "Values that the code explicitly declassifies ... count as public"; `fips205` lists the signature-revealed digits and indices); (3) the artifact and tool (F\* source, Jasmin source via `jasmin-ct`, machine code in HOL Light); (4) preservation status to the binary (proved / claimed but "not machine-checked for the current compiler version" / "toolchain stops with verified C code" / "compiler and CPU are trusted"); (5) hardware assumption (DIT/DOIT or "no absolute guarantees from the hardware makers"); (6) explicit out-of-scope list (speculation, power/EM, faults, zeroisation); (7) empirical evidence labelled as such ("evidence, not proof").
- Words that the careful projects avoid for a source/IR-level result: unqualified "constant-time implementation", "side-channel free", "timing-safe binary". Words they use: "secret independence", "at the source level", "resistance to some types of timing side-channels", "written in a constant-time style", "not verified to be side-channel resistant".
- The `fips205` sentence "The claim is at the source level: the compiler and CPU are trusted not to add secret-dependent timing, and the caller's RNG is outside it" is the closest existing wording to this project's situation; a machine-checked version can keep its structure and replace "checked by source review" with the theorem statement, while keeping the trust sentence unchanged because the theorem does not narrow that gap.
- Suggested skeleton for the section (synthesis; adapt names and facts to the actual development):
  - *What is proved.* "For the Lean model that Aeneas produces from Charon's extraction of this crate's MIR (rustc version, features, profile stated), key generation and signing for SLH-DSA-SHA2-128s satisfy: every branch condition, loop bound, slice index and length, and every operand of an operation the model treats as variable-time, is a function of public inputs only. Public inputs are: [parameter set, message and context lengths, hedged flag, and the values the signature reveals]. Secrets are: [SK.seed, SK.prf, opt_rand, derived FORS/WOTS+ values]. Panics and bounds checks are modelled as control flow and shown to depend only on public data. Verification handles only public data and carries no claim."
  - *What is assumed, not proved.* "(a) Charon and Aeneas faithfully represent the MIR. (b) rustc and LLVM do not introduce secret-dependent branches, addresses or variable-time instructions when compiling that MIR; no compiler-preservation result is known for rustc/LLVM, and compilers are documented to break source-level constant-time code that uses secret-dependent selects — this code has none, which removes the known trigger but is not a proof. (c) For the hardware-SHA build, the ARMv8 SHA-256 instructions are modelled axiomatically; Arm lists them as data-independent-time instructions when PSTATE.DIT is set. (d) Instruction latency is data-independent: guaranteed by the architecture only with PSTATE.DIT = 1, which [this library sets / the caller must set — e.g. `timingsafe_enable_if_supported` on macOS 15.2+, `msr dit` on Linux when HWCAP_DIT is present]. (e) libc/compiler-builtins routines, the allocator and the RNG are outside the model."
  - *What is out of scope.* "Speculative execution (the model is sequential), data-dependent prefetchers (on Apple M1/M2 DIT does not disable the DMP), frequency/power/EM channels, fault injection and Rowhammer, erasure of secrets from memory and registers, and anything the caller does with keys."
  - *Additional evidence, if any.* "Binary-level checks performed: [disassembly review of the compression function / Valgrind taint test on aarch64-linux / dudect on Apple Silicon], on [toolchain, flags, targets]; these are evidence, not proof."
- Publishing the exact toolchain, target triples, opt-level and feature flags that were inspected follows Breaking Bad's recommendation and makes the "compiler is trusted" sentence checkable by others.
