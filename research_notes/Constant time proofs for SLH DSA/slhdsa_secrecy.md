# Secrecy policy for SLH-DSA (FIPS 205): what is secret, what is public, and what the side-channel literature says

Research date: 2026-11-21. Parameter set of interest: SLH-DSA-SHA2-128s (n = 16, h = 63, d = 7, hence h' = 9, log t = a = 12, k = 14, w = 16, public key 32 bytes, secret key 64 bytes, signature 7,856 bytes — [sphincsplus README parameter table](https://github.com/sphincs/sphincsplus/blob/master/README.md)), pure signing, deterministic and hedged.

Method note. FIPS 205, the SPHINCS+ v3.1 submission, NIST IR 8413-upd1, SP 800-208, RFC 8391, RFC 8554, three papers and the implementation source files were downloaded and searched locally, so quotations from them are verbatim (PDF text extraction; mathematical symbols normalised to ASCII). Items marked "(via page summary)" were read through a summarising fetch tool and the wording should be re-checked before being quoted in a paper. ePrint PDFs returned HTTP 403 to direct download; only their abstract pages were read.

## 1. Which values are secret and which are public in FIPS 205 key generation and signing?

### Takeaway
The only long-term secrets are SK.seed and SK.prf; everything derived from SK.seed through PRF (WOTS+ chain starts, FORS secret leaf values) and every WOTS+ chain value *below* the revealed position is secret, as is `addrnd`/`opt_rand` in hedged mode by the convention of the one production implementation that annotates it. PK.seed, PK.root, M, ctx, R, the H_msg digest (md, idx_tree, idx_leaf), all ADRS values, every Merkle-tree node, FORS leaf values F(sk), FORS roots and the FORS public key, WOTS+ chain ends and public keys, every XMSS root, and therefore the WOTS+ digits at every layer are public: each is in the signature, computable by the verifier from (PK, M, SIG), or an internal Merkle node whose disclosure gives no advantage.

### Cited Findings

**Private key contents (FIPS 205, published and effective August 13, 2024).**
- "An SLH-DSA private key (Figure 15) consists of an n-byte seed SK.seed that is used to pseudorandomly generate all of the secret values for the WOTS+ and FORS keys and an n-byte key SK.prf that is used in the generation of the randomized hash of the message. An SLH-DSA private key also includes copies of PK.root and PK.seed, as these values are needed during both signature generation and signature verification." (Section 3) — [FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)
- "The SLH-DSA private key contains two random, secret n-byte values (see Figure 15). SK.seed is used to generate all of the WOTS+ and FORS private key elements. SK.prf is used to generate a randomization value for the randomized hashing of the message in SLH-DSA. The private key also includes a copy of the public key." (Section 9.1) — [FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)
- "The SLH-DSA private key contains a secret seed value and a secret PRF key. The public key consists of a key identifier PK.seed and the root of the hypertree." (Section 9) — [FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)

**Public key and PK.seed.**
- "An SLH-DSA public key (Figure 16) contains two n-byte components: (1) PK.root, which is the public key of the XMSS key at layer d − 1, and (2) PK.seed, which is used to provide domain separation between different SLH-DSA key pairs." (Section 3). Section 9.1 calls PK.seed "an n-byte public seed". — [FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)
- Algorithm signatures in the standard label the inputs: "Input: Secret seed SK.seed, public seed PK.seed, address ADRS." (e.g. Algorithms 6, 7, 9, 10, 14, 15, 16). — [FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)
- "An ADRS consists of public values that indicate the position of the value being computed by the function. ... In the case of PRF, this is used to generate a large number of different secret values from a single seed." (Section 4.2) — [FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)

**WOTS+ secrets and public values.**
- "A WOTS+ private key consists of len secret values of length n. In SLH-DSA, these are all generated from an n-byte seed SK.seed using a PRF. Chains of length w are then created from the secret values using a chaining function, and the end values from each of the chains are public values. The WOTS+ public key is computed as the hash of these public values. ... The signature consists of the appropriate entries from the chains for each of the integers in the message and checksum arrays." (Section 5) — [FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)
- Algorithm 7 (wots_sign): line 13 "sk ← PRF(PK.seed, SK.seed, skADRS) ▷ compute chain i secret value"; line 15 "sig[i] ← chain(sk, 0, msg[i], PK.seed, ADRS) ▷ compute chain i signature value". The number of chain steps is the message digit msg[i]. — [FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)

**FORS secrets and public values.**
- "A FORS private key consists of k sets of t n-byte strings, all of which are pseudorandomly generated from the seed SK.seed. Each of the k sets is formed into a Merkle tree, and the roots of the trees are hashed together to form the FORS public key. A signature on a k·a-bit message digest consists of k elements from the private key, one from each set selected using a bits of the message digest, along with the authentication paths for each of these elements." (Section 8) — [FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)
- "The fors_sign function splits k·a bits of md into k a-bit strings (line 2), each of which is interpreted as an integer between 0 and t − 1. Each of these integers is used to select a secret value from one of the k sets (line 4)." (Section 8.3) — [FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)

**Signing flow: R, digest, indices (Algorithm 19, slh_sign_internal).**
- Line 2: "opt_rand ← addrnd ▷ substitute opt_rand ← PK.seed for the deterministic variant"; line 3: "R ← PRF_msg(SK.prf, opt_rand, M) ▷ generate randomizer"; line 4: "SIG ← R"; line 5: "digest ← H_msg(R, PK.seed, PK.root, M) ▷ compute message digest"; lines 6–10 split the digest into md, idx_tree, idx_leaf; line 14 FORS-signs md; line 16 "PK_FORS ← fors_pkFromSig(SIG_FORS, md, PK.seed, ADRS) ▷ get FORS key"; line 17 "SIG_HT ← ht_sign(PK_FORS, SK.seed, PK.seed, idx_tree, idx_leaf)". — [FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)
- R is the first n bytes of the signature (line 4), so R is published; H_msg has only public inputs (R, PK.seed, PK.root, M), so the digest, md, idx_tree and idx_leaf are recomputed by every verifier (Algorithm 20: "begins by computing a message digest (line 8) and then extracting md (line 9), idx_tree (lines 10 and 12), and idx_leaf (lines 11 and 13) from the digest"). — [FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)
- Algorithm 12 (ht_sign) signs PK_FORS with the layer-0 XMSS key, then computes "root ← xmss_pkFromSig(idx_leaf, SIG_tmp, M, PK.seed, ADRS)" and signs that root at the next layer, for j = 1 .. d−1. Each layer's WOTS+ message is therefore PK_FORS or an XMSS root, both of which the verifier recomputes from the signature. — [FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)
- For SLH-DSA-SHA2-128s (Section 11.2.1): H_msg = MGF1-SHA-256(R ∥ PK.seed ∥ SHA-256(R ∥ PK.seed ∥ PK.root ∥ M), m); PRF = Trunc_n(SHA-256(PK.seed ∥ toByte(0, 64 − n) ∥ ADRS^c ∥ SK.seed)); PRF_msg = Trunc_n(HMAC-SHA-256(SK.prf, opt_rand ∥ M)); F, H, T_l = Trunc_n(SHA-256(PK.seed ∥ toByte(0, 64 − n) ∥ ADRS^c ∥ M_i)). — [FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)

**SPHINCS+ submission (v3.1, June 10, 2022).**
- "The SPHINCS+ private key contains two elements. First, the n-byte secret seed SK.seed which is used to generate all the WOTS+ and FORS private key elements. Second, an n-byte PRF key SK.prf which is used to deterministically generate a randomization value for the randomized message hash. The SPHINCS+ public key also contains two elements. First, the HT public key, i.e. the root of the tree on the top layer. Second, an n-byte public seed value PK.seed which is sampled uniformly at random." (Section 6.2) — [SPHINCS+ v3.1 specification](https://sphincs.org/data/sphincs+-r3.1-specification.pdf)
- "secret data is only processed by symmetric cryptographic primitives" (Section 9.4, full passage quoted in question 2). — [SPHINCS+ v3.1 specification](https://sphincs.org/data/sphincs+-r3.1-specification.pdf)

**The most explicit published secret/non-secret classification: "Side Channel Resistant Sphincs+" (NIST 5th PQC Standardization Conference paper, dated January 25, 2024; anonymous in the conference PDF, presented on CSRC under Scott Fluhrer's name; also circulated as ePrint 2024/500, which I could not download).** Section 3, "The secrets within Sphincs+", walks through signing step by step:
- PRF_msg: "While the result of this hash is public (the value R is included in the signature), the value SK.prf needs to remain secret."
- H_msg: "The message is again hashed (Hmsg), along the above hash R, and other public data to select the FORS leaves, the bottom most Merkle tree, and the bottom most Merkle leaf within that tree. No secrets are involved here."
- "The PRF function is used to convert the SK.seed value into the selected FORS secret values. The SK.seed value and the FORS secret values are secret."
- "The F function is used to convert the FORS leaf secret value into FORS leaf values. The FORS secret values are secret; the FORS leaf values are not."
- "The FORS leaf values are used to generate a Merkle tree using the forsnode function, and then combined into a single value using the T function. No secrets are involved here."
- "The PRF function is used again to convert the SK.seed value into WOTS initial values. The SK.seed and the WOTS initial values are secret."
- "The F function is used to advance from the WOTS initial value to the final chain top. These values are secret (some are exposed, but we won't know which ones will be, except that the final value is always exposed)."
- "These chain top values are combined with the T function into a single value. No secrets are involved here. Note that, even though the intermediate chain values are marked as 'potentially secret', the top value never is."
- "These values are used to generate a Merkle tree with the H function. No secrets are involved here."
- "All values listed as 'not secret' are values that, if the adversary learns them, does not give him an advantage. These are either values that are also computed by the verifier (and so the adversary has them), or internal nodes within a Merkle tree."
- "Summarizing this list, the secrets that we need to protect are: The secret input to the PRFmsg function. The inputs and outputs to the PRF function. The inputs and (sometimes) outputs to the F function. For everything else, we can use a straight-forward (unprotected) implementation."
- Footnote 4: "The key generation process consists of a subset of these steps, so that is not listed separately."
— all from [Side Channel Resistant Sphincs+ (NIST PQC conference 2024)](https://csrc.nist.gov/csrc/media/Events/2024/fifth-pqc-standardization-conference/documents/papers/side-channel-resistant-sphincs-plus.pdf)

**Same classification for the XMSS/WOTS+ building blocks (Kannwischer, master's thesis, TU Darmstadt, September 18, 2017, the basis of the COSADE 2018 paper).**
- "the only secret data that is processed inside W-OTS+ are the secret key parts x_i. The used randomization elements r and the keys k are public values ... not all intermediate values of the hash chains are secret values, since some of them are part of the generated signature (c^{b_i}_k(x_i, r)) or can be computed from them (c^α_k(x_i, r), α > b_i). Thus, all intermediate values c^α_k(x_i, r) for α < b_i are secret. Since the b_i's are not known before the actual message is signed, all intermediate values have to be considered secret." (Section 4.3.1) — [Kannwischer thesis](https://download.hrz.tu-darmstadt.de/pub/FB20/Dekanat/Publikationen/CDC/Matthias_Kannwischer.master.pdf)
- "The entire XMSS tree is public and, thus, leakage agnostic, i.e., even if it is leaked entirely, the adversary does not learn anything secret. This includes the W-OTS+ public keys and the intermediate values in the L-trees ... the intermediate values in the W-OTS+ hash chains need to be considered secret if they are below the parts contained in the W-OTS+ signature. If W-OTS+ has not yet been used to sign a message, all intermediate values need to be considered secret." (Section 4.3.2) — [Kannwischer thesis](https://download.hrz.tu-darmstadt.de/pub/FB20/Dekanat/Publikationen/CDC/Matthias_Kannwischer.master.pdf)

**SK.prf and opt_rand/addrnd.**
- FIPS 205 Section 9.2: "For the 'hedged' variant, addrnd is provided as an input, and opt_rand is set to addrnd. The hedged variant is the default and should be used on platforms where side-channel attacks are a concern. When using the hedged version, addrnd shall be an n-byte random value. While addrnd should ideally be generated by an approved random bit generator, other methods for generating fresh random values may be used. For the deterministic variant, addrnd is not provided as an input, and opt_rand is set to PK.seed, which results in signing being deterministic". The standard does not state that addrnd must be kept secret. — [FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)
- FIPS 205 Section 10.2: "If the default hedged variant of slh_sign_internal is used, the n-byte random value addrnd shall be generated by the cryptographic module that runs slh_sign_internal." — [FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)
- Why SK.prf matters: "If that value is known and either the randomness value is predictable or omitted, then system becomes vulnerable to several chosen message attacks which are easier than the targeted security level"; conversely with unpredictable opt_rand "the attacker may be able to recover the SK.prf value, but that does not give him any advantage; he still cannot conduct either attack (because the R value is still unpredictable), and the SK.prf value is not used anywhere else." — [Side Channel Resistant Sphincs+](https://csrc.nist.gov/csrc/media/Events/2024/fifth-pqc-standardization-conference/documents/papers/side-channel-resistant-sphincs-plus.pdf)
- Saarinen: "From a side-channel perspective, the R randomizer generation (Eq. 4) is the only part handling confidential variables (SK.prf) in this step. However, SK.prf is essentially redundant if randomization is used." — [Accelerating SLH-DSA by Two Orders of Magnitude with a Single Hash Unit (NIST PQC conference 2024; ePrint 2024/367)](https://csrc.nist.gov/csrc/media/Events/2024/fifth-pqc-standardization-conference/documents/papers/accelerating-slh-dsa.pdf)
- The pq-code-package `slhdsa-c` constant-time test harness treats the signing randomness as secret: "/* SK.seed and SK.prf, and the signing randomness, are secret */ SLH_CT_TESTING_SECRET(sk, 2 * prm->n); if (addrnd != NULL) { SLH_CT_TESTING_SECRET(addrnd, addrnd_sz); }". — [slhdsa-c test/xfips205.c](https://github.com/pq-code-package/slhdsa-c/blob/main/test/xfips205.c)
- The `fips205` Rust crate lists the secrets as "`SK.seed`, `SK.prf`, `opt_rand`, and the FORS and WOTS+ secret values derived from them". — [fips205 README](https://github.com/integritychain/fips205/blob/main/README.md)

**An industrial precedent for exactly which values get declassified (slhdsa-c, the SLH-DSA source used by liboqs).** "Constant-time testing with valgrind: secret data is marked as undefined, so that valgrind reports any branch or memory access depending on it. Values that are public by design are declassified when they are computed." — [slhdsa-c slh_sys.h](https://github.com/pq-code-package/slhdsa-c/blob/main/slh_sys.h). The declassification points in the signing and key-generation code are, in full:
- R: "Declassify the randomizer R. Required to use the message digest derived from it in conditional-branches and as tree indices. This is needed because R is computed from SK.prf, which is marked as secret (=undefined)."
- FORS public key: "Declassify the FORS public key. Required to use it in conditional-branches in WOTS+ signing. This is needed because it is computed from SK.seed, which is marked as secret (=undefined)."
- Each XMSS root: "Declassify the XMSS root of layer j-1. Required to use it in conditional-branches in WOTS+ signing of the next layer. This is needed because it is computed from SK.seed, which is marked as secret (=undefined)."
- Key generation: "/* Declassify public key */ SLH_CT_TESTING_DECLASSIFY(pk, 2 * n);" and "/* Declassify PK.root */".
- The harness declassifies the whole output signature after signing (`SLH_CT_TESTING_DECLASSIFY(sig_out, slh_sig_sz(prm))`) and the output key after key generation.
— [slhdsa-c slh_dsa.c](https://github.com/pq-code-package/slhdsa-c/blob/main/slh_dsa.c), [slhdsa-c test/xfips205.c](https://github.com/pq-code-package/slhdsa-c/blob/main/test/xfips205.c)

### Inferences
Proposed classification for a proof (my synthesis of the sources above; the "why" column names the supporting source).

| Value | Class | Why |
|---|---|---|
| SK.seed | secret | FIPS 205 §9.1 |
| SK.prf | secret | FIPS 205 §9.1 (essential in deterministic mode; in hedged mode with unpredictable addrnd its leak is argued harmless by Fluhrer/Saarinen, but FIPS still calls it secret) |
| addrnd / opt_rand (hedged) | secret (conservative) | FIPS 205 is silent; slhdsa-c and the fips205 crate both mark it secret; it is only ever an input to HMAC |
| opt_rand (deterministic) = PK.seed | public | FIPS 205 Alg. 19 line 2 |
| PRF outputs: WOTS+ chain starts, FORS secret leaf values | secret until/unless written into the signature | FIPS 205 §5, §8; Fluhrer §3 |
| WOTS+ chain values at positions below the signed digit; all chain values 0..w−2 of WOTS+ keys that are not signing (auth-path leaves, key generation) | secret | Kannwischer thesis §4.3.1–4.3.2; Fluhrer §3 |
| WOTS+ chain value at the signed digit (sig[i]) and everything above it up to the chain end | public | it is in the signature; the rest is computed by wots_pkFromSig |
| WOTS+ chain ends, compressed WOTS+ public keys, all XMSS tree nodes, XMSS roots, PK.root | public | FIPS 205 §5 ("end values ... are public values"); Kannwischer ("entire XMSS tree is public"); Fluhrer ("top value never is [secret]") |
| FORS leaf values F(sk), FORS tree nodes, FORS roots, PK_FORS | public | Fluhrer §3 ("the FORS leaf values are not [secret]"; "No secrets are involved here") |
| The k FORS secret values selected by md | secret before release, public after (they are in SIG_FORS) | FIPS 205 §8 |
| Unselected FORS secret values | secret | FIPS 205 §8; Fluhrer §3 |
| PK.seed, PK.root, M, ctx, M', message/context lengths, parameter set, hedged/deterministic flag | public | FIPS 205 §3, §10.2 |
| R | public (but derived from secrets: a declassification point) | Alg. 19 line 4; Fluhrer; slhdsa-c |
| digest, md (FORS indices), idx_tree, idx_leaf | public | function of R, PK, M only; Alg. 20 recomputes them |
| WOTS+ digits and checksum digits at every layer | public | digits of PK_FORS / XMSS roots, which the verifier recomputes |
| All ADRS contents | public | FIPS 205 §4.2 |

- Three declassification points suffice for signing (R; PK_FORS; the XMSS root at each of layers 0..d−2), plus PK.root in key generation. This is what slhdsa-c does, and it matches Fluhrer's "values also computed by the verifier".
- A finer-grained policy may also treat as public every Merkle node (XMSS and FORS), every WOTS+ chain end and every FORS leaf F(sk) as soon as it is computed, even for trees and leaves that this particular signature does not reveal. The support is Fluhrer's "internal nodes within a Merkle tree" clause and Kannwischer's "leakage agnostic" statement. This matters for a proof because auth-path computation manipulates nodes of subtrees that are siblings of the signing path; the simplest sound policy is that the output of T_len over chain ends, the output of F on a FORS secret, and all H outputs are public, while inputs to F inside WOTS+ chains are secret except on the signed chain at positions ≥ the digit.
- Intermediate values of a WOTS+ chain whose position is ≥ the digit are public only on the *signing* leaf. In an implementation that computes all w−1 steps for every chain (e.g. the SPHINCS+ reference `wots_gen_leafx1`), the code that copies out the signature value branches on the digit, not on the chain value; the chain values themselves never need to influence control flow or addresses.
- The policy "public" here is relative to unforgeability (protecting SK). It is not a claim that timing reveals nothing about the *message* or the *signature*; see question 3.

### Gaps
- FIPS 205 never states whether `addrnd` must be confidential. I found no NIST statement either way; treating it as secret is a convention taken from slhdsa-c and the fips205 crate.
- I did not locate a passage in the SPHINCS+ submission's formal security analysis (Section 9.1–9.3 of v3.1) that enumerates public values one by one; the classification above rests on FIPS 205's algorithm labels plus the Fluhrer and Kannwischer texts. The submission's own statement is the general one in Section 9.4.
- ePrint 2024/500 (the non-anonymous version of the Fluhrer paper) could not be downloaded (HTTP 403); author attribution comes from the CSRC presentation listing, not from the PDF I read.

## 2. Does FIPS 205 or NIST's accompanying material say anything explicit about timing side channels or constant-time implementation?

### Takeaway
FIPS 205 contains no constant-time requirement and never uses the words "timing" or "constant-time" about implementations; its only side-channel text is a non-normative paragraph in Section 3.2, a recommendation to use hedged signing where side channels are a concern, and a normative requirement to destroy sensitive intermediate data. The explicit timing statement comes from the SPHINCS+ submission (Section 9.4), not from NIST.

### Cited Findings
- Section 3.1 is normative, Section 3.2 is not: "This section specifies requirements for cryptographic modules that implement SLH-DSA. Section 3.2 discusses issues that implementers of cryptographic modules should take into consideration but that are not requirements." — [FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)
- The whole side-channel text of the standard (Section 3.2): "Side-channel and fault attacks. For signature schemes, the secrecy of the private key is critical. Care must be taken to protect implementations against attacks, such as side-channel attacks or fault attacks [17, 18, 19, 20, 21]. A cryptographic device may leak critical information with side-channel analysis or attacks that allow internal data or keying material to be extracted without breaking the cryptographic primitives." References 17–21 are Kannwischer et al. (DPA, COSADE 2018), Castelnovi–Martinelli–Prest (Grafting Trees), Genêt et al. (Practical Fault Injection Attacks on SPHINCS), Amiet et al. (FPGA-based SPHINCS+ Implementations: Mind the Glitch, DSD 2020) and Genêt (On Protecting SPHINCS+ Against Fault Attacks, TCHES 2023). None is a timing attack. — [FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)
- Normative data-destruction requirement (Section 3.1): "Destruction of sensitive data. Data used internally by key generation and signing algorithms in intermediate computation steps could be used by an adversary to gain information about the private key and thereby compromise security. The data used internally by verification algorithms is similarly sensitive for some applications, including the verification of signatures that are used as bearer tokens (i.e., authentication secrets) or signatures on plaintext messages that are intended to be confidential. Intermediate values of the verification algorithm may reveal information about its inputs (i.e., the message, signature, and public key), and in some applications, security or privacy requires one or more of these inputs to be confidential. Therefore, implementations of SLH-DSA shall ensure that any local copies of the inputs and any potentially sensitive intermediate data are destroyed as soon as they are no longer needed." — [FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)
- Hedged signing as a side-channel measure (Section 9.2): "The hedged variant is the default and should be used on platforms where side-channel attacks are a concern." — [FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)
- Floating point is forbidden for correctness, not timing: "Implementations of SLH-DSA shall not use floating-point arithmetic, as rounding errors in floating point operations may lead to incorrect results in some cases." — [FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)
- The CSRC page for FIPS 205 lists no errata, planning notes or updates as of this research; document history is 08/24/23 draft and 08/13/24 final; related publications are FIPS 203, FIPS 204 and SP 800-230 (Draft). (via page summary) — [CSRC FIPS 205 page](https://csrc.nist.gov/pubs/fips/205/final)
- SP 800-230 initial public draft, "Additional SLH-DSA Parameter Sets for Limited Signature Use Cases", published 04/13/2026 (comment period closed June 12, 2026), is a parameter-set extension; its abstract and page mention no side-channel, timing, fault or constant-time material. (via page summary) — [NIST SP 800-230 ipd](https://csrc.nist.gov/pubs/sp/800/230/ipd)
- NIST IR 8413-upd1 (third-round status report), on SPHINCS+: "The complexity of SPHINCS+ is a potential issue for implementation security ... The difficulty of protecting SPHINCS+ from side-channel attacks is mostly determined by the difficulty of protecting a keyed hash implementation from side-channel attacks." No statement about timing specifically for SPHINCS+. — [NIST IR 8413-upd1](https://nvlpubs.nist.gov/nistpubs/ir/2022/NIST.IR.8413-upd1.pdf)
- NIST SP 800-208 (stateful schemes) mentions only fault injection: implementations that re-sign a tree root on every signature "are vulnerable to fault injection attacks. Implementations compliant with this publication must sign the root of each tree only once." (footnote 9, citing Genêt et al. and Castelnovi et al.). It has no timing or constant-time text (a search of the full text for "side-channel", "timing", "constant-time" finds only this fault passage). — [NIST SP 800-208](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-208.pdf)
- SPHINCS+ submission v3.1, Section 9.4 "Implementation Security and Side-Channel Protection", in full for timing: "Timing attacks. Typical implementations of SPHINCS+ are naturally free of any secret-dependent branches or secretly indexed loads or stores. SPHINCS+ implementations are thus free of the two most notorious sources of timing variation. An exception is potentially SPHINCS+-Haraka, because Haraka is based on AES, which is well known to exhibit timing vulnerabilities in software implementations [4, 19, 6, 18]. Clearly, SPHINCS+-Haraka should only be used in environments that support AES in hardware (like almost all modern 64-bit Intel and AMD and many ARMv8a processors). On some processors also certain arithmetic instructions do not run in constant time; examples are division instructions on Intel processors and the UMULL multiplication instruction on ARM Cortex-M3 processors. Again, typical implementations of SPHINCS+ naturally do not use these instructions with secret data as input – secret data is only processed by symmetric cryptographic primitives that are designed to not make use of such potentially dangerous arithmetic." — [SPHINCS+ v3.1 specification](https://sphincs.org/data/sphincs+-r3.1-specification.pdf)
- Same section on physical attacks: "Differential and fault attacks. We expect that any implementation of SPHINCS+ without dedicated protection against differential power or electromagnetic radiation (EM) attacks or against fault-injection attacks will be vulnerable to such attacks. ... For protection against differential attacks this will typically require masking of the symmetric primitives; for protection against fault-injection attacks countermeasures on the hardware level. One additional line of defense against such advanced implementation attacks is included in the specification of SPHINCS+, namely the option to randomize the signing procedure via the value OptRand (see Subsection 8.1.5)." — [SPHINCS+ v3.1 specification](https://sphincs.org/data/sphincs+-r3.1-specification.pdf)
- Why OptRand exists (Section 8.1.5): "Deterministic signing can be a problem for devices which are susceptible to side-channel attacks as it allows to collect several traces for the exactly same computation by just asking for a signature on the same message multiple times." — [SPHINCS+ v3.1 specification](https://sphincs.org/data/sphincs+-r3.1-specification.pdf)
- The IETF stateful-scheme RFCs make the general claim: XMSS "naturally resists side-channel attacks" and hash-based schemes "are naturally resistant to most kinds of side-channel attacks" (RFC 8391, abstract and Section 1, May 2018); LMS/HSS "are naturally resistant to side-channel attacks" (RFC 8554, abstract, April 2019). Neither RFC has a dedicated side-channel subsection in its security considerations (full-text search). — [RFC 8391](https://www.rfc-editor.org/rfc/rfc8391.txt), [RFC 8554](https://www.rfc-editor.org/rfc/rfc8554.txt)

### Inferences
- A constant-time policy for SLH-DSA cannot be derived from a normative NIST sentence; it has to be justified from the algorithm's data flow (question 1) and the submission's Section 9.4. The proof's policy document should cite Section 9.4 as the designers' intent: no secret-dependent branches, no secretly indexed loads/stores, no variable-time arithmetic on secrets, secrets only ever enter hash/PRF calls.
- Section 9.4 names a third leak class beyond branches and addresses, namely variable-time instructions (division, some multipliers). A proof in the "cryptographic constant-time" model should therefore either exclude such instructions on secret operands or rely on a hardware data-independent-timing contract (question 6).
- FIPS 205's destruction requirement is about memory disclosure, not timing; it is a separate proof obligation (zeroisation) and is outside a timing model.

### Gaps
- I did not search FIPS 140-3 implementation guidance or CMVP/ACVP documents for SLH-DSA-specific non-invasive-attack requirements; whether any exists as of late 2026 is unconfirmed.
- The comments received on SP 800-230 ipd were not read.

## 3. In WOTS+ signing the chain lengths depend on the message digits. Is that a leak, and does observing chain lengths before the signature is released matter?

### Takeaway
It is not a leak of key material: the digits are base-16 digits of PK_FORS or of an XMSS root (plus checksum), all of which the verifier recomputes from the public key, message and signature; several sources say this explicitly. No source I found treats pre-release observation of chain lengths as an attack on the key; the residual concern is confidentiality of the message/signature themselves, which FIPS 205 flags only for applications that need it.

### Cited Findings
- "It isn't necessarily constant time; a Sphincs+ implementation may have conditionals based on, for example, the part of the tree we are exposing, or the revealed index within a Winternitz chain. However, that data can also be deduced by the attacker by examining the signature, message and public key, and hence these conditionals do not leak any secret information." (footnote 1, attached to "Typical implementations of Sphincs+ are immune to timing and cache-based side channel attacks. The obvious implementation makes no conditional jumps or memory references based on secret data, as long as the hash function implementation do not (and the standard implementations of SHA-2 and SHAKE do not when hashing messages of fixed length).") — [Side Channel Resistant Sphincs+](https://csrc.nist.gov/csrc/media/Events/2024/fifth-pqc-standardization-conference/documents/papers/side-channel-resistant-sphincs-plus.pdf)
- "Timing attacks are not a great concern for SLH-DSA, as conditional branching and memory access patterns are dependent on non-secret authentication paths; they are revealed by the signature and known to a verifier." (Section 6) — [Saarinen, Accelerating SLH-DSA](https://csrc.nist.gov/csrc/media/Events/2024/fifth-pqc-standardization-conference/documents/papers/accelerating-slh-dsa.pdf)
- "During key generation, the number of hash calls is fixed (w−1) and during signature generation, the number of hash calls solely depends on the message blocks (b_i). The blocks b_i only depend upon the message digest which is again of no interest to a potential attacker. According to assumption 1, the hash function itself does not contain a timing side-channel, therefore, evaluating c_k(x_i, r) cannot leak anything about x_i with respect to timing." — [Kannwischer thesis §4.3.1](https://download.hrz.tu-darmstadt.de/pub/FB20/Dekanat/Publikationen/CDC/Matthias_Kannwischer.master.pdf)
- "We have shown that timing side-channels in W-OTS+ can only be used to extract information about the b_i's, which the adversary either already knows (known message attack) or chooses himself (chosen-message attack). The additional computation in XMSS may leak some information about the internal state s, but this value is already contained in a valid signature and cannot be used to mount an attack. Therefore, we conclude that XMSS does not have a timing side-channel, if the assumptions from Section 4.2 hold." — [Kannwischer thesis §4.3.3](https://download.hrz.tu-darmstadt.de/pub/FB20/Dekanat/Publikationen/CDC/Matthias_Kannwischer.master.pdf)
- For plain W-OTS: "The runtime of a W-OTS signature generation only depends on the message to be signed and therefore does not leak any valuable information to an attacker." For LMS: "the timing of this chaining function does not leak any valuable information since it only depends on j which is not secret." For SPHINCS: "The number of hash function evaluations for both HORST key generation and HORST signature generation is independent of the secret key. ... The rest of the SPHINCS construction is only using W-OTS+ and XMSS and can thus not contain a timing side-channel." — [Kannwischer thesis](https://download.hrz.tu-darmstadt.de/pub/FB20/Dekanat/Publikationen/CDC/Matthias_Kannwischer.master.pdf)
- The peer-reviewed version (COSADE 2018) states in its abstract that "timing and simple power analysis attacks are unpromising" for XMSS and SPHINCS. (via page summary of the ePrint abstract) — [ePrint 2018/673](https://eprint.iacr.org/2018/673)
- Partial exposure of chain values is intrinsic: "the output of the chaining function is directly part of the signature and is, therefore, considered to be known to the adversary. If b_i = 0 this means that the adversary knows part of the secret key. However, this does not undermine the security of W-OTS+ due to its one-time nature and the checksum, i.e., partial leakage is an intrinsic characteristic of hash-based signature schemes." — [Kannwischer thesis §4.3.1](https://download.hrz.tu-darmstadt.de/pub/FB20/Dekanat/Publikationen/CDC/Matthias_Kannwischer.master.pdf)
- The caveat about pre-release secrecy of chain values (not digits): "Since the b_i's are not known before the actual message is signed, all intermediate values have to be considered secret." — [Kannwischer thesis §4.3.1](https://download.hrz.tu-darmstadt.de/pub/FB20/Dekanat/Publikationen/CDC/Matthias_Kannwischer.master.pdf)
- FIPS 205 recognises that inputs to verification (message, signature) can be confidential in some applications ("signatures that are used as bearer tokens ... or signatures on plaintext messages that are intended to be confidential"); the passage concerns destroying intermediate data, not timing. — [FIPS 205 §3.1](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)
- The top-of-checksum chain is partly public for structural reasons: "For the WOTS chain that corresponds to the most significant digit of the checksum field, that value has a reduced range. In particular, for Level 1, that digit will always be in the range 0-1 ... Hence, all positions in that WOTS chain past that will always be public". — [Side Channel Resistant Sphincs+](https://csrc.nist.gov/csrc/media/Events/2024/fifth-pqc-standardization-conference/documents/papers/side-channel-resistant-sphincs-plus.pdf)
- RFC 8391's security considerations contain no discussion of chain-length or timing leakage (full-text search for "side-channel", "timing", "constant-time" finds only the general "naturally resists side-channel attacks" claims in the abstract and introduction). — [RFC 8391](https://www.rfc-editor.org/rfc/rfc8391.txt)

### Inferences
- What an observer of chain lengths learns, layer by layer, in SLH-DSA: at layers 1..d−1 the WOTS+ message is the XMSS root of the tree below, a fixed function of the key pair and of idx_tree; at layer 0 it is PK_FORS, a fixed function of the key pair and (idx_tree, idx_leaf). Neither depends on M except through the indices. The FORS indices and (idx_tree, idx_leaf) are H_msg(R, PK.seed, PK.root, M). So timing of the hypertree part reveals at most which hypertree path was taken, and timing/addresses of the FORS part reveal md. All of this is in, or computable from, the eventual signature.
- "Before release" therefore changes nothing for key secrecy: the leaked quantities are outputs of H_msg and digits of values that the security proof already hands to the adversary with every signature. The scheme's EUF-CMA argument does not rely on the adversary being ignorant of md, the indices, PK_FORS or the roots at any time. The only quantity whose early disclosure could matter is R (a PRF_msg output), and R is simply published.
- Where it can matter is outside unforgeability: (i) a signer whose signatures or messages are confidential (signature transported under encryption, or signing of secret messages) leaks partial information about H_msg(R, …, M) and about the hypertree path through timing; (ii) a signer that aborts or withholds a signature after computing it has still leaked md/indices for that (R, M). Neither helps forge. If the project wants message privacy as well, md/idx would have to be reclassified as secret, which is a much stronger and non-standard policy (it would forbid index-dependent tree traversal).
- In the hedged variant R is fresh per signature, so the digits observed for one signing attempt are not replayable; in the deterministic variant the same (key, M) always yields the same path, which is what makes fault attacks easier (question 4) but still does not create a timing leak of the key.
- For the literal FIPS 205 algorithms, per-chain work in signing is msg[i] F-calls in wots_sign and w−1−msg[i] in the following xmss_pkFromSig, so layers 0..d−2 cost a constant number of F-calls; only the top layer (where Algorithm 12 skips xmss_pkFromSig) has a digit-dependent count. Total signing time is thus nearly, but not exactly, independent of the digits. (Derived from Algorithms 7, 8, 12 of [FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf); not stated in any source.)

### Gaps
- I found no paper, standard or mailing-list post that analyses the specific scenario "attacker observes WOTS+ chain lengths before (or without) seeing the signature" for SLH-DSA. An extended web search for it returned only the general statements above. The conclusion that it is harmless to the key is an inference from the scheme's structure.
- The SPHINCS+ v3.1 specification does not itself contain a sentence saying "the WOTS+ digits are public"; the closest designer statement is Section 9.4's "naturally free of any secret-dependent branches".

## 4. Which side-channel and fault attacks on SPHINCS / SPHINCS+ / SLH-DSA / XMSS / LMS are published, and is a software constant-time guarantee relevant to each?

### Takeaway
I found no published timing, cache or control-flow attack against a correct implementation of any standardised hash-based signature scheme; the literature says such attacks are "unpromising"/"not a great concern". Every published key-recovery or forgery attack is either power/EM analysis of the PRF (and F) calls that consume SK.seed, or a fault attack (glitching or Rowhammer) that makes a WOTS+ key sign two different values. A cryptographic-constant-time proof addresses none of these; it closes only class (a).

### Cited Findings

**(a) Timing / cache / control flow.**
- No attack found. Supporting statements: "Typical implementations of Sphincs+ are immune to timing and cache-based side channel attacks" — [Side Channel Resistant Sphincs+ (2024)](https://csrc.nist.gov/csrc/media/Events/2024/fifth-pqc-standardization-conference/documents/papers/side-channel-resistant-sphincs-plus.pdf); "Timing attacks are not a great concern for SLH-DSA" — [Saarinen (2024)](https://csrc.nist.gov/csrc/media/Events/2024/fifth-pqc-standardization-conference/documents/papers/accelerating-slh-dsa.pdf); "Timing attacks are impossible due to the constant runtime of all building blocks processing secret data" (abstract, about XMSS, conditional on a side-channel-free hash and PRNG) — [Kannwischer thesis (2017)](https://download.hrz.tu-darmstadt.de/pub/FB20/Dekanat/Publikationen/CDC/Matthias_Kannwischer.master.pdf); "timing and simple power analysis attacks are unpromising" (via page summary) — [Kannwischer et al., ePrint 2018/673](https://eprint.iacr.org/2018/673).
- The thesis adds the standard caveat: "a scheme cannot be proved to be timing side-channel resistant, since the implementation can still introduce additional leakage". — [Kannwischer thesis §2.2](https://download.hrz.tu-darmstadt.de/pub/FB20/Dekanat/Publikationen/CDC/Matthias_Kannwischer.master.pdf)
- A 2025 systematisation of PQC side-channel attacks exists (Dobias, Rezaeezade, Chmielewski, Malina, Batina, "SoK: Reassessing Side-Channel Vulnerabilities and Countermeasures in PQC Implementations", received 2025-06-30); its abstract does not mention hash-based signatures or timing, and I did not read the body. (via page summary) — [ePrint 2025/1222](https://eprint.iacr.org/2025/1222)
- Warning about a bogus source: a blog post titled "CVE-2026-7731: SPHINCS+ Timing Attack [Deep Dive]" appears in search results and describes a timing-based key recovery in "SPHINCS+/SLH-DSA implementations" without naming any library, version, discoverer or primary source. The actual CVE record CVE-2026-7731 (assigner VulDB, published 2026-05-04) is "code-projects BloodBank Managing System get_state.php sql injection" and has nothing to do with SPHINCS+. The blog post should be disregarded. — [CVE-2026-7731 record (MITRE CVE API)](https://cveawg.mitre.org/api/cve/CVE-2026-7731); contradicts [techbytes.app post](https://techbytes.app/posts/cve-2026-7731-sphincs-plus-timing-attack-deep-dive/)
- Relevance of a constant-time proof: this is exactly the class it rules out, given the hash primitive is itself constant-time (question 6).

**(b) Power / EM analysis.**
- Kannwischer, Genêt, Butin, Krämer, Buchmann, "Differential Power Analysis of XMSS and SPHINCS", COSADE 2018 (LNCS 10815, pp. 168–188; ePrint 2018/673, received 2018-07-13). Attacks, in the Hamming-weight model, a SHA-2-based PRNG for XMSS and the BLAKE-256-based PRF of SPHINCS-256; "at least a 32-bit chunk of the SPHINCS secret key can be recovered using a differential power analysis attack"; the XMSS DPA resistance "can be reduced to the differential power analysis resistance of the underlying pseudorandom number generator". (via page summary) — [ePrint 2018/673](https://eprint.iacr.org/2018/673)
- Why the PRF is the DPA target: "In SLH-DSA, the SK.seed is used as a input to the PRF function, with all other inputs being public, and varying per use. This situation is ideal for an attacker using DPA". — [Side Channel Resistant Sphincs+ (2024)](https://csrc.nist.gov/csrc/media/Events/2024/fifth-pqc-standardization-conference/documents/papers/side-channel-resistant-sphincs-plus.pdf)
- Saarinen (2024): "We show experimentally that an SLH-DSA implementation with CPU hashing will rapidly leak the SK.seed master key"; fixed-vs-random TVLA on an unaccelerated RISC-V software implementation of SLH-DSA-SHAKE-128f: "Leakage from SK.seed was rapidly evident, with t value reaching 24.5 in 1,000 traces ... leakage from these PRF calls can be combined in a horizontal attack as they all use the same SK.seed." Also: "the main target for SLH-DSA leakage countermeasures is the PRF function, as it directly handles secret variables" and "randomized signing makes side-channel attacks much more difficult to mount, so this must be the default in all high-security applications." — [Saarinen, Accelerating SLH-DSA](https://csrc.nist.gov/csrc/media/Events/2024/fifth-pqc-standardization-conference/documents/papers/accelerating-slh-dsa.pdf)
- Carrera Rodriguez, Zahreddine, Monthieu, Vasselle, Liardet, "SHAKEing SLH-DSA with Non-profiled SCAs" (ePrint 2026/2584, received 2026-10-21): correlation power analysis of the PRF of SLH-DSA-SHAKE; recovers the full secret seed, enabling universal forgery, in about 280 to 559 signatures on average, validated in simulation and on a 32-bit microcontroller. (via page summary) — [ePrint 2026/2584](https://eprint.iacr.org/2026/2584)
- Countermeasure cost context: Fluhrer's modified-PRF design "performed 1.7 times slower compared to an unprotected version" and is not key-compatible with standard SLH-DSA. — [Side Channel Resistant Sphincs+ (2024)](https://csrc.nist.gov/csrc/media/Events/2024/fifth-pqc-standardization-conference/documents/papers/side-channel-resistant-sphincs-plus.pdf)
- Relevance of a constant-time proof: none. These attacks observe data-dependent power/EM of the hash rounds on a device the attacker can probe; identical control flow and addresses do not help. The designers say the remedy is masking ("this will typically require masking of the symmetric primitives"). — [SPHINCS+ v3.1 specification §9.4](https://sphincs.org/data/sphincs+-r3.1-specification.pdf)

**(c) Fault injection.**
- Castelnovi, Martinelli, Prest, "Grafting Trees: a Fault Attack against the SPHINCS framework", PQCrypto 2018 (ePrint 2018/102): a fault during a repeated signature makes a one-time signature sign a different value than before; the two signatures let the attacker recover part of that one-time key and graft a chosen tree; one faulted signature can suffice for a universal forgery; the faulted signature still verifies. Applies to SPHINCS, Gravity-SPHINCS and SPHINCS+. (via search summary of the abstract) — [ePrint 2018/102](https://eprint.iacr.org/2018/102)
- Genêt, Kannwischer, Pelletier, McLauchlan, "Practical Fault Injection Attacks on SPHINCS" (ePrint 2018/674): first practical demonstration, on an Arduino Due (Cortex-M3) running SPHINCS; notes that caching one-time signatures blocks the attack for stateful XMSS/LMS but is less effective for stateless schemes. (via search summary of the abstract) — [ePrint 2018/674](https://eprint.iacr.org/2018/674)
- Amiet, Leuenberger, Curiger, Zbinden, "FPGA-based SPHINCS+ Implementations: Mind the Glitch", DSD 2020 (FIPS 205 reference [20]). I confirmed only the citation, not the content. — [DOI 10.1109/DSD51259.2020.00046](https://doi.org/10.1109/DSD51259.2020.00046)
- Genêt, "On Protecting SPHINCS+ Against Fault Attacks", TCHES 2023(2), pp. 80–114 (ePrint 2023/042): "the security guarantees of SPHINCS+ significantly drop when a single random bit flip occurs anywhere in the signing procedure"; "the resulting faulty signature cannot be detected with the verification procedure"; caching-based countermeasures are circumvented with "a tolerable number of queries in an active attack"; "the paper recommends real-world deployments of SPHINCS+ to implement redundancy checks." (via page summary) — [ePrint 2023/042](https://eprint.iacr.org/2023/042)
- A 2026 TCHES paper, "Fault Attack Countermeasures for SPHINCS+: WOTS+ with Checksum Segmentation and Subtree Root Children Caching", was returned by search; I could not open the page (bot protection), so title and venue are unverified beyond the search listing. — [TCHES article 13073](https://tches.iacr.org/index.php/TCHES/article/view/13073)
- Stateful schemes: SP 800-208 requires that HSS/XMSS^MT implementations sign each tree root only once because re-signing "implementations are vulnerable to fault injection attacks". — [NIST SP 800-208](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-208.pdf)
- The submission anticipated this class: the SPHINCS+ secret key contains a copy of the public key because signing "needs access to PK.seed (and possibly to PK.root for fault attack mitigation)". — [SPHINCS+ v3.1 specification §6.2](https://sphincs.org/data/sphincs+-r3.1-specification.pdf)
- Relevance of a constant-time proof: none. The attacker corrupts a computation; nothing is inferred from timing.

**(d) Rowhammer.**
- Boy, Purnal, Pätschke, Wilke, Eisenbarth, "SLasH-DSA: Breaking SLH-DSA Using an Extensible End-To-End Rowhammer Framework" (arXiv 2509.13048; v1 16 September 2025, v2 2 February 2026; to appear at uASC 2026). Abstract: "we present the first software-only universal forgery attack on SLH-DSA, leveraging Rowhammer-induced bit flips to corrupt the internal state and forge signatures. ... We demonstrate full end-to-end attacks against SLH-DSA in OpenSSL 3.5.1, achieving universal forgery for the SHAKE-128f (deterministic), SHA2-128s, and SHAKE-192f (randomized) parameter sets after one hour (deterministic) or eight hours (randomized) of hammering and post-processing ranging from minutes to an hour". Body: "For SLH-DSA's deterministic signing mode, which is not the default setting in OpenSSL but specified and allowed by the FIPS 205 standard, we achieve universal forgery for the SLH-DSA-SHAKE-128f parameter set after one hour of Rowhammer and 151 seconds of post-processing"; SHAKE-192f randomized "after eight hours of Rowhammer attack and 1417 seconds of post-processing". The v1 abstract named different parameter sets; cite v2. — [arXiv 2509.13048](https://arxiv.org/abs/2509.13048)
- This is the same grafting-tree fault mechanism delivered by software-induced DRAM bit flips; the paper itself uses timing side channels only as Rowhammer tooling (row-conflict timing, SPOILER) and mentions "a cache attack" as one way to synchronise with the victim, not to extract key material. — [arXiv 2509.13048](https://arxiv.org/abs/2509.13048)
- Relevance of a constant-time proof: none; SHA2-128s in a widely deployed library is explicitly among the demonstrated targets, so this is the most practically relevant out-of-model attack for the parameter set of interest.

### Inferences
- Model boundary to state in the proof: "cryptographic constant-time" (no secret-dependent control flow, memory addresses, or variable-latency instruction operands) covers remote timing and same-host cache/branch-predictor observers. It does not cover power/EM (b), faults (c, d), transient-execution leaks, or memory disclosure.
- Deterministic signing is strictly worse for (b), (c) and (d), because the same computation can be repeated; this is why FIPS 205 makes hedged the default. For class (a) the two variants are equivalent: the hedged variant adds one more secret input (`addrnd`) that flows only into HMAC-SHA-256.
- Because the same SK.seed feeds thousands of PRF calls per signature (Saarinen), the PRF call is also where a hardware data-independent-timing guarantee matters most: it is the one place where a variable-latency instruction on a secret operand would leak the master seed.

### Gaps
- I did not find, and cannot rule out, unpublished or very recent (late 2026) timing or microarchitectural work against a specific SLH-DSA library. Searches for timing/cache attacks on XMSS, LMS and SPHINCS+ implementations returned none.
- Bibliographic details of Castelnovi et al., Genêt et al. 2018 and Amiet et al. were taken from FIPS 205's reference list and search summaries; the papers themselves were not read (ePrint PDFs returned 403).
- No transient-execution (Spectre-class) analysis of any SLH-DSA implementation was found.

## 5. How do existing implementations describe their timing behaviour, and do they contain non-constant-time constructs?

### Takeaway
Every implementation examined branches and loops on the WOTS+ digits and tree indices and compares the final root with a variable-time `memcmp` or `==`; none treats this as a defect. Explicit, scoped constant-time claims exist only in the `fips205` Rust crate (source-level claim, dudect-measured) and in `slhdsa-c` (valgrind-based secret tracking with explicit declassification of R, PK_FORS and XMSS roots); OpenSSL, BoringSSL, RustCrypto and the SPHINCS+ reference code make no documented claim.

### Cited Findings
- **SPHINCS+ reference implementation.** The README makes no statement about timing. `ref/wots.c` `gen_chain` loops "for (i = start; i < (start+steps) && i < SPX_WOTS_W; i++)" (verification path). In signing, `ref/wotsx1.c` computes every chain of every leaf to the top and extracts the signature value with a digit-dependent branch: "if (k == wots_k) { memcpy( info->wots_sig + i * SPX_N, buffer, SPX_N ); }", with `wots_k` masked to ~0 for non-signing leaves and a branch "if (leaf_idx == info->wots_sign_leaf)". Verification ends with "if (memcmp(root, pub_root, SPX_N)) { return -1; }". — [sphincsplus ref/wotsx1.c](https://github.com/sphincs/sphincsplus/blob/master/ref/wotsx1.c), [ref/wots.c](https://github.com/sphincs/sphincsplus/blob/master/ref/wots.c), [ref/sign.c](https://github.com/sphincs/sphincsplus/blob/master/ref/sign.c), [README](https://github.com/sphincs/sphincsplus/blob/master/README.md)
- Scott Fluhrer (SPHINCS+ co-submitter) on pqc-forum, 20 February 2025: "Actually, providing a constant time SLH-DSA implementation would not be difficult."; the same message says the reference code is already close to constant-time for signing and that constant-time verification would roughly double verification time. (via page summary; thread truncated) — [pqc-forum thread "Constant time digital signature algorithm"](https://groups.google.com/a/list.nist.gov/g/pqc-forum/c/i38i7t950Cw)
- **PQClean.** The repository-wide checklist lists "No branching on secret data (dynamically checked using valgrind)" and "No access to secret memory locations (dynamically checked using valgrind)" as unchecked boxes, i.e. not yet an enforced property of the project. — [PQClean README](https://github.com/PQClean/PQClean/blob/master/README.md)
- **liboqs.** Current SLH-DSA comes from `pq-code-package/slhdsa-c` (pinned commit a0fc1ff…); the datasheet's columns "No branching-on-secrets claimed?" and "No branching-on-secrets checked by valgrind?" are both "False" for it. The older SPHINCS+ datasheet (liboqs 0.12.0, PQClean-derived) showed for SPHINCS+-SHA2-128s-simple: `clean` False/False, `avx2` True/True. — [liboqs slh_dsa.md](https://github.com/open-quantum-safe/liboqs/blob/main/docs/algorithms/sig/slh_dsa.md), [liboqs 0.12.0 sphincs.md](https://github.com/open-quantum-safe/liboqs/blob/0.12.0/docs/algorithms/sig/sphincs.md)

### Inferences
- Data-dependent loops over WOTS+ digits and index-dependent tree traversal are universal and accepted; the justification (digits and indices are public) is written down only by Fluhrer, Saarinen, the fips205 crate and, implicitly, slhdsa-c's declassification comments. A formal policy that declassifies R, PK_FORS and XMSS roots is therefore the mainstream position, not a relaxation.
- The fips205 crate's wording is close to a ready-made policy statement and can be cited as prior art for scope: source-level claim; compiler and CPU trusted; verify excluded; message/context length public.
- liboqs's "False/False" for slhdsa-c reflects a datasheet for a pinned commit and a project convention, not a known leak; upstream now runs CT tests. The two facts are not in conflict but the datasheet has not caught up (or the liboqs CI does not run its own valgrind check on this code).
- slhdsa-c's use of the KyberSlash variable-latency Valgrind patch shows current practice extends "constant-time" to "no secret operands to variable-latency instructions", matching Section 9.4 of the SPHINCS+ submission.

### Gaps
- No implementation documents a threat model in which md/indices are secret (message privacy).
- I did not check wolfSSL, Botan, Bouncy Castle, libcrux, mbedTLS/TF-PSA-Crypto, the Go standard library, or pqm4.
- OpenSSL's and BoringSSL's project-wide constant-time testing infrastructure may or may not cover SLH-DSA; I only inspected the SLH-DSA source files, not the test configuration.
- The pqc-forum thread was truncated after six messages; later replies were not seen.
- Whether AWS-LC ships SLH-DSA elsewhere in its tree (outside `crypto/fipsmodule`) was not confirmed; only the directory listing and PQREADME were checked.

## 6. Is SHA-256 itself constant-time, and what do Arm DIT and Intel DOIT guarantee for the hardware SHA instructions?

### Takeaway
Software SHA-256 is constant-time in the standard model: only 32-bit additions, rotations, shifts and bitwise operations on data, constant-indexed round constants, and a block count that depends only on (public) input length. For hardware SHA, Arm's architecture specification marks SHA256H, SHA256H2, SHA256SU0 and SHA256SU1 as data-independent-time instructions, but the guarantee holds only when PSTATE.DIT = 1; Intel lists SHA256RNDS2, SHA256MSG1 and SHA256MSG2 in its data-operand-independent-timing instruction table, with the guarantee conditional on DOITM being enabled on processors that enumerate it.

### Cited Findings

**SHA-256 in software.**
- "Hash functions implemented by BearSSL (MD5, SHA-1, SHA-224, SHA-256, SHA-384 and SHA-512) consist in bitwise logical operations and additions on 32-bit or 64-bit words, naturally yielding constant-time operations." and "HMAC is naturally as constant-time as the underlying hash function." — [BearSSL, "Constant-Time Crypto"](https://www.bearssl.org/constanttime.html)
- "the standard implementations of SHA-2 and SHAKE do not [make conditional jumps or memory references based on secret data] when hashing messages of fixed length". — [Side Channel Resistant Sphincs+ (2024)](https://csrc.nist.gov/csrc/media/Events/2024/fifth-pqc-standardization-conference/documents/papers/side-channel-resistant-sphincs-plus.pdf)
- "For SHA2, which is based on the Merkle-Damgård construction, the message blocks are combined to a digest by iteratively calling a compression function. The number of compression function calls is fixed for a fixed input size. ... None of these functions contains conditional branches depending on the input passed to the function." — [Kannwischer thesis](https://download.hrz.tu-darmstadt.de/pub/FB20/Dekanat/Publikationen/CDC/Matthias_Kannwischer.master.pdf)
- HACL* states its "Secret Independence" guarantee as: observations of the code's low-level behaviour, "the time it takes to execute or the memory addresses that it accesses", are independent of the secrets. (via page summary; the page read did not include the algorithm list, so SHA-2 coverage was not confirmed from it.) — [HACL* overview](https://hacl-star.github.io/Overview.html)

**Arm: PSTATE.DIT (FEAT_DIT).**
- DIT register description, value 0b0: "The architecture makes no statement about the timing properties of any instructions." Value 0b1: "The architecture requires that: The timing of every load and store instruction is insensitive to the value of the data being loaded or stored. For certain data processing instructions, the instruction takes a time which is independent of: The values of the data supplied in any of its registers. The values of the NZCV flags. For certain data processing instructions, the response of the instruction to asynchronous exceptions does not vary based on: The values of the data supplied in any of its registers. The values of the NZCV flags." The page says the Operational Information section of each instruction's description states whether it is affected. "On a Warm reset, this field resets to 0." (via page summary; mirror of Arm's system-register XML dated 26/03/2024) — [AArch64 DIT register (mirror of Arm sysreg XML)](https://df.lth.se/~getz/ARM/SysReg/AArch64-dit.html)
- Per-instruction status in Arm's A64 instruction-set XML, release 2026-03 (2026-03-26): the "Operational information" of SHA256H reads "This instruction is a data-independent-time instruction as described in About PSTATE.DIT." I checked the same sentence is present on the pages for SHA256H2, SHA256SU0 and SHA256SU1, and also for vector ADD, REV32 and LDR (immediate); it is absent from the UDIV page. — [SHA256H](https://www.scs.stanford.edu/~zyedidia/arm64/sha256h_advsimd.html), [SHA256H2](https://www.scs.stanford.edu/~zyedidia/arm64/sha256h2_advsimd.html), [SHA256SU0](https://www.scs.stanford.edu/~zyedidia/arm64/sha256su0_advsimd.html), [SHA256SU1](https://www.scs.stanford.edu/~zyedidia/arm64/sha256su1_advsimd.html), [UDIV](https://www.scs.stanford.edu/~zyedidia/arm64/udiv.html) (mirror of Arm's A64 ISA XML, 2026-03_rel)
- Apple's guidance: "Apple silicon provides data-independent timing (DIT), in which the processor completes certain instructions in a constant amount of time. With DIT enabled, the processor uses the longer, worst-case amount of time to complete the instruction, regardless of the input data. ... enabling DIT — and restricting your code to instructions that support DIT — before loading cryptographic key material, performing cryptographic operations, or processing sensitive data ensures the timing of specific instructions doesn't reveal information about the data being processed." "Apple cryptographic routines implemented in the operating system, and which are made available in APIs such as Apple CryptoKit, enable DIT internally." "While DIT ensures the timing of certain instructions don't reveal information about the data, you need additional programming practices to prevent other changes to the processor's microarchitectural state from providing an adversary with signals about secret values. For example, avoid conditional branches and memory access locations based on the value of the secret data." "In iOS 18.2, iPadOS 18.2, macOS 15.2 ... and later, two new function calls are available to control and optimize DIT ... You protect a set of cryptographic operations by calling timingsafe_enable_if_supported unconditionally to turn on DIT. Internally, the function uses safeguards adequate for the device CPU to limit the speculative computation; for example, speculation barriers (SB)." — [Apple, "Writing ARM64 code for Apple platforms"](https://developer.apple.com/documentation/xcode/writing-arm64-code-for-apple-platforms)
- Context from a search summary (not opened): FEAT_DIT is mandatory from Armv8.4; some cores, e.g. Neoverse-V1, show no data-value timing variation for the covered instructions regardless of the DIT setting; Linux enables DIT in the kernel (2022 patches) and user space must set it itself. — [linux-arm-kernel: "arm64: Enable data independent timing (DIT) in the kernel"](https://lore.kernel.org/linux-arm-kernel/CAMj1kXFv5gyp=jkgHPJPT9nLW16jpBF4rdo6tDCZYAPgkRma3Q@mail.gmail.com/T/)

**Intel: DOIT / DOITM.**
- Definition: with the mode enabled, instructions in the subset "execute with timing (in terms of processor cycles) that is independent of the data values in the sources of the instruction." "IA32_UARCH_MISC_CTL[DOITM] is a data operand independent timing mode control mechanism."; support is enumerated by IA32_ARCH_CAPABILITIES[12]. For older processors (Core before Ice Lake, Atom before Gracemont) that do not enumerate the MSR, "developers may assume that the instructions listed here operate as if DOITM is enabled."; newer processors enumerate DOITM, so the bit must be set to obtain the guarantee; SGX enclaves on such processors "will always enable data operand independent timing mode". Not covered: latency "may be affected by which memory address is used"; immediates and code bytes "may be inferable using timing attacks"; speculative execution may handle secrets in a data-dependent way; power/thermal/frequency channels are out of scope. Page shows "Updated 11/13/2026". (via page summary) — [Intel, Data Operand Independent Timing ISA Guidance](https://www.intel.com/content/www/us/en/developer/articles/technical/software-security-guidance/best-practices/data-operand-independent-timing-isa-guidance.html)
- Instruction table (last updated 2/23/2026): "The table below lists instructions that have data-independent timing." SHA256RNDS2, SHA256MSG1, SHA256MSG2, SHA1RNDS4, SHA1NEXTE, SHA1MSG1, SHA1MSG2 are listed, as are ADD, XOR, ROR, ROL, SHR, BSWAP, MOV, PSHUFB, PALIGNR, PADDD and AESENC. Caveats: listed instructions "may have variable latency for reasons unrelated to the data values"; listing does not imply resistance to power, thermal or frequency side channels; REP string instructions vary with the count. (via page summary) — [Intel, Data Operand Independent Timing Instructions](https://www.intel.com/content/www/us/en/developer/articles/technical/software-security-guidance/resources/data-operand-independent-timing-instructions.html)

**Why it matters for SLH-DSA specifically.**
- The submission's own warning: "On some processors also certain arithmetic instructions do not run in constant time; examples are division instructions on Intel processors and the UMULL multiplication instruction on ARM Cortex-M3 processors." — [SPHINCS+ v3.1 specification §9.4](https://sphincs.org/data/sphincs+-r3.1-specification.pdf)

### Inferences
- For the hw-sha2 build on AArch64, the proof obligation splits cleanly: (i) software level, every instruction that receives a secret operand is in Arm's DIT set (SHA256H/H2/SU0/SU1, vector ADD/EOR/REV, loads and stores are; division is not); (ii) platform level, PSTATE.DIT must be 1 while secrets are processed, otherwise "the architecture makes no statement". Setting DIT (e.g. `msr dit, #1`, or Apple's `timingsafe_enable_if_supported`) is a deployment assumption that should be stated in the theorem, since it is not established by the code's functional semantics.
- On x86-64 the analogous assumption is DOITM = 1 on Ice Lake-and-later / Gracemont-and-later processors; setting the MSR is a privileged operation, so user-space code depends on the OS.
- Both vendors' contracts exclude address-dependent timing and control flow: DIT/DOIT complement, and do not replace, the no-secret-branch/no-secret-index properties.
- In the SHA-2 instantiation the PRF and F inputs place PK.seed padded to a full 64-byte block first, so the first compression is over public data and the secret (SK.seed or a chain value) enters only in the second block; HMAC-SHA-256 for PRF_msg keys with SK.prf in the first block of both inner and outer hashes. The number of compression calls depends only on input lengths, which are public (n, ADRS^c size, and message/context length for PRF_msg and H_msg). (Derived from [FIPS 205 §11.2.1](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf).)

### Gaps
- I could not open Arm's own developer.arm.com pages or the Arm ARM PDF (DDI 0487) directly; the DIT text and per-instruction status come from third-party mirrors of Arm's machine-readable specification (system-register XML 2024-03 and A64 ISA XML 2026-03). The exact wording of the Arm ARM section "About PSTATE.DIT" and its category list should be checked against the current DDI 0487 release before being quoted.
- The Intel pages were read through a summarising tool; the instruction-table membership of the SHA instructions should be re-verified by direct inspection.
- No AMD statement on data-operand-independent timing for SHA-NI was searched for.
- I did not find a formally verified constant-time proof of a hardware-instruction SHA-256 kernel to cite as precedent (Vale/HACL* style work exists for x86 and Arm SHA-256 but was not retrieved here).

## 7. Does verification need any constant-time property?

### Takeaway
No, as far as key secrecy is concerned: verification takes only the public key, message, context and signature, and compares a recomputed root with PK.root; implementations uniformly use a variable-time comparison. The only caveat in the standard is for applications where the message or signature is itself confidential.

### Cited Findings
- Verification's inputs and final step: "Verification succeeds if the correct public-key value is computed, which is determined by using the computed public-key value along with other information to compute a candidate PK.root value and then comparing that value to the known value of PK.root from the SLH-DSA public key." (Section 5.3); Algorithm 20's inputs are M, SIG and PK = (PK.seed, PK.root). — [FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)
- The standard's only sensitivity statement about verification: "The data used internally by verification algorithms is similarly sensitive for some applications, including the verification of signatures that are used as bearer tokens (i.e., authentication secrets) or signatures on plaintext messages that are intended to be confidential. Intermediate values of the verification algorithm may reveal information about its inputs (i.e., the message, signature, and public key), and in some applications, security or privacy requires one or more of these inputs to be confidential." — [FIPS 205 §3.1](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)
- "Verify uses only public data and makes no constant-time claim." — [fips205 README](https://github.com/integritychain/fips205/blob/main/README.md)
- pqc-forum, 20 February 2025: Derek Atkins asked why constant-time verification would matter given that verification handles no secret data; Bas Westerbaan replied that bounded verification time matters for real-time applications; Atkins clarified that he sees the need for bounded time but questions the need for constant time; Scott Fluhrer noted constant-time verification is straightforward but would roughly double verification time. (via page summary) — [pqc-forum thread](https://groups.google.com/a/list.nist.gov/g/pqc-forum/c/i38i7t950Cw)
- Variable-time root comparison in practice: "if (memcmp(root, pub_root, SPX_N))" — [sphincsplus ref/sign.c](https://github.com/sphincs/sphincsplus/blob/master/ref/sign.c); "ret = (memcmp(node, pk_root, n) == 0);" — [openssl slh_hypertree.c](https://github.com/openssl/openssl/blob/master/crypto/slh_dsa/slh_hypertree.c); "return memcmp(node, pk_root, config->n) == 0;" — [boringssl merkle.cc.inc](https://github.com/google/boringssl/blob/main/crypto/fipsmodule/slhdsa/merkle.cc.inc); "return memcmp(node, var->pk_root, prm->n) == 0;" — [slhdsa-c slh_dsa.c](https://github.com/pq-code-package/slhdsa-c/blob/main/slh_dsa.c)
- Verification-side values are the definition of "not secret" for the signer: non-secret values "are either values that are also computed by the verifier (and so the adversary has them), or internal nodes within a Merkle tree." — [Side Channel Resistant Sphincs+ (2024)](https://csrc.nist.gov/csrc/media/Events/2024/fifth-pqc-standardization-conference/documents/papers/side-channel-resistant-sphincs-plus.pdf)

### Inferences
- A constant-time theorem for the project can be scoped to key generation and signing. For verification the relevant properties are functional correctness and, if desired, a worst-case time bound; early-exit comparison of the root leaks only how many leading bytes of a (public) recomputed root match PK.root.
- The exception to record explicitly: if the deployment treats the signature or message as a secret (bearer-token use), verification timing reveals the same public-by-construction quantities as signing timing (md, indices, digits of the candidate PK_FORS and roots). That is an application-level confidentiality concern, not a threat to the signing key, and FIPS 205 addresses it only through data destruction.
- Key generation, unlike verification, does need the property: it runs PRF on SK.seed and all w−1 steps of every WOTS+ chain of the top XMSS tree, with a fixed, digit-independent amount of work.

### Gaps
- I found no academic paper stating "SLH-DSA verification need not be constant-time" in those words; the support is the standard's input list, implementation practice, the fips205 crate's statement and the mailing-list exchange.
- No source discusses timing of signature *parsing/rejection* paths (malformed-length signatures) as a concern; lengths are public.
