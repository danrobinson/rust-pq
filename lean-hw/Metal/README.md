# Metal key generation and signing

[CommandValues.lean](CommandValues.lean) composes the command epochs, typed signature layout and FIPS 205 pipeline model. For supported parameters, well-formed signing keys and a successful public signing batch, the result contains the FIPS signature of each request in order, with its context and supplied randomness. The theorem covers pooled buffers larger than the current output, an empty batch and context rejection. The host checker instantiates it for both XMSS modes on all twelve parameter sets. [Host traces and public wrappers](../../scripts/metal-command.py) · [FIPS pipeline model](Pipeline.lean)

The command-composition lemma takes a local value contract for each command. The generated public signing theorems below derive every such contract. Its premise says that if every region read by that command contains its intended values, the command produces the intended values in its own output regions. Host initialization has no inputs in the command graph. Each GPU input has exactly one writer in an earlier epoch. Induction on epochs then supplies the local premises without assuming that the returned buffer already contains a valid signature.

| Producer | Value checked |
|---|---|
| Host | Context guard and framing, argument order to the randomizer and digest routines, key packing, selected key, descriptor fields and offsets, randomizer prefix and returned slices. For the Apple build, fresh Rust extractions bind the custom SHAKE message functions to the verified Apple SHAKE256 sponge. Lean also checks SHA-2 randomness and message hashing with the Apple streaming implementation, context framing, digest coordinates, and all FORS indices. [Host preprocessing theorem](HostPreprocess.lean) · [Host source extraction](../../scripts/check-metal-host-hash.py) |
| WOTS chain tips, two-phase and streaming XMSS leaves | WOTS PRF and hash address at each step, chaining value, ordered chain tips, address encoding, all compression or permutation inputs, padding, output truncation and word order. |
| FORS passes and XMSS reduction | The leaf secret and its PRF/F domain, ordered children, absolute node index and height at every parent hash, sibling node values, subroot publication, final root and output serialization. |
| FORS public key | Ordered tree roots, full hash transcript and truncated result. |
| WOTS signature | Selected FORS root or preceding layer root, message and checksum digits, chain length, key and address, final serialized bytes. |

The [shader value checker](../../scripts/check-metal-values.py) uses production MSL function bodies and CBMC bitvectors. Key data, messages, target indices, descriptor fields and cryptographic outputs are symbolic. Hash comparisons check the bytes entering compression or permutation and allow arbitrary results, so the claims compose with the primitive implementations. At threadgroup barriers the checker supplies an arbitrary table of node words indexed by height, absolute node index and word number. Each producer must write the specified entry. The prior [barrier checker](../../scripts/check-metal-workgroups.py) establishes that all lanes have published the required entries before the next phase reads. The [address checker](../../scripts/check-metal-reads.py) and grid checks justify specializing active lanes to their row-major coordinates and rebasing accesses to the selected records.

For two-phase signing, Lean now derives the chain-tip command's local contract on every parameter set. The source checker translates the four dispatch index expressions and step count from each production kernel and checks the entire key-loading, short-hash loop and word-store bodies. Lean proves that, starting with arbitrary pool contents, every interleaving of the dispatched word stores produces the expected chain tips. The two-phase signing proof uses these published tips as the input to leaf compression. A changed chain-index operator and a broadcast of the first word are mutation controls for each family. [Executable chain dispatch and proof](ChainDispatch.lean)

Lean also derives the XMSS leaf producer’s contract for both modes on all twelve parameter sets. In two-phase mode, the compression pass reads the word buffer produced by the chain dispatch. The proof reassembles each chain and checks the sequence of SHA-256 words, SHA-512 word pairs or SHAKE lanes absorbed. In streaming mode, it constructs the same transcript directly from the chain loop. The 24 public theorem instances accept arbitrary store order and initial leaf-buffer contents. Mutating an output word or duplicating a stream input fails the source projection for each of the four kernel bodies. [Leaf dispatch and buffer composition](LeafDispatch.lean) · [Production shader projection](../../scripts/metal-proof/leaf_dispatch.py)

For both modes, the signature pool in the strongest public theorem is computed by the final WOTS command’s scattered byte stores over an arbitrary initial buffer. Lean proves that every WOTS address has a unique writer and that its byte matches the corresponding FIPS signature at the same batch, layer, chain and byte index. It checks the first-layer FORS key or preceding-layer XMSS root, the high and low nibbles, the three checksum digits, chain steps, and the SHA-2 big-endian or SHAKE little-endian output stores. The proof accepts every permutation of the submitted grid. [WOTS output proof](WotsOutput.lean) · [Shader projection](../../scripts/metal-proof/wots_output.py)

The FORS public-key command uses the same stream and word-buffer proofs. Lean reads its ordered tree roots from the pass-one buffer when the tree has one pass, or from the pass-two buffer when the tree is split. It proves that the resulting T hash is the FIPS FORS public key and that the WOTS kernel reads it from the actual published buffer. This contract is discharged in all 24 public instances. [FORS public-key proof](ForsPkDispatch.lean) · [Shader projection](../../scripts/metal-proof/fors_pk.py)

The modeled host initializer derives its key table, indices and descriptor values from the framed requests. Lean proves the first matching slot remains valid after subsequent unique keys are appended, including repeated-key batches. It replays the randomizer prefix copy into arbitrary pool contents and proves that subsequent non-randomizer stores and the final WOTS scatter preserve those bytes. The FORS and XMSS producers write to disjoint typed locations in the same pooled output. [Host values and randomizer preservation](HostValues.lean)

XMSS reduction reads the physical leaf-word buffer produced by the selected leaf kernel. The source projection distinguishes initial leaf reads from threadgroup reads after a barrier and preserves child ordering, address height and node index. Lean proves each active node, traces the root through its word buffer into WOTS signing, and traces each authentication byte through all later writes into the FIPS signature. [XMSS reducer](XmssDispatch.lean) · [Signature fields and scatter preservation](ReducerBytes.lean) · [Both shader projections](../../scripts/metal-proof/xmss_reducer.py)

The FORS passes start from the host descriptor’s key slot, tree and leaf addresses, and the message’s base-2ᵃ indices. The shader projection follows the two-leaf parity choice, child and sibling indices, lower and upper reduction levels, and the physical word reads between passes. Lean proves each final root word and signature byte. The one-pass kernel publishes its roots directly to the FORS public-key reader. For split trees, the second pass consumes the exact first-pass buffer. [FORS dispatch and signature proof](ForsDispatch.lean) · [Both shader projections](../../scripts/metal-proof/fors_reducer.py)

The source checker generates 24 public signing theorems named `*_signing_execution`, one for each parameter set and XMSS mode. Given the required output capacity and completed grids, the modeled host and shader writes produce the concatenated FIPS signatures for arbitrary requests, initial pool bytes and permitted store orders. Lean also checks the public rejection path for an oversized context. For each instance, a second theorem named `*_canonical_fips` constructs the grids and exact output capacity and proves the same public result with no execution hypotheses. This includes empty batches. FORS and XMSS stores, including writes from threadgroup memory, execute the family’s word-to-byte serialization in the final pool. The checker audits the complete axiom closure of each generated headline theorem. [Canonical schedule construction](SigningSchedule.lean)

All command values are derived. The grid premises cover all scheduled word and signature-byte stores, including the unique writers of the intermediate signature fields.

Key generation replays the extracted keygen command sequence, including the host’s final root read. Lean checks the returned keypair for each batch element, the single-key seed slices and the key packing order for all twelve sets in both modes. The arbitrary-schedule theorem permits different initial buffer contents, and the canonical theorem constructs a complete grid. The big-endian SHA-2 and little-endian SHAKE readback helpers, slice strides, singleton wrappers and typed API routing are checked against Rust. [Key generation dispatch](KeygenDispatch.lean) · [Host readback checker](../../scripts/metal-proof/keygen_output.py)

For each named set Lean also checks the runtime choice between the streaming and two-phase grids, including an override of the default leaf threshold. After the submitted command returns, Rust reads the buffers only on success. The Objective-C bridge tests the driver status after its wait and propagates an incomplete or failed command as an error. Lean proves every successful public batch return equals FIPS and covers the empty-batch and context-rejection early returns. The bridge source check follows each null guard from context, pipeline and shared-buffer creation through command-buffer and encoder creation. A generated Lean theorem characterizes a successful read for arbitrary lists of pipeline and allocation attempts, using the observed availability of Objective-C handles and completed status. Error classification abstracts the diagnostic text. [Completion and return semantics](Completion.lean) · [Mode selection and public outputs](../../scripts/metal-proof/completion.py)

The internal signing API processes the caller’s exact message bytes. Its proof instantiates the same command producers and pooled readback directly on these inputs. The typed wrappers then cover single hedged signing, deterministic signing using PK.seed, and common-key batches with supplied or deterministic randomness. Common-context batches reject an oversized context even for an empty message list. Rust’s equal-length precondition applies when messages and randomness are passed as separate lists. For typed keygen, Lean proves the returned vectors fit their fixed 4n- and 2n-byte arrays. [Raw-message signing](InternalSign.lean) · [Public signing wrappers](PublicSignatures.lean)

The hash boundaries use specification PRF, F, H and T with native words represented by their serialized bytes. The separate shader and primitive checkers check their input conventions, including the precompressed SHA-2 seed state. Applying the public theorem to a device requires faithful source projections and compilation, valid representable counts and offsets, correct buffer binding and lifetime, coherent memory, and successful dispatch and synchronization. Native signature comparisons exercise finite vectors.

Run from the repository root with CBMC installed or `CBMC` set to its executable.

```sh
python3 scripts/check-metal-kernels.py
python3 scripts/check-metal-values.py
cargo test --release --manifest-path metal/Cargo.toml --test metal_verify
uv run --script scripts/check-metal-reads.py
uv run --script scripts/check-metal-workgroups.py
```
