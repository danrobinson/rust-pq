# multi/ — constant time: what is proved (2026-11-22)

For the portable (default) build of `multi/rust`, all six SHA-2 parameter sets, the Lean
library [lean/Ct](lean/Ct) proves the statements of the main tree's
[../lean/CT_STATUS.md](../lean/CT_STATUS.md): key generation leaks nothing, each signer's
trace is a simulator's on public inputs, verification's inputs are all public, SHA-256 and
SHA-512 traces depend only on the length, and the key codecs leak only lengths (and, when
decoding, the position where the input leaves the fixed DER prefix). Build it with

```
cd multi/lean && lake build Ct
```

The `hw-sha2` build (`multi/lean-hw`) and `hw-sha512` are not covered.

## Same model, same machinery

The leakage model is the main tree's: the same events (`Ct/Leak.lean`, linked), the same table
of instrumented primitives (`Ct/Model.lean`, linked), the same `do` elaborator (`Ct/Do.lean`,
linked), the same checker. The instrumented program [lean/Ct/Funs.lean](lean/Ct/Funs.lean) is
generated from the verified translation `lean/Slhdsa/Funs.lean` by
[scripts/ct-gen.sh](scripts/ct-gen.sh) (adapted from `../scripts/ct-gen.sh`, which is
unchanged): only the header and the final `end` change, and the script checks that the body is
byte-for-byte the source's. Then

* `Ct/Check.lean`: all 480 definitions of `Ct.Funs` use only instrumented primitives and
  whitelisted non-leaking operations;
* `Ct/Erase.lean`: 441 erasure theorems (`slhdsa_leak.f.erase_eq`), one per function and
  constant of `Slhdsa/Funs.lean`, 0 failures.

What this translation needed beyond the main tree's model, all of it in this tree's files:

* **One instrumented primitive** ([lean/Ct/ModelBuild.lean](lean/Ct/ModelBuild.lean)):
  `core.slice.index.Slice.index_mut`, a mutable sub-slice of a *slice* (`&mut sk[a..b]` on the
  key buffers the generic key generation writes into, and in `der_encode`). It emits what the
  read-only `core.slice.index.Slice.index` of `Ct/Model.lean` emits: the range and the slice's
  length. (`Ct/CheckTestBuild.lean` checks the name resolves to it and that the
  un-instrumented one is rejected.)
* **Five whitelist entries** ([lean/Ct/Check.lean](lean/Ct/Check.lean), a copy of the main
  tree's checker with the entries marked `[multi]` and their reasons written there):
  `core.num.U64.wrapping_add` and `core.num.U64.rotate_right` (SHA-512's 64-bit counterparts
  of the 32-bit `wrapping_add` / `rotate_right` already listed; constant rotation amounts),
  `core.num.U64.MAX` (a constant, shifted by the public tree height in `digest_tree`), and
  `U128.ofNat` / `UScalarTy.U128` (the literal `8#u128` and the cast target of SHA-512's
  128-bit length field `(len as u128) * 8`). None branches, indexes or divides. Division and
  remainder on every width, including `u128`, still go only through the leaking instances
  (`Ct/CheckTestBuild.lean` has a positive control for a `u128` division).

The checker accepted everything else unchanged: no branch, index, length or division of the
generated text escaped the model.

## The theorems

Generic, for every `p` with `PN p N` (`(paramsS p).Valid ∧ p.n = N`, as in the functional
theorems): the relational lemmas of every function (`Ct.Hash.*`, `Ct.Fors.*`, …, with `N`, `p`
and lengths shared by the two runs and seeds, states, blocks and messages separate), the
simulators `slhdsa_leak.Sim.signInternal N p pk m sig` (and `signInternalChecked`, `sign`,
`signChecked`, `signDeterministic`, `signDeterministicChecked`), the simulation theorems
`Ct.Sign.sign_internal`, `sign_internal_checked`, `slh_sign`, `slh_sign_checked`,
`api_sign`, `api_sign_checked`, `api_sign_deterministic`, `api_sign_deterministic_checked`,
`slh_sign_long_ctx`, `api_long_ctx`, and `Ct.Theorems.generic.keygen_internal_ct`,
`keygen_internal_trace`, `keygen_ct`.

Per set, in `Ct/Sets/Sha2_<set>.lean`, namespace `Ct.Theorems.sha2_<set>`: the 15 per-set
statements of `../lean/Ct/Theorems.lean` (`keygen_internal_ct`, `keygen_internal_trace`,
`keygen_ct`, `keygen_trace`, `sign_simulated`, `sign_deterministic_simulated`,
`sign_checked_simulated`, `sign_deterministic_checked_simulated`, `slh_sign_simulated`,
`slh_sign_checked_simulated`, `slh_sign_internal_simulated`,
`slh_sign_internal_checked_simulated`, `sign_long_context`, `sign_two_runs`, `verify_ct`)
and the 11 of `../lean/Ct/Encoding.lean`, about the set's wrappers `sets.sha2_<set>.*` (the
functions with fixed-size key types). The 16th, `sha256_trace_eq`, does not depend on the set
and is stated once in `Ct/Theorems.lean`, with the new `sha512_trace_eq`. The per-set
simulators `slhdsa_leak.Sim.sha2_<set>.*` are the generic ones at the set's `N` and
`PARAMS`; they are given the public key, the message, the context and the signature only.

SLH-DSA-SHA2-128s, `lean/Ct/Sets/Sha2_128s.lean` lines 134–139 (the other signers follow the
same pattern):

```lean

    (slhdsa_leak.Sim.sha2_128s.sign pk m ctx sig.deref).run = .ok ((), t)
```

### Against the main tree's statements

* The Rust functions are this crate's per-set wrappers (`sets.sha2_128s.sign` for `api.sign`,
  `sets.sha2_128s.slh_sign` for `slh.slh_sign`, …), and `hpk` uses this crate's
  `sets.sha2_<set>.public_key`.
* The message-length hypotheses are the functional theorems' of this tree: `Room m.length 409`
  / `152` for the n = 16 sets (the main tree's numbers) and `561` / `304` for n = 24, 32
  (SHA-512 for `H_msg` and `PRF_msg`). No other hypothesis.
* The simulators of a set take exactly what the main tree's take (pk, m, ctx, sig); they are
  defined through the generic simulators, which also take `N` and `p` (public).
* `sha256_trace_eq` is stated once (it does not depend on the set); `sha512_trace_eq` is new.
* PKCS#8 decoding: the fixed prefix is 20 bytes (n = 16, 24) or 22 bytes (n = 32), and the
  hypothesis is `der.val.take 20` / `take 22` accordingly; SPKI: 18 in every set.
* The generic statements carry, in addition, `PN p N`, the key-slice length `4N` and
  `pk.val = sk.val.drop (2N)` (what the per-set `public_key` gives), and for key generation the
  equality of the output buffers' lengths.

## Axioms

Every `#print axioms` in `Ct/Theorems.lean` (15) and `Ct/Sets/*.lean` (26 each, 156 in all):
`[propext, Classical.choice, Quot.sound]`. No `sorry`, `axiom`, `native_decide` or
`bv_decide` under `lean/Ct`.

## Findings about the Rust code

Nothing of `multi/rust`'s portable build branches, indexes, sizes an allocation or a copy, or
divides on a secret: the relational lemmas hold with every seed, SHA-256/SHA-512 state, block,
node value and message treated as secret except for lengths. The new control flow is on public
data only, as `multi/STATUS.md` says: `N == 16` (both runs share `N`), fields of `Params`, and
lengths and ranges of the `LEN_MAX`/`K_MAX` arrays (`blocks[0..2N+3]`, `[0..k]`), which do
appear in traces and are why the simulators are given `p`. Two facts carried over unchanged from
the main tree: the checked signer compares roots with array `==`, so a run that returns
`none` after a failed recomputation reveals the common prefix of the two roots (no claim is
made about such runs); `der_decode` returns at the first byte that differs from the (public)
prefix. The generic functions' traces also depend on the lengths of the caller's key buffers;
the per-set wrappers fix them.

## Not done

* `hw-sha2` build (`multi/lean-hw`): no instrumented copy, no proofs (its chain kernel's
  statement would need the `HeadsEq` precondition that `Ct.Hash.chain_blocks` keeps).
* `hw-sha512`: not translated.
* Everything listed under "What this does not cover" in `../lean/CT_STATUS.md` (compiler,
  processor, faults, erasure) applies here unchanged; no binary-level evidence was collected
  for this tree.
