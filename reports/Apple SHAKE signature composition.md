# Successful Apple SHAKE signatures

For 128s, 128f, 192s, 192f, 256s and 256f, Lean proves that a successful signer trace satisfying the specified call and return equations produces exactly the bytes of FIPS 205 `slhSignInternal`. For a context of at most 255 bytes it also proves equality with `slhSign`. The wrapper theorem covers both caller-supplied randomness and the deterministic choice of the public seed. These are the statements `supported_internal_eq`, `supported_pure_eq` and `supported_wrapper_eq`. [Composition theorems](../lean/Spec/AppleSignerComposition.lean) · [FIPS specification](../lean/Spec/SlhDsa.lean)

### What Lean composes

The witness `Signature` contains the observed randomizer, digest, FORS signature, recovered FORS public key, and per-layer XMSS signatures and intermediate roots. The hypotheses constrain the calls made on this particular signing input. The checker can give arbitrary values to intermediate buffers whose contents are never used.

* The randomizer and message digest use the correct secret-key components, randomness, message and output length. The Lean sponge expression uses the checked-in Apple Keccak permutation witness and reduces to FIPS 202 SHAKE256.
* The digest determines the FORS selections, hypertree index and leaf index. FORS rows contain the selected secret followed by the sibling block for each height. Recovery climbs the corresponding authentication paths and hashes the ordered roots at the FORS-roots address.
* For each XMSS signature, an inductive node equation connects WOTS leaves and ordered child hashes to the specified subtree root. The proof combines each authentication block with the observed WOTS signature. XMSS recovery starts with the WOTS-recovered leaf and proves the correct address and child order at each path height.
* At every hypertree layer, the signature bytes are appended and the tree and leaf indices advance. The next message comes from XMSS recovery only if another layer remains. Lean proves that keeping the current message at the final layer gives the same complete signature as `Spec.htSign`. The top-level proof then checks the concatenation of randomizer, FORS signature and hypertree signature.
* The context wrapper supplies the byte `0x00`, the one-byte context length, the context, and the original message. The deterministic path chooses the third `n`-byte block of the secret key as its randomness input.

The native checks use several representations of the same data, including flat signature bytes, Rust vectors, native address structures, register values and logical byte lists. The program-specific Python checks and SMT proofs establish individual caller and callee equations in these representations. Lean checks the mathematical consequences when those equations describe one trace. There is currently no Lean construction that takes the starting Mach-O bytes and ABI state, runs the complete AArch64 semantics and constructs a value of `Signature` for that execution. The checked-in Keccak and rate-block byte witnesses give a closer instruction-level connection for those kernels.

### Assumptions on the native claim

The native result concerns successful executions with valid keys and input slices, enough space for framing and all intermediate allocations, a conforming allocator and memory primitives, and the specified Arm ISA and ABI. It assumes the loader preserves the measured code and constants. Several gates use representative disjoint virtual addresses and abstract callee clobber sets. A universal proof for all valid address placements would also need a memory refinement result showing that each callee's layout, aliasing, ownership and liveness preconditions follow at every call. The external checkers, disassembler/lifter and SMT solver remain part of the trusted software for the machine-level claim. Execution of panic paths, faults and physical leakage require separate evidence.

### Nonvacuity and native checker controls

For each standardized SHAKE set, `LinkedArm.Signer.trace_iff` establishes that the mathematical trace has a witness exactly when its output equals `Spec.slhSignInternal`. The reverse direction constructs every intermediate node, path and layer from the reference algorithm for arbitrary input bytes. This rules out inconsistent trace premises. The separate task of constructing that witness from execution of a linked binary still requires a native semantics and memory refinement. Run `lake build Spec.AppleSignerComposition` from the Lean directory. All five axiom reports list only `propext`, `Classical.choice` and `Quot.sound`.

An independent replay tightened the XMSS result bounds to exactly one node, checked signing-driver copy source and destination liveness, checked callee output buffers against the active stack, and checked that the tree-hash terminal covers the whole symbolic input domain. In particular the old access guard admitted a write to bytes 16–23 after a 16-byte XMSS output. The fixed checker rejects that access and a read past the message. These were changes to the proof harness. All 24 linked SHAKE driver entry/set combinations, all six SHA-2 internal drivers, and the tree-hash, XMSS signing and recovery, keygen and verification gates replayed on the measured image. The five driver instruction-mutation controls also failed as intended.

`scripts/linked-signer/audit_contracts.py` runs memory-region controls and checks the three supplemental VEX bitvector operations against independent bit selection and byte-index equations. The shift test covers all 256 low-byte counts in each lane, arbitrary high count bits and arbitrary 128-bit operands. Run it with the dependencies pinned in `scripts/linked-signer/driver.py`. The checks validate the registered operations against these equations. The translation of an AArch64 instruction to its VEX operation remains trusted.
