# Linked SLH-DSA signer verification

The extracted Rust has Lean proofs against the executable FIPS 205 specification. The recorded Apple arm64 release ACVP consumer from revision `74b1b3e` also has checks that start at public signing entries, execute actual instructions and inspect the bytes returned to the caller. Lean also composes key generation, signing and verification traces for all twelve SHAKE and SHA-2 sets. The session theorem proves both existence and uniqueness of the observable results under the mathematical call equations. For arbitrary seeds of the specified lengths, a message, a valid context and randomness, the resulting keys and signature equal their FIPS definitions and the verifier accepts. For arbitrary signature bytes it separately proves that the observed verdict matches FIPS, including rejection. The strongest combined theorem compares the public executable model directly with the public Rust functions for all twelve sets. For the same inputs, both key buffers and every byte of the returned signature vector agree. Each side passes its own signer’s output to its own verifier and returns true. The theorem covers deterministic and supplied randomness, public aliases and the modeled successful allocation paths. Native cryptographic calls use reference implementations of their local contracts. [Public Rust-to-binary agreement](../lean/Facade/ApplePublicAgreement.lean)

The twelve public session theorems run the crate's actual `sets::<profile>::keygen`, `sign` or `sign_deterministic`, and `verify` functions from the Rust extraction. They use arbitrary initial output buffers, pass the returned signature vector to the verifier and prove that the full tuple of keys, signature bytes and verdict is exactly the FIPS session. Each profile theorem discharges its own parameter and array-size obligations. [All twelve public API sessions](../lean/Facade/PublicSession.lean)

The source-level theorem `extracted_session` starts with three seeds and caller-provided output buffers. It executes the extracted Rust keygen adapter, passes its returned secret key to the signer and passes that signature and the returned public key to the verifier. It proves that each call returns successfully and that their outputs give a complete FIPS session. It covers deterministic and supplied randomness for all twelve parameter sets, under their slice lengths, valid context and message arithmetic bounds. For arbitrary submitted signature bytes, a second theorem identifies the actual verifier return with the trace verdict. On oversized contexts the verifier returns false and the signer returns the original destination buffer. The Lean axiom audit lists `propext`, `Classical.choice` and `Quot.sound`. The Rust-to-Lean translation remains trusted. [Extracted Rust session](../lean/Facade/EndToEnd.lean)

For the measured Apple executable, `LinkedArm.NativeSession.run_eq` composes actual keygen, internal signing and internal verification driver replays on all twelve SHAKE and SHA-2 sets, including both keygen ABIs and four successful allocation profiles. From arbitrary correctly sized seeds and randomness and an arbitrary message, the restricted interpreters with reference cryptographic callees return the FIPS keys, the exact FIPS signature and `true`. The companion `internal` theorem permits any callee implementations satisfying the checked local equations. For arbitrary submitted signatures the native verifier has independent correct- and wrong-length proofs. The model uses fixed disjoint memory regions and contracts for successful calls. The deeper native component checks use separate semantics and SMT. ## Current Apple arm64 release consumer

A locked release build of the ACVP test executable with Rust 1.100.0, `platform-sha2` and Rust source tree `fca56bbd2c46fea8294b51292a050f96bb7adb0e` produced SHA-256 `9fd48af0eb2f4990e5e764d997d9be21a0500c324ff06de6baf9003d4bd092fc`. For each of its twelve parameter sets, Lean follows the actual `sign`, `slh_sign` and `sign_deterministic` instructions on every 64-bit context length greater than 255. It checks the caller-visible None discriminator, destination writes, deterministic key reads and restoration of the return address, stack and preserved registers. The model allows a 4 KiB valid stack region and separate key and return buffers. A linked caller independently identifies the return discriminator. [Current instruction witnesses](../lean/Spec/ApplePublicRejectWitness.lean) · [Executor for indexed stack operations](../lean/Spec/ArmPublicReject.lean)

For all twelve `slh_verify_internal` entries in that same file, Lean checks the parameter record and the length comparison. Every representable signature of the wrong length returns false. On the valid-length path, Lean checks that the first call to `H_msg` receives the randomizer and the two public-key components in the correct order. The full arbitrary-signature verdict and successful signing paths still need machine-code proofs for this executable. [Length and message-hash argument semantics](../lean/Spec/ArmVerifyLength.lean)

For all twelve sets, Lean also executes both public key-generation entries through normal return. The driver reads the actual parameter record and constructs both the private and public keys from three arbitrary `n`-byte seeds and the computed root. The SHAKE driver calls the linked batched subtree routine with height `h′`, index zero and layer `d−1`. The SHA-2 driver uses the linked XMSS routine's explicit output argument. Lean checks these call arguments, the returned root's placement, every byte of both keys, and register and stack restoration. These are driver proofs with the FIPS result supplied at the subtree boundary. SHA-2 also uses a local seed-context contract, including the relocated inline SHA-256 region for its 128-bit sets. [Successful key-generation witnesses](../lean/Spec/ApplePublicKeygenWitness.lean) · [Callee conventions and key bytes](../lean/Spec/ArmPublicKeygen.lean)

Run `python3 scripts/apple-binary/current_keygen.py --require-recorded` and `python3 scripts/apple-binary/current_rejection.py --require-recorded` on Apple arm64 to rebuild the consumer and compare the generated proof input with the checked-in witness. Passing a path checks another executable against the same properties. Omit `--require-recorded` to accept a different image after Lean checks fresh witnesses. The comparison includes the file hash and each extracted instruction word.

## Artifact, assumptions and replay

The full session theorem above uses the executable built from revision `74b1b3e` with Rust 1.100.0 and the crate's `platform-sha2` feature. Its file SHA-256 is `ab672dc82d293ec220beb29f475bedda4614d59c76636cd16edef18705e1ac0a`. A downstream application can produce different instructions. The Apple gates require an unstripped thin arm64 image with the expected symbols. The release build and the existing Linux artifact checks are described in the [platform verification report](SHAKE%20and%20linked%20binary%20verification.md).

Run the combined replay from the repository root with Apple command-line tools, uv, Rust and the repository’s Lean dependencies available. It takes a private snapshot of the supplied binary and runs each checker against the same bytes. The individual checks remain independently runnable.

```sh
scripts/extract.sh --check
python3 scripts/check-linked-consumer.py /path/to/acvp --self-test --require-session-image
```

The November 23 replay regenerated the Rust functions and types byte-for-byte, matched the native witnesses to the recorded Mach-O, and passed the combined symbolic checks with instruction mutations enabled. The public agreement target passed its kernel axiom audit for all twelve sets. Separately, the release tests passed 53 ACVP cases and 36 RustCrypto interoperability cases, and the peer proof replay checked 24 typed and wire equalities on each of the three target configurations.

The linked-signer checks trust their Python specifications, Mach-O parsing, the AArch64 instruction lifter, symbolic executor and SMT solver. An equality check asks whether any input consistent with that path makes the expressions different. Unresolved control transfers, inaccessible memory under the region model, a missing terminal path or an exceeded execution bound fail the gate. The driver checks mutation controls for the PRF key, digest and radix shifts, hypertree index update and returned length. The XMSS check mutates the recursive height and child ordering. These are solver-based checks. The instruction-level rejection witness and the separately identified Lean theorems replay in the Lean kernel.

The model uses fixed disjoint addresses for code, a writable stack, keys, results and fresh allocations. It assumes successful allocation, normal return, a valid nonwrapping input slice and enough space for a framed message. It models capacity bounds and the effects of growth, copy and deallocation. It allows arbitrary sufficient final-signature capacities within the modeled allocation size and uses the modeled growth policy for the inner vectors. The modeled calls may clobber scratch registers and use the recorded return convention for the link register. The message is an opaque slice in the signing-driver check. The framing check establishes its byte layout separately. Allocation failure, panic unwinding, arbitrary virtual address placements, loader behavior, hardware faults and physical leakage fall outside these checks.

An unconditional native result still needs a composition proof for the remaining native callees and the memory/runtime model. For SHAKE, the component checks reach the single- and double-state Keccak routines. The native proof still needs to derive each callee’s preconditions at every call from a common machine state and construct the mathematical trace from those executions. For SHA-2 the batched chain proof covers both WOTS bounds and the independent one-round indices at the FORS calls. Both SHA-2 internal drivers now construct traces in Lean. Their component contracts still need to be discharged in the same full-machine semantics as their callers. The long-message SHA-2 signing and verification paths have their own driver proofs. Their segmented HMAC and message hash calls share the remaining component and runtime assumptions. Additional facade and DER operations have separate native bodies. The Linux release checks cover selected primitives. No whole-binary theorem currently identifies all native library operations with RustCrypto or OpenSSL.
