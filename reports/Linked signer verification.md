# Linked SLH-DSA signer verification

The extracted Rust has Lean proofs against the executable FIPS 205 specification. The linked Apple arm64 release ACVP consumer also has checks that start at public signing entries, execute actual instructions and inspect the bytes returned to the caller. A proof that every instruction of the compiled signer implements FIPS 205 remains open. The table identifies where each check stops. The result comparison uses independently symbolic bytes from each signing operation, so it detects a misplaced or omitted byte even when the final length agrees. The linked base conversion runs both times it is called and its output is checked against slices of the original symbolic digest. [Driver](../scripts/linked-signer/driver.py)

## Artifact, assumptions and replay

The measured consumer was linked with Rust 1.100.0 and the crate's `platform-sha2` feature. Its file SHA-256 is `ab672dc82d293ec220beb29f475bedda4614d59c76636cd16edef18705e1ac0a`. A downstream application can produce different instructions. The Apple gates require an unstripped thin arm64 image with the expected symbols. The release build and the existing Linux artifact checks are described in the [platform verification report](SHAKE%20and%20linked%20binary%20verification.md).

Run from the repository root with Apple command-line tools, uv, Rust and Lean available. Supply the same binary to each check.

```sh
python3 scripts/apple-binary/check.py /path/to/acvp --self-test
uv run --python 3.12 --script scripts/linked-signer/driver.py /path/to/acvp --self-test
uv run --python 3.12 --script scripts/linked-signer/keygen.py /path/to/acvp --self-test
uv run --python 3.12 --script scripts/linked-signer/verify.py /path/to/acvp --self-test
python3 scripts/apple-binary/check_digest.py /path/to/acvp --self-test
uv run --with z3-solver==4.15.4.0 python scripts/apple-binary/absorb.py /path/to/acvp --self-test
uv run --python 3.12 --script scripts/linked-signer/xmss_node.py /path/to/acvp --self-test
```

The linked-signer checks trust their Python specifications, Mach-O parsing, the AArch64 instruction lifter, symbolic executor and SMT solver. An equality check asks whether any input consistent with that path makes the expressions different. Unresolved control transfers, inaccessible memory under the region model, a missing terminal path or an exceeded execution bound fail the gate. The driver checks mutation controls for the PRF key, digest and radix shifts, hypertree index update and returned length. The XMSS check mutates the recursive height and child ordering. These are solver-based checks. The instruction-level rejection witness and the separately identified Lean theorems replay in the Lean kernel.

The model uses fixed disjoint addresses for code, a writable stack, keys, results and fresh allocations. It assumes successful allocation, normal return, a valid nonwrapping input slice and enough space for a framed message. It models capacity bounds and the effects of growth, copy and deallocation. It allows arbitrary sufficient final-signature capacities within the modeled allocation size and uses the modeled growth policy for the inner vectors. Callees may clobber ABI scratch registers. The message is an opaque slice in the signing-driver check. The framing check establishes its byte layout separately. Allocation failure, panic unwinding, arbitrary virtual address placements, loader behavior, hardware faults and physical leakage fall outside these checks.

An unconditional native result still needs a composition proof for the remaining native callees and the memory/runtime model. Each remaining primitive contract in the public key-generation and verification paths also needs a native proof. Context-taking verification and other facade operations have additional native bodies to check. The Linux release checks cover selected primitives. No whole-binary theorem currently identifies all native library operations with RustCrypto or OpenSSL.
