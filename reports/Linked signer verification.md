# Linked SLH-DSA signer verification

The extracted Rust has Lean proofs against the executable FIPS 205 specification. The linked Apple arm64 release ACVP consumer also has checks that start at public signing entries, execute actual instructions and inspect the bytes returned to the caller. Lean also composes key generation, signing and verification traces for all twelve SHAKE and SHA-2 sets. The session theorem proves both existence and uniqueness of the observable results under the mathematical call equations. For arbitrary seeds of the specified lengths, a message, a valid context and randomness, the resulting keys and signature equal their FIPS definitions and the verifier accepts. For arbitrary signature bytes it separately proves that the observed verdict matches FIPS, including rejection. ## Artifact, assumptions and replay

The measured consumer was linked with Rust 1.100.0 and the crate's `platform-sha2` feature. Its file SHA-256 is `ab672dc82d293ec220beb29f475bedda4614d59c76636cd16edef18705e1ac0a`. A downstream application can produce different instructions. The Apple gates require an unstripped thin arm64 image with the expected symbols. The release build and the existing Linux artifact checks are described in the [platform verification report](SHAKE%20and%20linked%20binary%20verification.md).

Run the combined replay from the repository root with Apple command-line tools, uv, Rust and the repository’s Lean dependencies available. It takes a private snapshot of the supplied binary and runs each checker against the same bytes. The individual checks remain independently runnable.

```sh
python3 scripts/check-linked-consumer.py /path/to/acvp --self-test
```

The linked-signer checks trust their Python specifications, Mach-O parsing, the AArch64 instruction lifter, symbolic executor and SMT solver. An equality check asks whether any input consistent with that path makes the expressions different. Unresolved control transfers, inaccessible memory under the region model, a missing terminal path or an exceeded execution bound fail the gate. The driver checks mutation controls for the PRF key, digest and radix shifts, hypertree index update and returned length. The XMSS check mutates the recursive height and child ordering. These are solver-based checks. The instruction-level rejection witness and the separately identified Lean theorems replay in the Lean kernel.

The model uses fixed disjoint addresses for code, a writable stack, keys, results and fresh allocations. It assumes successful allocation, normal return, a valid nonwrapping input slice and enough space for a framed message. It models capacity bounds and the effects of growth, copy and deallocation. It allows arbitrary sufficient final-signature capacities within the modeled allocation size and uses the modeled growth policy for the inner vectors. The modeled calls may clobber scratch registers and use the recorded return convention for the link register. The message is an opaque slice in the signing-driver check. The framing check establishes its byte layout separately. Allocation failure, panic unwinding, arbitrary virtual address placements, loader behavior, hardware faults and physical leakage fall outside these checks.

An unconditional native result still needs a composition proof for the remaining native callees and the memory/runtime model. For SHAKE, the component checks reach the single- and double-state Keccak routines. The native proof still needs to derive each callee’s preconditions at every call from a common machine state and construct the mathematical trace from those executions. For SHA-2, deeper WOTS chaining and FORS subtree and recovery contracts also require native evidence. Additional facade and DER operations have separate native bodies. The Linux release checks cover selected primitives. No whole-binary theorem currently identifies all native library operations with RustCrypto or OpenSSL.
