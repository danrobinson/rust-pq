# SHAKE and linked binary verification

## The six SHAKE sets

The proofs apply to 128s, 128f, 192s, 192f, 256s and 256f. Three properties answer different questions about the signer.

| Property | What the proof establishes | Boundary |
|---|---|---|
| Functional correctness | The extracted implementation produces the FIPS 205 keys, signatures and verification verdicts, including the optimized hypertree signing logic. | Rust translation, the formal specification and the stated platform primitive and input assumptions. [Public API proofs](../lean/Facade.lean) |
| Classical unforgeability | A successful forger against the internal or pure byte-string scheme yields adversaries against named component properties. Lean specializes ordinary and strong chosen-message forgery bounds to the six executable SHAKE components and proves the scheme-to-game correspondences. | The remaining advantage terms are cryptographic assumptions. Their values for SHAKE256 and quantum-query security require separate arguments. [Concrete components](../security/MLink/ShakePrimitives.lean) · [Extracted Rust correspondence](../security/ME2E/ShakeRust.lean) · [Bounds](../security/MReduction/Shake.lean) |
| Source leakage | Key generation has an identical trace across seeds. A simulator given the public key, message, context and published signature reproduces the successful hedged or deterministic signing trace. The proofs cover arbitrary-length streaming SHAKE, the fixed-size key APIs and DER operations. | Default and `hw-sha2` extracted configurations. The events include branches, indices and copy lengths. DER decoding allows disclosure of public header mismatches. The separately compiled compatibility facade and accelerated `platform-sha2` signer need their own leakage proofs. [Trace statements and model](../lean/CT_STATUS.md) |

In a separate classical ideal model, Lean proves query-bounded internal forgery estimates when the underlying byte-string oracle is uniformly random. Answering the same model's queries with concrete SHAKE256 yields the implementation's internal scheme, including the prefix relationship between different XOF output lengths. The numerical ideal bounds apply to the random oracle. The concrete reduction retains its twelve advantage terms. [Ideal bounds](../security/MReduction/ShakeIdeal.lean) · [Concrete oracle correspondence](../security/MReduction/ShakeOracle.lean)

The internal Rust correspondence accepts every representable message slice with correctly sized keys. The pure context-bearing operations have the arithmetic room assumption stated in their theorems. [Rust theorem statements](../security/ME2E/ShakeRust.lean)

## Evidence from linked executables

The [linked signer verification report](Linked%20signer%20verification.md) records the later checks from Apple signing entries through return, including the per-layer SHAKE data flow, and lists the remaining callee contracts.

The crate distributes Rust code. Downstream linking selects and can transform the final machine code. For this audit we used the ACVP test consumer and benchmark consumer, linked into three executables in release mode with `platform-sha2` from library revision `74b1b3e`. Each checker reads the final file, identifies the code and constants, checks them and reports the complete file's digest. A new deployment needs a replay against its own artifact.

The machine-code results assume that the loader preserves the measured bytes, that the CPU implements the modeled ISA and enabled features, and that pointers, stack, alignment and non-aliasing satisfy the function's ABI. The Apple gate also trusts the Mach-O reader, LLVM disassembly for the SHA-2 and hypertree checks, and the restricted Python checkers. The mathematical certificates are checked by Lean. Whole-program dispatch, other machine-code routines, allocator/runtime behavior, speculation, physical timing and fault resistance remain open.

## Replaying the checks

On Apple Silicon, with the repository's Lean and Rust dependencies and the Apple command-line tools installed, run from the repository root:

```sh
python3 scripts/apple-binary/check.py --self-test --certificate /tmp/LinkedArm.lean
```

The public signing rejection witness replays with `cd lean && lake build Spec.AppleSignRejectWitness` and checks four mutations of the threshold, output address, restored register and key read. The inductive sponge checker uses the peer proof's Z3 dependency. Replay it with `uv run --with z3-solver==4.15.4.0 python scripts/apple-binary/absorb.py --self-test` on the same Apple build, or supply the executable path. The checked-in round witness can also be replayed on any supported Lean host with `cd lean && lake build Spec.AppleKeccakWitness Spec.AppleRateBlocksWitness`. The Apple checker builds the locked release ACVP consumer by default. To check a different unstripped thin Apple arm64 executable with the supported routines and instruction schedules, pass its path as the positional argument. Three whole-rate-block controls change a message address, the inner loop back edge, and output packing. The seven other image mutation controls change a SHA3 rotation, the Keccak loop back edge, the wrapper's direct call, a round constant, a SHA-256 round instruction, a public keygen buffer length and the hypertree's final recovery guard.

For an x86-64 Linux release consumer, including a stripped ELF with suitable unwind metadata:

```sh
uv run --script scripts/test-keccak-elf.py /path/to/consumer
```

For a Linux AArch64 release consumer, with the Rust AArch64 Linux target and an AArch64-capable Clang assembler installed:

```sh
uv run --script scripts/check-arm-sha2-elf.py --negative-controls /path/to/consumer
```

The x86 checker rejects four independent byte mutations. The recorded Apple file SHA-256 is `ab672dc82d293ec220beb29f475bedda4614d59c76636cd16edef18705e1ac0a`. The Linux x86-64 stripped file SHA-256 is `d0684e30aa7e85cc8c7229cd5da885ae7f9eb6d9c857d01363b90f993c330c69`. The Linux AArch64 stripped file SHA-256 is `4b84c1a3a0dcd701e837bc09c7b70ccff0c7774a24f13040cede8bc44e50346b`. Its checker builds the locked dependency’s release assembly or accepts a supplied copy. It rejects six mutations across the two compressors. All three executables were built with Rust 1.100.0. As a separate runtime check, the measured Apple executable passed all 53 ACVP test groups, and the matching release RustCrypto interoperability target passed all 36 test groups.
