# Proving SLH-DSA leaks only public data

**The proof is a trace theorem over a leakage-instrumented copy of the Aeneas model.** Every branch, every array or slice index and length, and every division operand emits an event; the instrumented copy is proved to erase to the already-verified program; and the trace of key generation and signing is proved equal to an explicit function of what a verifier already holds: the public key, message, context and the signature itself. This is cryptographic constant-time exactly as ct-verif, Jasmin, HACL\*, Vale and CompCert-CT define it, stated in the single-run form Bedrock2 uses and with the public-output declassification that SLH-DSA cannot do without, because R, the FORS public key and the XMSS roots are computed from secrets and then steer WOTS+ chain lengths, FORS leaf indices and tree paths. **No such proof exists in Lean 4 or on Aeneas output today**: Microsoft's SymCrypt effort states "we verify only functional correctness, not leakage resistance", and Aeneas has neither a leakage effect nor secret types, so this is new work, for which the existing functional proof supplies the safety precondition every method requires. SLH-DSA is a favourable target: only SK.seed, SK.prf, the hedging randomness and hash-chain values below the revealed position are secret, they enter nothing but SHA-256, and no timing or cache attack on a correct hash-based signature implementation has been published. The published attacks are power/EM analysis of the PRF and fault or Rowhammer forgeries, and a constant-time theorem addresses none of them. The theorem also stops at Rust MIR: no proof that rustc/LLVM preserves constant-time is known and Rust's own documentation says no mechanism exists, Arm guarantees data-independent instruction latency only while PSTATE.DIT is set, and the model is sequential. An honest claim therefore reads "secret-independent at the source level under a named leakage model", lists the compiler, CPU timing mode, hardware SHA instructions, speculation, power, faults and erasure as assumed or out of scope, and labels any binary-level testing as evidence.

## Every constant-time proof is trace equality over an instrumented semantics

### Three leakage models, nested by what each step emits

All mainstream work defines constant-time the same way: instrument the semantics so that each execution step emits an observation, then require that runs agreeing on public data emit the same sequence. ct-verif states it for a while-language with arrays: "A leakage model L maps program configurations c to observations L(c)", and a program is secure "when all of its initially Xi-equivalent and finally Xo-equivalent executions are indistinguishable", where Xi are the public inputs and Xo the declared public outputs ([ct-verif, USENIX Security 2016](https://www.usenix.org/system/files/conference/usenixsecurity16/sec16_paper_almeida.pdf)). Barthe, Grégoire and Laporte name the general property observational non-interference and catalogue the policies by the type of the leakage: the **program-counter** policy emits the value of every guard, the **constant-time** policy emits guards and accessed addresses, and the **size-respecting** policy adds operand sizes for specific operators such as division ([CSF 2018](https://members.loria.fr/VLaporte/files/CSF2018_ConstantTimePreservation.pdf)). The survey literature uses the same ladder: "The simplest leakage model is the program counter policy", the constant-time policy "additionally assumes that memory accesses are leaked", and the size-respecting policy "also assumes that operand sizes are leaked for specific variable-time operations" ([SoK: Computer-Aided Cryptography](https://www.andrew.cmu.edu/user/bparno/papers/cac-sok.pdf)).

The middle rung, branches plus addresses, is what "cryptographic constant-time" means, and it rests on a theorem, not folklore. Vale summarises the Coq-formalised result of Barthe et al. (CCS 2014) as "a program is free of cache-based side channels if it does not branch on secrets, and if it performs no secret-dependent memory accesses" ([Vale](https://www.usenix.org/system/files/conference/usenixsecurity17/sec17-bond.pdf); [ePrint 2014/422](https://ia.cr/2014/422)). The Jasmin group restates it with its hypothesis attached: the two rules protect against an adversary controlling the cache and the scheduler "provided the victim program and the adversary execute in different processes, and memory isolation between processes are guaranteed" ([Structured leakage, CCS 2021](https://members.loria.fr/VLaporte/files/CCS2021_StructuredLeakage.pdf)). The third rung covers the "variable-time operands" clause of the question. ct-verif lets a division emit "some function over the operands"; Vale's machine semantics records "all inputs to variable-latency instructions"; in Bedrock2 "division and modulo leak their arguments"; and Jasmin's `--doit` mode requires the arguments of any instruction outside the vendor data-operand-independent-timing lists to be public, checked after instruction selection ([ct-verif](https://www.usenix.org/system/files/conference/usenixsecurity16/sec16_paper_almeida.pdf); [Vale](https://www.usenix.org/system/files/conference/usenixsecurity17/sec17-bond.pdf); [Bedrock2, PLDI 2025](https://arxiv.org/html/2504.15550); [Jasmin docs](https://jasmin-lang.readthedocs.io/en/latest/tools/ct.html)). **No formal model examined gives shifts or multiplications an operand-leak rule**; they are covered only by membership in a vendor list, which is a per-CPU fact outside any proof, and is why `crypto-bigint` warns it "is NOT suitable for use on processors with a variable-time multiplication operation" ([crypto-bigint docs](https://docs.rs/crypto-bigint/latest/crypto_bigint/)).

Two modelling details matter for a source-level proof. A language without machine addresses still expresses the memory-access policy by leaking array indices, since "the base variables need not be leaked as they can be inferred from the control flow" ([ct-verif](https://www.usenix.org/system/files/conference/usenixsecurity16/sec16_paper_almeida.pdf)). And a flat list of events suffices: Jasmin's tree-shaped leakage exists only because, with flat concatenation, "it is hard to identify the leakages belonging to the sub-parts" when compiler passes must transform leakage ([Structured leakage, CCS 2021](https://members.loria.fr/VLaporte/files/CCS2021_StructuredLeakage.pdf)).

### Four proof styles, and a Rust program modelled in Lean can use only the deductive ones

The tools split into four styles: a security type system or taint analysis that keeps secrets out of every leaking position; a relational or product-program proof that two runs emit the same trace; a unary proof that the trace is a function of public inputs; and a proof that a compiler preserves the property. Everything else checks or tests the binary without a foundational proof.

| Tool chain | Observations | Checked on | Method | Declassification | Where the guarantee stops |
|---|---|---|---|---|---|
| ct-verif | branches; indices/addresses; optional operand function | optimised LLVM IR | product program reduced to assertion safety | public outputs; "benign" branch annotations | LLVM IR; code generation unverified |
| Jasmin `jasmin-ct` | branch conditions, addresses, array indices, `for` bounds; DOIT mode adds operands | Jasmin source or any later pass | flow-sensitive security type system | `#declassify`, unchecked | assembly, via Coq-proved leakage transformers |
| Jasmin + EasyCrypt | explicit `leakages` list | extracted EasyCrypt model | pRHL equivalence equating the leakage | precondition of the equivalence | same |
| Low\*/HACL\* | `brT`/`brF`, `read`/`write` with address and offset | Low\* source, carried to Clight on paper | abstract secret-integer type plus a metatheorem | none in `Lib.IntTypes` | C; GCC and Clang untrusted |
| Vale | every branch, memory address, variable-latency input | assembly AST | verified taint analyser (Dafny) | `pubStartLocs`/`pubEndLocs` | the assembly itself |
| CompCert-CT | truth value of conditions; pointer accessed or called | Clight to Asm | CT-simulation diagrams in Coq | relation on initial states | assembly |

The rows draw on the primary papers and documentation ([ct-verif](https://www.usenix.org/system/files/conference/usenixsecurity16/sec16_paper_almeida.pdf); [Jasmin docs](https://jasmin-lang.readthedocs.io/en/latest/tools/ct.html); [Low\*](https://arxiv.org/pdf/1703.00053); [Vale](https://www.usenix.org/system/files/conference/usenixsecurity17/sec17-bond.pdf); [CompCert-CT](https://eprint.iacr.org/2019/926); [Bedrock2](https://arxiv.org/html/2504.15550); [libcrux-secrets](https://docs.rs/libcrux-secrets/latest/libcrux_secrets/); [s2n-bignum SOUNDNESS.md](https://github.com/awslabs/s2n-bignum/blob/main/SOUNDNESS.md); [machine-code relational Hoare logic, arXiv 2505.14348](https://arxiv.org/pdf/2505.14348); [Binsec/Rel](https://arxiv.org/pdf/1912.08788); [CT-tools list](https://crocs-muni.github.io/ct-tools/)). Several cells rest on abstracts or slides only: the bodies of the CCS 2014 and CompCert-CT papers and the primary sources for FaCT, ctgrind and dudect were not read.

The type-abstraction style is the cheapest per program. In Low\*, secret limbs have an abstract type with no comparison returning `bool`, and Theorem 3.1 shows that two instantiations of a well-typed program either both get stuck or "both programs make progress with the same trace" ([Low\*](https://arxiv.org/pdf/1703.00053)). HACL\*'s `Lib.IntTypes` gives `div`, `mod` and comparisons only at `PUB` and masks at `SEC`, with no function from `SEC` to `PUB`; the escape hatch is a separate module whose header says using it "BREAKS secret independence" ([Lib.IntTypes.fsti](https://raw.githubusercontent.com/hacl-star/hacl-star/main/lib/Lib.IntTypes.fsti); [Lib.RawIntTypes.fsti](https://raw.githubusercontent.com/hacl-star/hacl-star/main/lib/Lib.RawIntTypes.fsti)). hax's F\* backend applies the same idea to Rust, treating `i32` as secret so that `input % 3329` fails to typecheck, and `libcrux-secrets` offers a Rust-side version in which every `.declassify()` "represents a potential side-channel leak" ([Cryspen, ML-KEM verification](https://cryspen.com/post/ml-kem-verification/); [libcrux-secrets](https://docs.rs/libcrux-secrets/latest/libcrux_secrets/)). FaCT sits in the same family as a DSL that the SoK lists as able to "automatically generate secure implementations from insecure implementations"; it was examined here only through secondary classifications ([SoK](https://www.andrew.cmu.edu/user/bparno/papers/cac-sok.pdf); [CT-tools list](https://crocs-muni.github.io/ct-tools/)). The price of this style is that the guarantee is a metatheorem about a language. A shallow embedding of generated code in Lean has no such metatheorem unless someone proves one about the embedding, so per-function deductive proof is the realistic route.

The deductive styles reduce constant-time to ordinary program proof. ct-verif's product program asserts at each control point that the two copies' guards and indices agree and then runs both under one control structure, so it "has only as many paths as P itself", and its loop invariants "are simply conjunctions of equalities between some program variables and their shadowed copies" ([ct-verif](https://www.usenix.org/system/files/conference/usenixsecurity16/sec16_paper_almeida.pdf)). EasyCrypt reduces security of `c` to the single relational judgment `[c] ∼ [c] : φ ∧ ={leak} ⟹ ={leak}` over code in which leakage is an explicit global list, and Vale's `isLeakageFree` has the same shape with the trace as a ghost field of the machine state and public locations at entry and exit ([Laporte, GLSec 2022](https://members.loria.fr/VLaporte/files/GLSEC22_FineGrainedConstantTimePolicies.pdf); [Vale](https://www.usenix.org/system/files/conference/usenixsecurity17/sec17-bond.pdf)). Bedrock2 avoids two-run reasoning altogether with "∃f. ∀ public/private inputs. p ⇓ {(t,k) | k = f(public)}", at the cost that such specifications are "unfortunately nonmodular": composing `f2` after `f1` requires knowing that the value passed on is itself a function of public data ([Bedrock2](https://arxiv.org/html/2504.15550)). Three lessons carry over directly. **Every deductive method requires safety first** (ct-verif's Theorem 1 speaks of "a safe program", Jasmin builds safety into its definition, Vale considers only successful runs), and a functional-correctness proof supplies exactly that. Only ct-verif's public outputs and Vale's `pubEndLocs` let control flow depend on secret-derived values that the output publishes, which is the feature a signature scheme needs. And only verified compilers carry the result to machine code: CompCert-CT and Jasmin prove preservation, Low\* reaches Clight by a hand proof, and Binsec/Rel found violations introduced by gcc `-O0` and clang backend passes in code that an LLVM-level verifier had accepted ([CompCert-CT](https://eprint.iacr.org/2019/926); [Structured leakage](https://members.loria.fr/VLaporte/files/CCS2021_StructuredLeakage.pdf); [Low\*](https://arxiv.org/pdf/1703.00053); [Binsec/Rel](https://arxiv.org/pdf/1912.08788)).

### Lean 4 and Aeneas have infrastructure but no constant-time proof

The search found **no published Lean 4 proof of constant-time for a real cryptographic implementation**, and a community list of 55 constant-time tools contains none based on Lean ([CT-tools list](https://crocs-muni.github.io/ct-tools/)). What exists is infrastructure. VCVio defines `TraceNoninterference oa₁ oa₂ := RelTriple oa₁ oa₂ (fun z₁ z₂ => z₁.2 = z₂.2)` on computations returning a result and a trace, calls it "the VCVio analogue of constant-time execution", and proves a one-time pad leak-free, but its observations are oracle queries in its `OracleComp` monad, not branches or memory accesses of compiled code ([VCVio Leakage.lean](https://github.com/Verified-zkEVM/VCVio/blob/main/VCVio/ProgramLogic/Relational/Leakage.lean); [VCVio one-time-pad example](https://github.com/Verified-zkEVM/VCVio/blob/main/Examples/OneTimePad/LeakageFree.lean)). CatCrypt Core offers a probabilistic relational Hoare logic, Lean's built-in `mvcgen` is unary and says nothing about leakage, and a 2026 Lean 4 development bounds the leakage of masked Barrett reduction, which is hardware masking analysis ([CatCrypt Core](https://reservoir.lean-lang.org/@spitters/catcryptCore); [Lean reference, mvcgen](https://lean-lang.org/doc/reference/latest/The--mvcgen--tactic/); [arXiv 2604.24670](https://arxiv.org/pdf/2604.24670)).

On Aeneas output the answer is an explicit no. The SymCrypt paper says: "although the Rust code is defensively written in constant-time style to protect against microarchitectural side channels, we verify only functional correctness, not leakage resistance", and relies instead on "leakage-specific fuzzing and symbolic execution on compiled binaries" ([arXiv 2609.15648](https://arxiv.org/html/2609.15648)). The same paper shows what a functional proof does and does not say: it caught a bug in FrodoKEM's `ct_equal_u16`, yet the theorem proved is that the mask has the right value, with nothing about how it is computed. Aeneas's `Result` has been an interaction tree since September 2026, but `RustEffect` has one constructor, `fail`, and a source comment that begins "TODO: when we add more effects"; the stated direction is "separation logic to support unsafe code and concurrent code" ([Aeneas Primitives.lean](https://github.com/AeneasVerif/aeneas/blob/main/backends/lean/Aeneas/Std/Primitives.lean); [Aeneas README](https://github.com/AeneasVerif/aeneas/blob/main/README.md)). A search of the Aeneas and vendored Charon sources for "constant-time", "side-channel", "leakage" and "secret" returns one unrelated hit ([Aeneas repository](https://github.com/AeneasVerif/aeneas)). hax 0.4 now reaches Lean by driving Charon and Aeneas, and none of its 2026 posts mention secret integers or secret independence for that backend ([hax blog, 2026](https://hax.cryspen.com/blog/archive/2026/)). Two limits on this negative finding: Lean and Aeneas Zulip archives and the GitHub issue trackers were not searched, so an unpublished prototype cannot be ruled out.

## A writer monad over `Result` carries the property onto Aeneas output

No source presents relational rules for a shallowly embedded, leakage-instrumented `Result` monad in Lean, so the design below is assembled from the cited deep-embedding semantics; it is a derived construction, not an existing method. The instrumented monad is a writer over `Result`, in effect `Result (α × List Event)`. The emission rules come straight from the literature: `pure` emits nothing and bind concatenates; a conditional emits the guard's value and then the taken branch's events, as in the CSF 2018 rule `leak(e, ρ)·λif([e]ρ)` and Jasmin's `if_b`; an array or slice access emits its index, as in ct-verif's address model and Jasmin's `[z]`; a loop emits per iteration whether it continued or exited, as in Jasmin's `while_t`/`while_f`; division and remainder emit their operands, as in Bedrock2 ([CSF 2018](https://members.loria.fr/VLaporte/files/CSF2018_ConstantTimePreservation.pdf); [Structured leakage](https://members.loria.fr/VLaporte/files/CCS2021_StructuredLeakage.pdf); [Bedrock2](https://arxiv.org/html/2504.15550)). Aeneas translates Rust loops with a `loop` combinator over `ControlFlow` values `cont` and `done`, so the loop rule attaches to one definition ([Aeneas Primitives.lean](https://github.com/AeneasVerif/aeneas/blob/main/backends/lean/Aeneas/Std/Primitives.lean)). Because Aeneas emits uninstrumented definitions and its translation needs "no heap model", the instrumented copy has to be produced outside Aeneas, by a metaprogram, a patched extraction or by hand, and it is an unverified model unless an **erasure theorem** shows that forgetting the trace returns the verified function ([Aeneas overview](https://github.com/AeneasVerif/aeneas/blob/main/documentation/aeneas-overview.md)). A leakage event added to `RustEffect` would remove the duplication, but that is a possibility the interaction-tree redesign opens, not a feature.

The statement has a relational form, `φ x x' → trace (f x) = trace (f x')`, and a unary form, `∃ L, ∀ pub sec, trace (f pub sec) = L pub`. For deterministic total functions the two are interderivable, so a probabilistic relational logic such as VCVio's is more machinery than the property needs; the unary form turns each lemma into an equation that rewriting can chain. The proof rules follow from the cited systems. For bind, the continuation's trace must be public-determined for the value actually produced, so each callee lemma carries a second clause saying which parts of its result are functions of public data; this is Low\*'s obligation that library functions return related results "while producing identical traces" and Bedrock2's modularity caveat in another guise ([Low\*](https://arxiv.org/pdf/1703.00053); [Bedrock2](https://arxiv.org/html/2504.15550)). For a conditional, prove the guard public-determined; for an access, prove the index public-determined; for a loop, the invariant is that the trace so far and the public part of the loop state are public-determined, the analogue of ct-verif's shadow-equality invariants. `Result.fail` and bounds-check panics are observable control flow, and the existing proof that the function returns `ok` on valid inputs discharges them.

The working tree's uncommitted `lean/Ct/` directory already has this shape: a `Leak` writer monad over `Result`, events for branches, indices with lengths, sub-slice ranges, copies, vector growth, division and remainder, and an instrumented copy obtained by re-elaborating the unchanged Aeneas text in a namespace that shadows the leaking primitives. Its module comments name an erasure proof and a whitelist check on the elaborated terms that are not yet in the tree. Measured against the literature, those two pieces are what turn the copy from a model into a statement about the verified program, and the table of which primitive emits what is the trusted artefact, in the sense Libjade gives when it says its checker is trusted and "the leakage model itself is not assumed to be a faithful model of reality, but good enough to guarantee that the best practices in protection against timing attacks are correctly deployed" ([Libjade assurance](https://github.com/formosa-crypto/formosa-libjade/blob/main/docs/assurance.md)). Lifting checked addition, multiplication and shifts without an event matches every model read; it also makes the absence of a shift or multiply rule an assumption about the target CPU. A Rust-side secret-integer newtype in the style of `libcrux-secrets` or `secret_integers` is a cheap complementary lint that catches the same three violation classes at compile time but yields no Lean theorem and leaves every declassification unchecked ([secret_integers](https://docs.rs/secret_integers/latest/secret_integers/)).

## Two seeds are secret; R, the digest and every WOTS+ digit are public once published

### The classification rests on FIPS 205's labels and two explicit walk-throughs

FIPS 205 fixes the long-term secrets: "The SLH-DSA private key contains two random, secret n-byte values", SK.seed, which generates every WOTS+ and FORS private element, and SK.prf, which generates the message randomiser; PK.seed is "an n-byte public seed", and an ADRS "consists of public values" ([FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)). The most explicit step-by-step classification is the 2024 NIST conference paper "Side Channel Resistant Sphincs+", attributed to Scott Fluhrer, which concludes: "the secrets that we need to protect are: The secret input to the PRFmsg function. The inputs and outputs to the PRF function. The inputs and (sometimes) outputs to the F function. For everything else, we can use a straight-forward (unprotected) implementation", and defines non-secret values as "either values that are also computed by the verifier (and so the adversary has them), or internal nodes within a Merkle tree" ([Side Channel Resistant Sphincs+](https://csrc.nist.gov/csrc/media/Events/2024/fifth-pqc-standardization-conference/documents/papers/side-channel-resistant-sphincs-plus.pdf)). Kannwischer's thesis gives the same answer for the XMSS and WOTS+ building blocks: "The entire XMSS tree is public and, thus, leakage agnostic", while chain values "need to be considered secret if they are below the parts contained in the W-OTS+ signature" ([Kannwischer thesis](https://download.hrz.tu-darmstadt.de/pub/FB20/Dekanat/Publikationen/CDC/Matthias_Kannwischer.master.pdf)).

| Value | Class | Basis |
|---|---|---|
| SK.seed, SK.prf | secret | FIPS 205 §9.1 |
| `addrnd` / `opt_rand` in hedged mode | secret by convention | FIPS 205 is silent; slhdsa-c and the `fips205` crate mark it secret |
| PRF outputs: WOTS+ chain starts, FORS secret leaf values | secret unless written into the signature | FIPS 205 §5, §8; Fluhrer §3 |
| WOTS+ chain values below the signed digit; every non-final chain value of WOTS+ keys that are not signing | secret | Kannwischer §4.3; Fluhrer §3 |
| WOTS+ chain ends and public keys, every XMSS and FORS tree node, FORS leaves F(sk), FORS roots | public | FIPS 205 §5; Kannwischer; Fluhrer |
| R | public, but computed from SK.prf | Algorithm 19 line 4; slhdsa-c |
| digest, md (the FORS indices), idx_tree, idx_leaf | public | H_msg takes only R, PK.seed, PK.root, M; Algorithm 20 recomputes them |
| PK_FORS and the XMSS root of each layer, hence the WOTS+ digits and checksum digits at every layer | public, but computed from SK.seed | the verifier recomputes them; slhdsa-c |
| PK.seed, PK.root, M, ctx, lengths, parameter set, hedged flag, all ADRS contents | public | FIPS 205 §3, §4.2, §10.2 |

Two rows carry judgment. FIPS 205 never says `addrnd` must be confidential; treating it as secret follows slhdsa-c's test harness ("SK.seed and SK.prf, and the signing randomness, are secret") and the `fips205` crate, and costs nothing because it only ever enters HMAC ([slhdsa-c xfips205.c](https://github.com/pq-code-package/slhdsa-c/blob/main/test/xfips205.c); [fips205 README](https://github.com/integritychain/fips205/blob/main/README.md)). And "public" here is relative to unforgeability. FIPS 205 notes that message and signature are confidential in some applications, such as "signatures that are used as bearer tokens", and no implementation examined documents a threat model in which md and the indices are secret; adopting one would forbid index-dependent tree traversal altogether ([FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)).

### Three kinds of declassified value carry all secret-derived control flow

WOTS+ chain lengths are the message digits: Algorithm 7 computes `sig[i] ← chain(sk, 0, msg[i], PK.seed, ADRS)`, and at layer 0 the message is PK_FORS while at each higher layer it is the XMSS root of the tree below ([FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)). Those values are functions of SK.seed, so a plain non-interference statement is false for signing, and the designers and implementers agree the dependence is harmless. Fluhrer: an implementation "may have conditionals based on, for example, the part of the tree we are exposing, or the revealed index within a Winternitz chain. However, that data can also be deduced by the attacker by examining the signature, message and public key, and hence these conditionals do not leak any secret information". Saarinen: "Timing attacks are not a great concern for SLH-DSA, as conditional branching and memory access patterns are dependent on non-secret authentication paths; they are revealed by the signature and known to a verifier" ([Side Channel Resistant Sphincs+](https://csrc.nist.gov/csrc/media/Events/2024/fifth-pqc-standardization-conference/documents/papers/side-channel-resistant-sphincs-plus.pdf); [Saarinen, Accelerating SLH-DSA](https://csrc.nist.gov/csrc/media/Events/2024/fifth-pqc-standardization-conference/documents/papers/accelerating-slh-dsa.pdf)).

The industrial precedent pins the declassification points down exactly. slhdsa-c, the SLH-DSA source used by liboqs, marks the secrets undefined for Valgrind and declassifies **R** ("Required to use the message digest derived from it in conditional-branches and as tree indices"), **the FORS public key** ("Required to use it in conditional-branches in WOTS+ signing") and **the XMSS root of each layer** before it is signed at the next, plus the public key in key generation ([slhdsa-c slh_dsa.c](https://github.com/pq-code-package/slhdsa-c/blob/main/slh_dsa.c)). For SLH-DSA-SHA2-128s, with d = 7, that is R, PK_FORS and six roots, each 16 bytes ([sphincsplus README](https://github.com/sphincs/sphincsplus/blob/master/README.md)). A proof needs nothing finer provided the code never branches or indexes on a chain value or tree node; the sources would support treating every Merkle node and chain end as public as soon as it is computed, but that policy is only needed by code that inspects them. Key generation needs no declassification inside the computation, since it runs every chain to the top with a fixed amount of work.

One question has no direct answer in the literature: whether observing chain lengths before the signature is released matters. No paper, standard or mailing-list post analyses it. The structural argument is that the leaked quantities are outputs of H_msg and digits of values the security proof hands the adversary with every signature, so early disclosure changes nothing for the key; what it does disclose is partial information about a signature that a signer later withholds or transmits under encryption. Kannwischer's caveat points the other way and concerns chain values, not digits: "Since the b_i's are not known before the actual message is signed, all intermediate values have to be considered secret" ([Kannwischer thesis](https://download.hrz.tu-darmstadt.de/pub/FB20/Dekanat/Publikationen/CDC/Matthias_Kannwischer.master.pdf)).

### The attack literature has no timing attack, and real power and fault attacks

FIPS 205 contains no constant-time requirement. Its side-channel text is one paragraph in the non-normative Section 3.2, a recommendation that the hedged variant "should be used on platforms where side-channel attacks are a concern", and a normative requirement to destroy sensitive intermediate data ([FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)). The designers' intent is in the SPHINCS+ submission: "Typical implementations of SPHINCS+ are naturally free of any secret-dependent branches or secretly indexed loads or stores", and they "naturally do not use" variable-time instructions such as division "with secret data as input – secret data is only processed by symmetric cryptographic primitives" ([SPHINCS+ v3.1](https://sphincs.org/data/sphincs+-r3.1-specification.pdf)). The research found **no published timing, cache or control-flow attack on a correct implementation of any standardised hash-based signature scheme**; the peer-reviewed assessment is that "timing and simple power analysis attacks are unpromising" ([ePrint 2018/673](https://eprint.iacr.org/2018/673)). A blog post describing a "CVE-2026-7731" SPHINCS+ timing attack should be disregarded: the actual CVE record is an SQL injection in an unrelated product ([CVE-2026-7731 record](https://cveawg.mitre.org/api/cve/CVE-2026-7731)).

The attacks that do exist sit outside the constant-time model. Power and EM analysis targets the PRF because "SK.seed is used as a input to the PRF function, with all other inputs being public, and varying per use. This situation is ideal for an attacker using DPA"; Saarinen measured leakage from SK.seed "with t value reaching 24.5 in 1,000 traces" on an unprotected software implementation, and a 2026 correlation power analysis of SLH-DSA-SHAKE reports full seed recovery in roughly 280 to 559 signatures ([Side Channel Resistant Sphincs+](https://csrc.nist.gov/csrc/media/Events/2024/fifth-pqc-standardization-conference/documents/papers/side-channel-resistant-sphincs-plus.pdf); [Saarinen](https://csrc.nist.gov/csrc/media/Events/2024/fifth-pqc-standardization-conference/documents/papers/accelerating-slh-dsa.pdf); [ePrint 2026/2584](https://eprint.iacr.org/2026/2584)). Fault attacks make a one-time key sign two different values: the grafting-tree attack applies to the whole SPHINCS framework, and Genêt shows that "the security guarantees of SPHINCS+ significantly drop when a single random bit flip occurs anywhere in the signing procedure" while the faulty signature still verifies ([ePrint 2018/102](https://eprint.iacr.org/2018/102); [ePrint 2023/042](https://eprint.iacr.org/2023/042)). The same mechanism is now delivered in software: SLasH-DSA reports Rowhammer universal forgeries against OpenSSL 3.5.1 for parameter sets that include **SHA2-128s**, after one hour of hammering in deterministic mode and eight in randomised mode ([arXiv 2509.13048](https://arxiv.org/abs/2509.13048)). For the parameter set of interest, that is the most practically relevant attack outside the model, and a constant-time proof is orthogonal to it.

Implementation practice matches the policy. The SPHINCS+ reference code, OpenSSL, BoringSSL, RustCrypto's `slh-dsa`, slhdsa-c and the `fips205` crate all loop or branch on WOTS+ digits and tree indices, and all compare the recomputed root with a variable-time `memcmp` or `==`; none treats this as a defect ([sphincsplus wotsx1.c](https://github.com/sphincs/sphincsplus/blob/master/ref/wotsx1.c); [OpenSSL slh_wots.c](https://github.com/openssl/openssl/blob/master/crypto/slh_dsa/slh_wots.c); [BoringSSL wots.cc.inc](https://github.com/google/boringssl/blob/main/crypto/fipsmodule/slhdsa/wots.cc.inc); [RustCrypto wots.rs](https://github.com/RustCrypto/signatures/blob/master/slh-dsa/src/wots.rs)). Verification takes only the public key, message, context and signature, so it needs no constant-time property for key secrecy; the `fips205` crate says so in terms: "Verify uses only public data and makes no constant-time claim" ([fips205 README](https://github.com/integritychain/fips205/blob/main/README.md)). The hash itself is the remaining link. Software SHA-256 consists of "bitwise logical operations and additions on 32-bit or 64-bit words, naturally yielding constant-time operations", and its number of compression calls depends only on input length, which is public here ([BearSSL](https://www.bearssl.org/constanttime.html)). The default build's compression function is therefore inside the theorem as ordinary Rust code.

## The honest theorem is a source-level simulator statement

### What the statement says

The theorem for signing has this shape (names illustrative):

```lean
theorem sign_trace_public (sk : SecretKey) (M ctx) (addrnd) (h : valid sk M ctx) :
    ∃ sig tr, (sign_leak sk M ctx addrnd).run = ok (sig, tr)
      ∧ tr = signTrace sk.pk M ctx addrnd.isSome sig
```

Here `signTrace` is a definition in the development that never receives SK.seed, SK.prf or `addrnd`: it recomputes the digest from R and the public key, and PK_FORS and the layer roots from the signature, exactly as verification does, and replays the control flow. Key generation gets the simpler form, a trace that is constant for the parameter set. Verification gets no theorem. A companion lemma, `erase (sign_leak …) = sign …`, ties the instrumented copy to the functionally verified program.

The explicit simulator matters more for SLH-DSA than the usual choice between relational and unary form suggests; what follows is this report's analysis, not a cited result. ct-verif's public-output definition quantifies over pairs of runs whose outputs agree. For a signature scheme, two runs with the same public key and the same signature have, for all practical purposes, the same secret key, so the set of pairs is close to the diagonal and the statement constrains almost nothing. An abstract `∃ L` over the signature has the same weakness, because a signature that determines the key makes every trace "a function of" it. The statement acquires its meaning from `signTrace` being a named, inspectable program that uses only public hashing: anyone holding the public key, message and signature computes the trace for about the cost of a verification, so the trace adds nothing to what the adversary is already given. Proving that the declassified values equal what verification recomputes reduces, through the functional-correctness proof already in hand, to the scheme's completeness: verifying an honest signature recomputes the same PK_FORS and the same roots.

The surrounding text names the artifact and the policy. The property holds for the Lean model that Aeneas produces from Charon's extraction of the crate's MIR, for a stated rustc version, feature set and profile. The observations are branch outcomes, loop exits, indices and lengths of every element access, and operands of division and remainder. The secrets are SK.seed, SK.prf, `addrnd` and the FORS and WOTS+ values derived from them; the public inputs are the parameter set, PK.seed, PK.root, message, context, lengths and the hedged flag; the declassified values are R, PK_FORS and the layer roots. Panics and bounds checks are control flow whose outcome the functional proof fixes. The `fips205` crate's README is the closest existing wording, and a machine-checked version keeps its structure: "Control flow and memory access follow only public data: the parameter set, the message and context lengths, the `hedged` flag, and the message digest, tree indices and WOTS+ digits that the signature reveals… The claim is at the source level: the compiler and CPU are trusted not to add secret-dependent timing, and the caller's RNG is outside it" ([fips205 README](https://github.com/integritychain/fips205/blob/main/README.md)).

### What it leaves out

| Layer | Status under the theorem | What the sources establish |
|---|---|---|
| Charon, Aeneas, the leakage table | trusted | SymCrypt trusts the same toolchain; the instrumented copy is tied back only by erasure |
| rustc and LLVM | assumed not to add secret-dependent branches, addresses or variable-time instructions | no preservation result found; Rust's documentation denies any mechanism |
| Caches | covered in the model: accessed indices are public | the model has indices, not addresses, lines or stack layout |
| Instruction latency | assumed data-independent | Arm guarantees it only with PSTATE.DIT = 1; user space must set the bit |
| Hardware SHA-256 instructions | axiomatised, outside the default-build theorem | Arm lists them as data-independent-time instructions under DIT |
| Speculation | out of scope | the model is sequential; only Jasmin code has machine-supported speculative constant-time |
| Prefetchers, frequency scaling | out of scope | DIT disables Apple's DMP on M3 only; Hertzbleed is unmitigated |
| Power/EM, faults, Rowhammer | out of scope | the published attacks on SLH-DSA are all here |
| Erasure of secrets | no claim | FIPS 205 §3.1 makes it a requirement |
| libc routines, allocator, RNG | outside the model | timing depends on lengths and sizes, argued public |

**The compiler.** Charon consumes rustc MIR, and LLVM runs afterwards, so the theorem sits before every transformation shown to break constant-time code ([Charon paper](https://arxiv.org/html/2410.18042v3)). The Rust standard library is categorical: "there is no mechanism in the entire Rust language that can provide the guarantees required for constant-time cryptography. (There is also no such mechanism in LLVM, so the same is true for every other LLVM-based compiler.)" ([Rust std docs, black_box](https://doc.rust-lang.org/std/hint/fn.black_box.html)). LLVM's `llvm.ct.select` work was still in open pull requests on 2026-11-21, covers only selection, and by its own RFC is "not intended to, and in fact cannot, prevent hardware-level security issues like SPECTRE or Rowhammer" ([llvm-project PR #166702](https://github.com/llvm/llvm-project/pull/166702); [LLVM RFC](https://discourse.llvm.org/t/rfc-constant-time-coding-support/87781)). The only machine-checked preservation results found are for a modified CompCert and for Jasmin, and Libjade documents even Jasmin's as "not machine-checked for the current compiler version" ([ePrint 2024/1203](https://eprint.iacr.org/2024/1203); [Libjade assurance](https://github.com/formosa-crypto/formosa-libjade/blob/main/docs/assurance.md)). The documented breakages share one trigger: source that computes something conditional on a secret in branch-free form, or divides a secret. Breaking Bad, covering 8 libraries, GCC 5–13, LLVM 5–18 and six architectures including aarch64, found mask selects turned into branches or secret-dependent addresses "even when the high-level source code was formally verified to be free of side channels"; clangover (CVE-2024-37880) recovered an ML-KEM-512 key in "5-10 minutes" from a Clang-inserted branch; and in Rust, RUSTSEC-2024-0344 records that in curve25519-dalek "LLVM saw an opportunity to insert a branch instruction" in a masked loop ([Breaking Bad](https://arxiv.org/html/2410.13489v2); [clangover](https://github.com/antoonpurnal/clangover); [RUSTSEC-2024-0344](https://rustsec.org/advisories/RUSTSEC-2024-0344.html)). SLH-DSA signing needs no secret-dependent select, comparison or division: secrets are copied and hashed under public loop bounds. No source documents a compiler adding a secret-dependent branch to such code, and no source proves it cannot; Breaking Bad's own conclusion is "We did not find a way to ascertain if a specific arithmetic source code pattern is safe just by looking at the source code." The accurate summary is "the known trigger is absent", with two qualifications. The theorem does not establish that absence, because a mask-based select on a secret emits no event in any of these models, so it remains a source-review fact. And no study measures compiler-introduced leaks in Rust crates at scale. SHA-256's Ch and Maj are bitwise multiplexers over full words, not 0/−1 masks, and no report of either being turned into a branch was found; a one-off disassembly check of the compression function is cheap. The variable-time-operand clause is the weakest of the three at this level, because ct-verif already observed that operand-based properties "are generally not preserved" by code generation, and the KyberSlash authors note that whether a source-level division becomes a division instruction depends on compiler and flags ([ct-verif](https://www.usenix.org/system/files/conference/usenixsecurity16/sec16_paper_almeida.pdf); [KyberSlash FAQ](https://kyberslash.cr.yp.to/faq.html)).

**Instruction timing and the hardware SHA instructions.** With PSTATE.DIT = 0, "The architecture makes no statement about the timing properties of any instructions"; with DIT = 1 the timing of loads and stores is "insensitive to the value of the data being loaded or stored" and listed data-processing instructions take time independent of their operands ([Arm DIT register, mirror of Arm XML](https://df.lth.se/~getz/ARM/SysReg/AArch64-dit.html)). This applies to the portable build's additions and rotations as much as to the SHA extension. Arm's instruction reference marks SHA256H as "a data-independent-time instruction as described in About PSTATE.DIT", with the same note on SHA256H2, SHA256SU0 and SHA256SU1 and absent from UDIV ([SHA256H, mirror of Arm ISA XML](https://www.scs.stanford.edu/~zyedidia/arm64/sha256h_advsimd.html)). For a hardware-SHA build the Lean model can only axiomatise the intrinsics, so the claim there is that the Rust around them is secret-independent and that the instructions are assumed data-independent-time. Setting the bit is a deployment fact the functional semantics cannot establish. On macOS 15.2 and later the call is `timingsafe_enable_if_supported`; on Linux the kernel enables DIT only for itself, and user space must set it after checking `HWCAP_DIT` ([Apple, Writing ARM64 code](https://developer.apple.com/documentation/xcode/writing-arm64-code-for-apple-platforms); [Linux commit 01ab991fc0ee](https://github.com/torvalds/linux/commit/01ab991fc0ee5019aecc4ca461311fc8aa75ece5)). Cores before Armv8.4 have no DIT bit, and the only assurance is Arm's statement, quoted in a Go issue, that it "is not aware of any Arm processor implementations from before the introduction of FEAT_DIT that exhibit data value timing variation for the instructions covered" ([golang/go#49702](https://golang.org/issue/49702)). On x86 the SHA-NI instructions are on Intel's DOIT list, but enabling DOITM is privileged, and an x86 maintainer, speaking personally, wrote in March 2026 that "DOITM itself is dead" for Linux ([Intel DOIT instruction list](https://www.intel.com/content/www/us/en/developer/articles/technical/software-security-guidance/resources/data-operand-independent-timing-instructions.html); [LKML, 18 Mar 2026](https://lkml.iu.edu/hypermail/linux/kernel/2603.2/07054.html)). The Arm text here comes from mirrors of Arm's machine-readable specification and should be checked against the current Arm ARM before being quoted in a paper.

**Speculation, prefetchers and frequency.** Classical constant-time is defined over sequential execution, and "this semantics is not aligned with the behavior of modern processors that make use of speculative execution" ([Barthe et al., S&P 2021](https://eprint.iacr.org/2020/1104)). Rust bounds checks have the Spectre-v1 gadget shape, a branch guarding an indexed load, and "indices are public" says nothing about what a mispredicted check loads transiently. Only Jasmin-based code has machine-supported speculative constant-time, on x86-64; s2n-bignum's wording is the model to copy: "the model is non-speculative. Side-channel risks from speculative execution (Spectre-class) are not addressed by the current proofs" ([Libjade assurance](https://github.com/formosa-crypto/formosa-libjade/blob/main/docs/assurance.md); [s2n-bignum SOUNDNESS.md](https://github.com/awslabs/s2n-bignum/blob/main/SOUNDNESS.md)). GoFetch showed that Apple's data memory-dependent prefetcher extracts keys from constant-time code, and that "the DIT bit set on m3 CPUs effectively disables the DMP. This is not the case for the m1 and m2" ([GoFetch](https://gofetch.fail/)). No source says whether DIT disables the DMP on M4 or later cores, and none addresses whether the DMP is exploitable against a hash-based signer, so the correct wording is "outside the model", not "not applicable". Hertzbleed adds that "even when implemented correctly as constant time, cryptographic code can still leak via remote timing analysis" through frequency scaling, which neither DIT nor DOIT covers ([Hertzbleed](https://www.hertzbleed.com/)).

**Erasure and everything physical.** FIPS 205 §3.1 requires that implementations "shall ensure that any local copies of the inputs and any potentially sensitive intermediate data are destroyed as soon as they are no longer needed" ([FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf)). A secret-independent trace implies nothing about that, and `zeroize` itself warns that "stack spilling and other optimizations may leave temporary copies" ([zeroize docs](https://docs.rs/zeroize/latest/zeroize/)). Because erasure is a conformance requirement, silence would be misread; the claim should say "no claim about erasure". Power, EM, fault injection and Rowhammer need one sentence each, since the published SLH-DSA attacks all live there.

### How careful projects word it, and what closes the gap in practice

The claims that have aged well share an anatomy: the property in observable terms, the secret and public sets, the artifact it was proved on, the status of the path to the binary, the hardware assumption, an explicit out-of-scope list, and empirical evidence labelled as such. HACL\* claims "secret independence (resistance to some types of timing side-channels)" and writes "our toolchain stops with verified C code"; Breaking Bad later found an HACL\* mask select compiled to secret-dependent code, and the claim survived because it never covered the compiler ([hacl-star README](https://github.com/hacl-star/hacl-star); [HACL\* paper](https://eprint.iacr.org/2017/536); [Breaking Bad](https://arxiv.org/html/2410.13489v2)). libcrux says "Executables compiled from the code in this repository are *not* verified to be side-channel resistant, although we try to enforce that the source code is secret-independent" ([libcrux Readme](https://github.com/cryspen/libcrux)). s2n-bignum, which proves the property on machine code, still writes that its proof "does not and cannot guarantee that the hardware executes those instructions in constant time" ([s2n-bignum SOUNDNESS.md](https://github.com/awslabs/s2n-bignum/blob/main/SOUNDNESS.md)). The phrases to avoid for a source-level result are an unqualified "constant-time implementation" and "side-channel free".

Projects without a verified compiler close the gap with binary-level checks and say what those are. slhdsa-c runs its Valgrind taint tests in CI with the KyberSlash authors' patch that also flags variable-latency instructions, across several gcc and clang versions and optimisation levels; `crypto-bigint` runs `cargo checkct` with BINSEC on supported architectures; the `fips205` crate publishes dudect measurements with the caveat "they are evidence, not proof", and records no AArch64 run ([slhdsa-c ct-tests.yml](https://github.com/pq-code-package/slhdsa-c/blob/main/.github/workflows/ct-tests.yml); [crypto-bigint docs](https://docs.rs/crypto-bigint/latest/crypto_bigint/); [fips205 dudect README](https://github.com/integritychain/fips205/blob/main/dudect/README.md)). Breaking Bad's recommendation is to publish the tested architectures, compilers and flags, which makes the sentence "the compiler is trusted" checkable by others ([Breaking Bad](https://arxiv.org/html/2410.13489v2)).

## Conclusion

SLH-DSA inverts the usual difficulty of a constant-time proof. For lattice or elliptic-curve code the hard part is masked arithmetic, and the compiler is the enemy because it recognises the masks. Here there are no masks; the intellectual content is the declassification argument, and the functional-correctness proof already contains it, because the values that steer control flow are exactly the ones verification recomputes. Stating the result as an explicit simulator over the verifier's view also gives it a use beyond documentation: a signing oracle that additionally returns the leakage trace is simulated by the ordinary oracle plus `signTrace`, so the theorem composes with an existing unforgeability proof to cover an adversary who sees the trace. That composition is this report's inference and is worth checking against the project's security theorems.

The same structure moves the residual risk. With the known compiler trigger absent, the next unit of assurance is not more constant-time proof but two cheap engineering facts the theorem cannot supply: PSTATE.DIT set around key generation and signing, and a Valgrind-style taint test of the shipped AArch64 binary with the same three declassification points. The attacks actually demonstrated against SLH-DSA implementations, power analysis of the PRF and Rowhammer-induced forgeries that include SHA2-128s, call for hedged signing by default, masking and redundancy, which are separate properties with separate arguments. If Aeneas later gives `RustEffect` a leakage event, the instrumented copy and its erasure theorem disappear, so the theorem is best phrased against the trace function, not against the mechanism that produces the trace.
