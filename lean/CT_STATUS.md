# Constant time: what is proved (2026-11-22)

For the portable (default) build of `../rust`, all six SHA-2 parameter sets, the Lean
library [Ct](Ct) proves the statements of the single-set tree's constant-time proofs (its
method and model are described in [Part 3](#part-3-the-method) below): key generation leaks nothing, each signer's
trace is a simulator's on public inputs, verification's inputs are all public, SHA-256 and
SHA-512 traces depend only on the length, and the key codecs leak only lengths (and, when
decoding, the position where the input leaves the fixed DER prefix). Build it with

```
cd lean && lake build Ct
```

The `hw-sha2` build is covered too ([Part 2](#part-2)); `hw-sha512` is not.

## Same model, same machinery

The leakage model is the single-set tree's: the same events (`Ct/Leak.lean`, linked), the same table
of instrumented primitives (`Ct/Model.lean`, linked), the same `do` elaborator (`Ct/Do.lean`,
linked), the same checker. The instrumented program [Ct/Funs.lean](Ct/Funs.lean) is
generated from the verified translation `Slhdsa/Funs.lean` by
[scripts/ct-gen.sh](../scripts/ct-gen.sh) (adapted from the single-set tree's): only the header and the final `end` change, and the script checks that the body is
byte-for-byte the source's. Then

* `Ct/Check.lean`: all 480 definitions of `Ct.Funs` use only instrumented primitives and
  whitelisted non-leaking operations;
* `Ct/Erase.lean`: 441 erasure theorems (`slhdsa_leak.f.erase_eq`), one per function and
  constant of `Slhdsa/Funs.lean`, 0 failures.

What this translation needed beyond the single-set tree's model, all of it in this tree's files:

* **One instrumented primitive** ([Ct/ModelBuild.lean](Ct/ModelBuild.lean)):
  `core.slice.index.Slice.index_mut`, a mutable sub-slice of a *slice* (`&mut sk[a..b]` on the
  key buffers the generic key generation writes into, and in `der_encode`). It emits what the
  read-only `core.slice.index.Slice.index` of `Ct/Model.lean` emits: the range and the slice's
  length. (`Ct/CheckTestBuild.lean` checks the name resolves to it and that the
  un-instrumented one is rejected.)
* **Five whitelist entries** ([Ct/Check.lean](Ct/Check.lean), a copy of the single-set
  tree's checker with the entries marked `[six-set]` and their reasons written there):
  `core.num.U64.wrapping_add` and `core.num.U64.rotate_right` (SHA-512's 64-bit counterparts
  of the 32-bit `wrapping_add` / `rotate_right` already listed; constant rotation amounts),
  `core.num.U64.MAX` (a constant, shifted by the public tree height in `digest_tree`), and
  `U128.ofNat` / `UScalarTy.U128` (the literal `8#u128` and the cast target of SHA-512's
  128-bit length field `(len as u128) * 8`). None branches, indexes or divides. Division and
  remainder on every width, including `u128`, still go only through the leaking instances
  (`Ct/CheckTestBuild.lean` has a positive control for a `u128` division).

The checker accepted everything else unchanged: no branch, index, length or division of the
generated text escaped the model.

Nothing of `../rust`'s portable build branches, indexes, sizes an allocation or a copy, or
divides on a secret: the relational lemmas hold with every seed, SHA-256/SHA-512 state, block,
node value and message treated as secret except for lengths. The new control flow is on public

### The kernel's data-dependent part, for N = 16, 24, 32

The only place the kernel's control flow or addresses depend on block contents is the
first-round cache in `enter::<N>`: it copies `block[0..16]` into `head` and compares it with
`first.head` (array `==`, so the trace has the length of the common prefix and the outcome).
For every `N` the key is the same 16 bytes `block[0..16]` (`rust/src/sha256.rs`, `enter`:
`head.copy_from_slice(&block[0..16])`, independent of `N`). The blocks that reach
`chain_blocks::<N>` are `ADRSc (22 bytes) ‖ value (N bytes) ‖ SHA-256 padding`: the value sits
at bytes 22..22 + N, so for N > 16 it runs past byte 38 (into 38..46 for N = 24, 38..54 for
N = 32), but it never reaches below byte 22. The key is the first 16 bytes of the compressed
address, public for every `N`.

The precondition is therefore the single-set tree's, unchanged for all three values of `N`:
`HeadsEq blocks.val blocks'.val` (the two runs' blocks agree on bytes 0..16; everything else,
the value, the step counter and, for N = 24, the padding bytes 46..54 that the kernel saves in
`tail`, is treated as secret). The lemma is

```lean
-- lean-hw/Ct/Hw/Chain.lean
theorem hw_chain_blocks (N : Usize) (state state' : Array U32 8#usize)
    (blocks blocks' : Slice Block)
    (start e : Slice U32) (hb : HeadsEq blocks.val blocks'.val) :
    Rel (sha256.hw.chain_blocks N state blocks start e)
      (sha256.hw.chain_blocks N state' blocks' start e)
      (fun p q => p.1 = q.1 ∧ HeadsEq p.2.val q.2.val)
```

for every `N` (it covers 16, 24 and 32, the values for which the kernel runs, and the others,
for which it returns `false` at once). `leave::<N>` writes bytes 18..22, 22..38 and, for
N > 16, 38..54, all at or after byte 16, so `HeadsEq` holds again afterwards and is the
invariant of `chain_all`'s loops (`Ct.Hw.leave`, via `headEq_of_store_be`). The other
branches the generic kernel adds (`N = 16`, `N = 24`, `N > 16`, `N > 24`, the mask choice, the
last `SHA256H2` for N > 16) are on `N`, shared by both runs; `xb` and `tail` only pass through
register-only wrappers and fixed-position loads and stores.

`Ct/ChainTop.lean` states `hash::chain_blocks` exactly as the portable build does (same
`HeadsEq` hypothesis and conclusion). The callers are therefore the portable build's proofs,
linked: every block given to `chain_blocks` is built by `hash::short_block` from a public
address (`Ct.Hash.short_block` proves the two runs' blocks have equal heads whatever the
message), and between steps only bytes ≥ 18 change. No new argument was needed in `Wots`,
`Fors` or above.

## Summary (single-set tree, 2026-11-21)

For both builds of the crate, the Lean library [Ct](Ct) proves that what key
generation and signing reveal through branches and memory accesses is either
nothing or computable from public data. Build it with
`cd lean && lake build Ct` (default build) and `cd lean-hw && lake build Ct`
(`hw-sha2`); [Ct/Theorems.lean](Ct/Theorems.lean), one file for both, holds
the statements and prints their axioms (the three standard ones).

### What is secret and what is public

- **Secret:** SK.seed, SK.prf, the signing randomness `addrnd`, and everything
  derived from them before publication (WOTS+ and FORS secret values, chain
  values below the signed digit).
- **Public:** PK.seed, PK.root, the message, the context, the signature, and
  so everything a verifier recomputes from them: the randomizer R, the digest
  and its indices, the FORS public key, every XMSS root, hence every WOTS+
  digit.

Signing cannot have a trace that is independent of the key given its public
*inputs* alone: R and the chain lengths depend on the key and are then
published. The property that can hold, and is proved, is that the trace is
determined by the public key, the message, the context and the signature.

### The model

A run of a function produces, besides its result, a list of events
([Ct/Leak.lean](Ct/Leak.lean), [Ct/Model.lean](Ct/Model.lean)):

- the outcome of every `if`, and so of every loop test;
- for every array, slice or vector element access: the index and the length;
- for every sub-slice: its bounds and the length;
- for every `copy_from_slice`, `push` and `extend_from_slice`: the lengths;
- for every comparison of two arrays: how long their common prefix is;
- for every division and remainder: both operands;
- for a `match` on an optional value: whether it is present.

Not recorded: the operands of addition, subtraction, multiplication and bit
operations, and shift amounts (every shift amount in the code is a public
height or counter). A run that fails has no trace; the functional theorems
show that runs do not fail.

The instrumented program is not written by hand. [Ct/Funs.lean](Ct/Funs.lean)
is the text of the verified translation, `Slhdsa/Funs.lean`, copied verbatim by
`scripts/ct-gen.sh` and elaborated where the primitives it names are the
instrumented ones. Two things tie it to the verified program:

- [Ct/Check.lean](Ct/Check.lean) inspects all resulting definitions (240 in
  the default build, 280 with `hw-sha2`) and rejects any that reaches a
  primitive that is neither instrumented nor on a short list of ones that
  leak nothing in this model.
- [Ct/Erase.lean](Ct/Erase.lean) proves, for each function and constant (208
  and 244), that dropping the trace gives exactly the verified function.

### The `hw-sha2` build

[lean-hw/Ct](../lean-hw/Ct) is the same library over that build's translation.
Every file that does not depend on the build is shared; what is specific is
the instrumented copy, the lemmas for the two functions whose bodies differ
(`sha256::compress`, `hash::chain_blocks`), the lemmas for the hardware
kernels, and a leakage model of the eighteen intrinsic wrappers
([lean-hw/Ct/ModelBuild.lean](../lean-hw/Ct/ModelBuild.lean)):

- the wrappers that load from or store to a caller's slice record the range
  they touch and the slice's length;
- the feature test records nothing itself (the `if` on its answer is a branch
  like any other; whether the processor has the instructions is public);
- **the register-only wrappers record nothing. This is an assumption about the
  processor**: they are fixed-latency vector and SHA-256 instructions, which
  Arm lists as taking time independent of their operands when its
  data-independent-timing mode is on. The crate does not switch that mode on.

The four-lane kernel's control flow has two inputs besides lengths: the step
ranges, which are public, and a cache keyed on the first 16 bytes of a block.
Those bytes are part of the hash address. The lemma about `chain_blocks`
therefore requires the two runs' blocks to agree on their first 16 bytes
(the value bytes are free), and the proofs of the callers show that every
block that reaches it is built from a public address.

### The theorems

- **Key generation leaks nothing** (`keygen_ct`, `keygen_trace`, and the same
  for `slh_keygen_internal`): any two runs, whatever their seeds, return with
  the same trace.
- **Signing leaks only what the signature shows** (`sign_simulated`,
  `sign_deterministic_simulated`, `slh_sign_simulated`,
  `slh_sign_internal_simulated`, and the four `…_checked_simulated`): if a
  signer returns a signature with trace `t`, then a simulator returns with
  the same trace `t`. The simulator ([Ct/Sign.lean](Ct/Sign.lean),
  `slhdsa_leak.Sim`) is given only the public key, the message, the context
  and that signature. It runs the signer's steps with zeros in place of the
  seeds and the randomness, and with each value the signer derives from
  secrets replaced by what a verifier recomputes from the signature.
  The statement is put this way, and not as "two runs with equal public
  outputs have equal traces", because two runs with the same public key and
  signature have practically the same key, which would make the two-run
  statement nearly empty. `sign_two_runs` is that weaker statement, as a
  corollary.
- **A context longer than 255 bytes** (`sign_long_context`): the trace is one
  branch.
- **Keys in transit** ([Ct/Encoding.lean](Ct/Encoding.lean)): comparing two
  private keys and encoding a key have the same trace whatever the keys;
  accepting bytes as a key reveals only their length; decoding an encoded key
  reveals only its length and where its fixed 20-byte (18 for a public key)
  prefix first departs from the expected one.
- **Verification** (`verify_ct`): all of its inputs are public.

The only hypothesis is the message-length bound of the functional theorems.

### What this does not cover

- **The compiler.** The statement is about the Rust source as Aeneas
  translates it. Nothing proves that rustc and LLVM preserve it, and Rust's
  own documentation says the language has no mechanism that guarantees
  constant-time code. This code only copies and hashes its secrets; it has no
  secret-dependent selection or arithmetic of the kind compilers are known to
  turn into branches.
- **The processor.** That an instruction takes the same time whatever its
  operands is a property of the processor, on Arm only promised in its
  data-independent-timing mode, which the application has to switch on.
  Speculative execution, prefetchers, frequency scaling, power and
  electromagnetic emanation are outside the model.
- **Faults.** See the checked signer in the README. When a checked signer
  returns nothing because a recomputation disagreed, its trace shows how many
  leading bytes of the two roots agreed; no claim is made about such runs.
- **The adapter** in `compat/`: its glue is not translated.
- **Erasure of secrets from memory**: tested in `compat/`, not modelled here.

### What is trusted, beyond the functional proof's trust base

`Ct/Model.lean` (which primitive emits what), `Ct/Do.lean` (the elaborator
that turns each `if` of the program text into a recorded branch), the list of
non-leaking operations in `Ct/Check.lean`, and that `scripts/ct-gen.sh`
copies the program text unchanged (it checks this itself).

### Binary-level evidence

`rust/ct-evidence` checks the two compiled builds on one machine (Apple M5,
results of 2026-11-21 in `rust/ct-evidence/RESULTS.md`):

- **Traces, under an emulator:** control flow, memory addresses, allocation
  sizes and copy lengths were identical across secrets in every comparison,
  in both builds: 3,433 secret pairs over 61 component experiments each, and
  the whole signers with the published values pinned (136 pairs default, 264
  `hw-sha2`). Controls that must differ did.
- **Timing:** whole signing, key generation and everything above the hash
  level showed no difference between secrets. Short hash calls did, with the
  processor's data-independent-timing mode off: for example an all-zero input
  block compresses about 0.5 to 1.1 percent faster. With that mode on, nothing
  was distinguishable in either build. Since the instruction and address
  traces for those inputs are identical, the difference arises in the
  processor; the crate does not switch the mode on, and an application that
  needs data-independent timing must.
